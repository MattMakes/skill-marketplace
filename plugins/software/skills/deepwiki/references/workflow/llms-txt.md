# Phase: llms-txt (Phase 8)

## Goal

Generate LLM-friendly entry points into the wiki, following the [llms.txt specification](https://llmstxt.org/):

- `llms.txt` at the repo root — the standard discovery path. Links plus one-sentence descriptions, small enough for any context window.
- `llms-full.txt` in the wiki — the same structure with every page's content inlined, for agents that want the whole corpus in one read.

Both files are derived from the **actual** wiki: page titles, sections, and descriptions come from `{output_dir}/toc.json` and the generated pages, never from a template.

## Inputs

| Name | Required | Default | Description |
|------|----------|---------|-------------|
| `repo_path` | Yes | - | Absolute repository path |
| `output_dir` | No | `docs/wiki` | Documentation output directory |
| `doc_dir` | No | `{output_dir}` | Directory containing the generated `.md` pages |
| `toc_file` | No | `{output_dir}/toc.json` | Supplies `project.name`, `project.description`, page titles and order |
| `language` | No | `en-US` | Output language/locale |

## Outputs

| Path | Description |
|------|-------------|
| `{repo_path}/llms.txt` | Root discovery file — links + descriptions, 1–5 KB |
| `{output_dir}/llms-full.txt` | Full inlined content of every linked page, 50–500 KB |

Links in the root `llms.txt` are relative to the repo root, so they point *into* the wiki: `[Contributor Guide](./docs/wiki/onboarding/contributor-guide.md)`.

## References

- `../toc_schema.md`: structure of `{toc_file}` — the source of page titles, order, and descriptions
- `../evidence_citation_policy.md`: citations inside inlined pages are preserved verbatim

## Prerequisites

This phase reads what `doc-write` produced. If `{doc_dir}` contains no wiki pages, either run the wiki generation phases first, or generate a minimal `llms.txt` from the README plus a source scan — with the section list omitted rather than faked.

## Guard: Never Overwrite a Hand-Written `llms.txt`

Before writing the root file:

```bash
ls "{repo_path}/llms.txt" 2>/dev/null
```

- Does not exist → write it, and include the marker line `<!-- Generated by deepwiki -->` immediately after the H1.
- Exists **with** the marker → regenerate in place.
- Exists **without** the marker → it was hand-written. Do NOT overwrite. Report: `llms.txt already exists at repo root and was not generated by deepwiki — skipping`.

## Workflow

### 1. Gather Project Context

Collect, in this order:

1. **Project identity** — `project.name` and `project.description` from `{toc_file}`; primary language and key technologies from the build manifests.
2. **Wiki pages** — every `.md` under `{doc_dir}`, with its title and section grouping from `{toc_file}`. Exclude `_reports/` and `_context/`.
3. **Onboarding guides** — `{output_dir}/onboarding/`, if the onboarding phase has run.
4. **README** — the core project description, for the blockquote summary.
5. **Key entry points** — main files, API surface, configuration.

### 2. Write `llms.txt` (repo root)

Spec-compliant structure:

```markdown
# {Project Name}

<!-- Generated by deepwiki -->

> {Dense one-paragraph summary: what it does, who it's for, key technologies.}

{2-3 paragraphs of important context: architectural philosophy, hard constraints, what makes this project different. Include the things an LLM would get wrong if nobody told it.}

## Onboarding

- [Contributor Guide](./docs/wiki/onboarding/contributor-guide.md): Environment setup, first task, testing, and the coding conventions this repo actually enforces
- [Staff Engineer Guide](./docs/wiki/onboarding/staff-engineer-guide.md): Architectural deep-dive — design decisions, domain model, component types, and failure modes
- [Executive Guide](./docs/wiki/onboarding/executive-guide.md): Capability overview for engineering leaders — risk assessment, technology investment, scaling model
- [Product Manager Guide](./docs/wiki/onboarding/product-manager-guide.md): Feature-focused guide — user journeys, capabilities, limitations, data and privacy

## Architecture

- [Architecture Overview](./docs/wiki/02_architecture.md): System architecture, component boundaries, and deployment topology
- [Data Model](./docs/wiki/03_data-model.md): Core entities, relationships, and data invariants

## Getting Started

- [Setup Guide](./docs/wiki/01_getting-started.md): Prerequisites, installation, and first run

## Deep Dive

- [{Component Name}](./docs/wiki/04_component.md): What this component owns and where its boundaries are

## Optional

- [Changelog](./docs/wiki/changelog.md): Recent changes and version history
- [Contributing](./docs/wiki/contributing.md): How to contribute to the project
```

**Format rules**

1. **H1** — project name. Exactly one, required.
2. **Blockquote** — a dense, specific summary. Required. Must be unique to THIS project.
3. **Context paragraphs** — non-obvious constraints; the things an LLM would get wrong without being told.
4. **H2 sections** — each holds a markdown list of `[Title](url): Description` entries.
5. **"Optional" H2** — reserved meaning in the spec: everything under it may be skipped for a shorter context. Put changelog, contributing, and supplementary material here — nothing load-bearing.
6. **Relative links only**, resolving from the file's own location.
7. **Section order matters** — most important first: Onboarding → Architecture → Getting Started → Deep Dive → Optional.
8. **Everything is derived** from `{toc_file}` and the real pages. Never ship a template section for a page that does not exist.

**Description quality** — a description says what the reader will *learn*, not what the title already said:

| Bad | Good |
|-----|------|
| "Architecture overview" | "System architecture showing how Orleans grains communicate via message passing with at-least-once delivery" |
| "Getting started guide" | "Prerequisites, local dev setup with Docker Compose, and a first API call walkthrough" |
| "The API reference" | "REST endpoints with auth requirements, rate limits, and request/response schemas" |

The blockquote gets the same treatment. Not "a project for doing things" but "a distributed task orchestration engine built on Orleans virtual actors, providing reliable workflow execution with at-least-once delivery for Azure-hosted microservices". Context paragraphs should surface the traps — e.g. "Although the API surface resembles FastAPI, it uses a custom router that does not support dependency injection."

### 3. Write `llms-full.txt`

Same H1, blockquote, context paragraphs, and section order as `llms.txt`. The link lists are replaced by `<doc>` blocks holding the full page content:

```markdown
# {Project Name}

> {Same blockquote summary}

{Same context paragraphs}

## Onboarding

<doc title="Contributor Guide" path="onboarding/contributor-guide.md">
{Full markdown content of contributor-guide.md}
</doc>

<doc title="Staff Engineer Guide" path="onboarding/staff-engineer-guide.md">
{Full markdown content of staff-engineer-guide.md}
</doc>

## Architecture

<doc title="Architecture Overview" path="02_architecture.md">
{Full markdown content of 02_architecture.md}
</doc>

## Optional

<doc title="Changelog" path="changelog.md">
{Full markdown content of changelog.md}
</doc>
```

**Inlining rules**

- Each `<doc>` carries `title` and `path`. `path` is relative to `{output_dir}`.
- **Strip YAML frontmatter** (`---` blocks) from every inlined page.
- **Preserve Mermaid diagrams** — keep the ```` ```mermaid ```` fences intact.
- **Preserve citations** — every `[file.ts:42](REPO_URL/blob/COMMIT/file.ts#L42)` or `(file.ts:42)` stays exactly as written.
- **Preserve tables** and `<!-- Sources: ... -->` comment blocks — the comments carry diagram provenance.
- Keep the section order identical to `llms.txt`.

### 4. Validate

- [ ] Every link in `llms.txt` resolves to a file that actually exists
- [ ] Every `<doc>` block in `llms-full.txt` has real content — none empty, none placeholder
- [ ] The blockquote is specific to this project, not boilerplate that would fit any repo
- [ ] Sections are ordered: Onboarding → Architecture → Getting Started → Deep Dive → Optional
- [ ] No page appears in two sections
- [ ] "Optional" holds only genuinely skippable material
- [ ] `llms.txt` is 1–5 KB
- [ ] `llms-full.txt` covers every wiki page

### 5. Report

```markdown
## llms.txt Generation Report

- `llms.txt` — root discovery file, {N} sections, {M} linked pages, {size} KB
- `{output_dir}/llms-full.txt` — {N} sections, {M} inlined pages, {size} KB

| Section | Pages | Notes |
|---------|-------|-------|
| Onboarding | 4 | All audience-tailored guides |
| Architecture | 3 | Core architecture pages |
| Getting Started | 2 | Setup and configuration |
| Deep Dive | {N} | Component documentation |
| Optional | {N} | Changelog, contributing |
```

Report any file that was skipped by the overwrite guard.
