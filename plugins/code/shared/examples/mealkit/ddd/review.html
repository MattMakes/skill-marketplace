One modular monolith or split the warehouse service now?

A

One modular monolith now; fulfilment is a module reached from the warehouse over the network.

Pros
  • One deploy, one database, one log to read at 2am
  • Nothing to split until a real runtime constraint shows up
Cons
  • A cloud outage stops packing on the warehouse floor
  • Warehouse latency and uptime needs are ignored until they bite
Risks
  • The fulfilment module quietly reaches into subscription tables and the seam disappears
B

Split the warehouse service now so packing runs on the warehouse network.

Pros
  • Packing keeps working when the cloud link drops
  • Fulfilment can deploy on the warehouse schedule, not the app schedule
Cons
  • Two deploys and two data stores for one person
  • week-charged needs a real contract and an outbox from day one
Risks
  • Distributed failure modes (duplicate box-packed, lost events) arrive before the business has a second site
C

One modular monolith with a warehouse module boundary enforced by a fitness test, split when the runtime need is proven.

Pros
  • Cheapest now; the split stays possible because the test keeps the seam clean
  • The decision waits for evidence instead of guessing
Cons
  • Still one runtime, so the outage problem is only deferred
  • Someone must keep the fitness test honest
Risks
  • The test passes while the shared database still couples the modules underneath
Would flip if
  • The warehouse network is proven unreliable enough that packing must survive a cloud outage
  • A second warehouse or a packing partner appears and needs its own deploy
  • The founder hires a second developer who can carry a separate service

Does billing stay its own bounded context?

Achosen

Keep billing as its own context that wraps Stripe behind an anticorruption layer.

Pros
  • Stripe words (charge, intent, decline code) stop at the ACL; the core keeps saying week-charged
  • The Stripe adapter can be swapped or stubbed in tests without touching menu choice
  • Retries and failed cards are modelled once, in one place
Cons
  • One more module for one person to keep alive
  • Every charge crosses a boundary that in practice is an in-process call
Risks
  • A context that only forwards to Stripe stays thin and tempts people to bypass it
  • The ACL erodes if nobody writes a fitness test for it
Why

Billing wraps a bought capability. Keeping it apart keeps Stripe vocabulary out of the core and turns the ACL into something a fitness test can guard. The cost is one thin module, which one person can carry.

B

Fold billing into subscriptions as a payment policy on the subscription aggregate.

Pros
  • Fewer moving parts; the charge happens where the week is chosen
  • No cross-context message for the most common flow
Cons
  • Stripe types leak into the core model and its tests
  • Declines and refunds start to share a transaction with menu choice
  • Splitting it out later means rewriting the aggregate
Risks
  • A Stripe API change forces a core domain release
  • The subscription aggregate grows into a god object
C

Charge the card synchronously inside the choose-meals request, no billing context at all.

Pros
  • Simplest happy path; one request confirms meals and payment
  • The subscriber sees a decline immediately
Cons
  • Card latency sits on the hot path of the core flow
  • A Stripe outage blocks menu choice for every subscriber
  • Week cut-off and payment retry cannot be scheduled apart
Risks
  • A timeout after Stripe charged but before we saved it double-charges without idempotency keys
  • Fulfilment never learns about a week that was chosen but not charged
Would flip if
  • Payment rules turn out to depend on menu choice state, so the charge and the choice must share one transaction
  • No second payment provider or provider change is plausible within a year and the ACL guards nothing
