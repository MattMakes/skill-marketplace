# Product

ddd review page: the one self-contained HTML file that makes a whole Domain-Driven Design run
(nine step artifacts, decisions, diagrams, contracts) reviewable in one sitting.

All facts below are inferred from the user's brief and the repository (no interview mechanism
was available in this session; the orchestrating agent's brief is the product truth). Inferred
facts are marked (inferred).

## Platform
web

## Stack
Vanilla HTML/CSS/JS generated by Node (ESM, no build, no npm install, no external URLs). One
file, opens from disk. Diagrams are inline SVG drawn by lib/render/diagrams; explorers are HTML
from lib/render/explorers; palette and type from lib/render/core/palette.mjs.

## Users
The designer who ran the ddd chain (a solo founder or a small team lead) and the reviewer they
hand it to (an architect, a stakeholder, a coding agent reading PNGs). Both are tired, both
want to know in one screen what needs a person and what stops the work (inferred).

## Product Purpose
A finished run is 100+ files of dense technical English nobody reads. The page puts the things
that need a human first, in short sentences, and keeps the whole run underneath so a reviewer
never leaves the file.

## Positioning
Not a dashboard, not a wiki: a review sheet. "Illuminate the design with visuals that are
consistent from run to run. Make them beautiful. Don't make this look cookie cutter. And make
the info-dense data easy to understand." (user, verbatim)

## Operating Context
Opened in a browser from disk after `ddd mark` or `ddd review`; read top to bottom on a laptop
or a wide monitor, often printed or screenshotted; regenerated on every step so nothing is
hand-edited. Light and dark both matter (OS scheme) (inferred).

## Capabilities and Constraints
- Renders gates, never re-derives them; reads JSON, never prose.
- Section ids fixed by the plan: verdict, worklist, decisions, shape, diagrams, domain, stores,
  words, steps, canvases, contracts, flows, artifacts, everything.
- Must work on a half-finished run with honest empty states.
- Self-contained: no http(s) URLs, no script src, no web fonts.
- One visual language shared with the diagrams (context colour by id hash, EventStorming
  stickies, one arrow vocabulary, FONTS from palette.mjs).

## Brand Commitments
Typography pinned by palette.mjs: Iowan Old Style / Palatino for titles, Avenir Next / Segoe UI
for labels, SF Mono / Menlo for ids. Twelve curated context hues; accent hues shared with
diagrams (--core amber, --event orange, --command blue, --store green, --external violet).

## Evidence on Hand
The mealkit example workspace (3 contexts, 2 deployables, 3 contracts, 1 flow); rendered
diagrams in /tmp/ddd-diagrams; explorer smoke render /tmp/ddd-explorers.png.

## Product Principles
- What needs a person comes first; the whole run stays underneath.
- Never say OK while a gate says FAIL.
- Show an unknown key rather than drop it.
- A note-trace is a prompt, not an accusation.

## Accessibility & Inclusion
Keyboard reachable folds and search, visible focus, contrast >= 4.5:1 for text in both themes,
no colour-only meaning (labels beside every colour), print-safe.
