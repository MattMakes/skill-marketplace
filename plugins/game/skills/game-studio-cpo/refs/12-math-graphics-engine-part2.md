## Math, Graphics & Engine Internals (continued)

### Spatial Partitioning

- Reduce the all-pairs O(n²) collision/interaction loop with spatial partitioning or sweep-and-prune — sort object extents on an axis and exploit temporal coherence with insertion sort to approach O(n); split moving from static so two static objects never test each other (widely corroborated).
- Solve collision scaling with spatial partitioning, not faster per-pair tests — partitioning turns O(n²) all-pairs into a handful of small cells (e.g. 100M → 500K checks).
- Partition large worlds into a hierarchy (cells, sectors, quadtree for flat worlds, octree for vertical ones, BVH) so you cull vast geometry in a few tests — you cannot throw millions of polys at the pipeline per frame.
- Use sphere trees for culling huge numbers of moving objects — the common case (object stays inside its parent sphere) costs one inline squared-distance test; reintegrate via FIFO queues only when it escapes.
- Prefer bounding-volume trees over space-partitioning trees (BSP/k-d/octree) when splitting triangles or multi-node membership is unacceptable — BV trees stop cleanly at one triangle per leaf with no splitting.
- Use BSP trees for perfect back-to-front (or front-to-back) draw order from any viewpoint via in-order traversal — no per-frame polygon sort, no z-buffer needed; build them offline, and cull whole subtrees when a node is outside the frustum.
- Compress AABB trees aggressively (~11 bytes/triangle) — store child extents as 8-bit offsets relative to the parent and reuse the root index slot to mark leaves; the smaller data set nearly offsets decode cost via cache.
- Replace recursive quadtree traversal with direct array lookup for highly dynamic data — XOR the integer span endpoints to find the deepest fully-containing level and index directly; node-pointer chasing thrashes the cache and mispredicts branches.
- Represent terrain as a grid of sub-terrain chunks (e.g. 32×32 cells) so each chunk culls as one object — a single huge mesh defeats object culling.
- Use a position→value dictionary with a Contains check as the "already generated?" guard for unbounded grids — fast membership test prevents overwriting placed content (object pooling by coordinate).

### Collision Detection & Response

- Test cheap bounding volumes before exact geometry, in a hierarchy (sphere → box/capsule → triangles) — culls the vast majority of non-collisions; a sphere-sphere test is a few ops versus full triangle-triangle (widely corroborated).
- Do sphere-vs-sphere collision by checking center distance ≤ sum of radii — the cheapest object-to-object test; keep it in squared form (compare against `(r1+r2)²`) and defer divides.
- Pick the base bounding primitive to fit the object's topology — spheres for balls, capsules for elongated bodies/characters, boxes/OBBs for boxy objects; a poor fit either misses collisions or fires false positives. Shrink the volume (50–70%) where appropriate, and compute a custom tighter sphere for meshes with long extrusions (tails) to avoid false collisions.
- Build collision/AI/culling at only the accuracy the game needs — a fully general system is often overkill; accept brief sub-pixel interpenetration players won't notice and spend the saved cycles elsewhere. **When it flips:** racing/physics sims demand fidelity → guard physics accuracy as a real bug, since wrong dynamic behavior is immediately felt.
- Use world-axis-aligned boxes (AABB) for cheap per-pair tests but recompute when objects rotate; use OBBs to avoid per-frame recompute at the cost of pricier pairwise tests — choose by whether objects deform (AABB/sphere recompute cheaply for skinned/deforming meshes; OBB best for static geometry).
- Use swept volumes (or substep) for fast/thin objects — a static frame-to-frame test misses a fast missile passing through a tank or a player teleporting through an infinitely-thin wall between frames.
- Detect fast objects tunneling thin walls with outcodes (bitflag regions relative to the world box) — compare current vs previous outcode each frame.
- Default to discrete collision detection — continuous is ~10× costlier and continuous-dynamic ~10× again; reserve them for fast objects that fall through walls, and lower the fixed timestep first as a cheaper fix before resorting to continuous.
- Split Colliders (moving) from Collidables (moving+static) so two static objects never test each other, and mark immovable world geometry as static colliders (no rigidbody) — static colliders go in an optimized data structure (widely corroborated).
- Maintain a curated collection of only the collision pairs that actually matter, not all N² — prune player-vs-prop, skip wall-vs-wall; handle each pair once with symmetric code, and let either side veto the pair.
- Use a linked list, not an array, for a collision-pair collection — deleting one critter/entity removes ~N pairs; in an array that's O(N³), in a list it's cheap.
- Rely on IEEE divide-by-zero (±∞) to handle rays parallel to AABB slabs — the resulting [∞,∞] interval naturally fails the intersection test, removing a special case.
- Treat the surface/edge as "not yet collided" (reserve collision for penetration > 0) — handles the degenerate hit-exactly-on-an-edge case cleanly.
- Cast a ray and test plane intersection for movement blocking, ground height, and mouse picking — one technique answers "did I hit a wall, what's the floor height, what did I click"; reuse it downward for ground height and upward for ceiling/steepness.
- Offset a raycast origin slightly outside the collider — a ray starting inside a collider can miss it entirely; raise the origin and extend the length, and disable "queries start in colliders" so a self-collider doesn't register a false hit.
- Use a downward raycast from the feet pivot for ground checks — simplest reliable grounded test; know a single ray samples one point and can miss at platform edges (scale up to multiple rays, OverlapCircle, or BoxCast as projects grow).
- Reflect a bounce by adding twice the perpendicular-to-plane distance back along the normal, then re-test the new endpoint until no collision — vectors shrink each bounce; apply a damping scalar (0=stop, 1=elastic, >1=adds energy) only to the post-collision segment.
- Move colliding critters apart along their center line after a collision and skip moving fixed critters — two objects shouldn't occupy the same place, and bumpers/walls must not be shoved.
- Approximate complex shapes with several primitive colliders (sphere/capsule/box) instead of a mesh collider — primitives are an order of magnitude cheaper and far more stable for dynamic bodies (widely corroborated).
- Give a mesh collider a simplified collision mesh distinct from the render mesh, and use non-convex/concave mesh colliders only on static geometry or as triggers — physical and graphical representations need not match and players rarely notice; concave-to-concave mesh collisions are catastrophically expensive (often forbidden) (widely corroborated).
- Split a level mesh into separate collision meshes — ground (height), walls/obstacles (blocking), decorative (visual-only) — and test intersection against only the mesh that matters; let walkable geometry double as the height field via a downward ray-cast.
- Generate collision data offline from image transparency, encoded to bitmasks — cheap in-game collision via AND-masks for 2D.
- Verify physics behaviors against high-school physics expectations — a struck crate should decelerate and stop, not keep moving; wrong dynamic behavior signals broken physics code.
- Mark interactive areas with geometric triggers (sphere/box/cylinder/triangle) carrying an ID — pick the cheapest adequate shape; stepping in fires a script without per-pixel checks; use triggers for overlap-without-bounce (pickups, zones) and solid colliders for blocking.
- Ensure at least one of two colliding objects has a rigidbody (both with colliders) — two plain colliders never raise a detection callback; trigger-based sensors also need a rigidbody to fire on a non-moving object.
- Always use the dimension-correct physics callbacks (2D-suffixed for 2D colliders) — plain 3D callbacks silently never fire on 2D colliders (a classic "why isn't my collision working" bug); 2D and 3D physics don't interoperate.
- Guard one-hit-one-target with an isHit flag — a trigger can fire multiple times before the object is removed, causing accidental double damage.
- Prune the layer collision matrix to only necessary layer pairs — every disabled pair removes broadphase bounding-volume checks each timestep and is faster than checking-and-rejecting in code; unchecked pairs skip tests entirely at broadphase, and layers also prevent self-damage/friendly fire (widely corroborated).

### Numerical Integration & Game Physics

- Derive simulation update rules by "turning around" the calculus (velocity += dt·accel; position += dt·velocity) — Euler integration is adequate for most games (widely corroborated).
- Use semi-implicit (symplectic) Euler as the default integrator — it conserves energy and stays stable for position-dependent/spring forces at explicit-Euler cost, far more robust than plain Euler.
- Avoid explicit Euler for stiff systems (strong springs/damping) — its O(h) error makes orbits/oscillators spiral out of control; shrinking the timestep only partly helps and tanks performance.
- Update velocity then position within an integration step, and clamp near-zero velocity/acceleration to zero — wrong order overwrites velocity prematurely; tiny residual velocities cause distracting micro-drift after objects should have stopped.
- Reach for RK4 only when accuracy truly matters — it's O(h⁴) but needs 4 force evaluations per step; for fast frame rates and low accelerations, semi-implicit Euler is enough and far cheaper. **When it flips:** orbital/scientific accuracy → RK4 earns its cost.
- Prefer stability over correctness in game physics — a stable approximate simulation beats a 100%-accurate one that can explode; implicit methods bleed energy (dampen), acceptable since you usually add damping anyway. **When it flips:** competitive racing/flight sims that sell on fidelity → bias toward physical accuracy and validate against real-world behavior.
- Choose liveliness, snappiness, and playability over 100% physical accuracy — approximate gravity (`F = g·m`) and use shortcuts; if an unrealistic tweak plays better, use it (e.g. add only the aim-direction component of the shooter's velocity to bullets, not the full velocity).
- Skip physics for characters' own locomotion — characters control their motion directly; faked acceleration/deceleration reads better than rigid-body feel.
- Use Verlet integration for particle systems with distance constraints (cloth, rope, ragdoll) but not for spinning rigid bodies — Verlet is stable and skips velocity, but its estimated velocity lags a step, making angular dynamics awkward.
- Resolve collisions with impulse-based response, not stiff constraint springs — impulses apply an instantaneous velocity change along the collision normal; stiff springs are hard to integrate stably.
- Set the coefficient of restitution per object in [0,1] — 1 = perfectly elastic, 0 = inelastic/stick; outside [0,1] adds energy or causes attraction/interpenetration.
- Skip the impulse when relative velocity along the normal is separating (negative) — the objects are already moving apart; a response would wrongly pull them back.
- Resolve interpenetration by pushing objects apart along the normal by a fraction of the penetration distance — pushing the full distance looks abrupt; let the impulse finish separating over a frame or two.
- Handle resting contact with a micro-impulse engine, not raw collision response — a box on the floor gains downward gravity velocity each step and would jitter/leap if treated as a fresh collision.
- Resolve multiple simultaneous contacts iteratively (sequential impulses / projected Gauss-Seidel), not by solving one giant linear system — Gaussian elimination is too expensive; accumulate and clamp impulses iteratively (allowing negative accumulation cuts jitter).
- Simplify the physics problem to gain performance — a tank/FPS game is effectively 2D (one moment-of-inertia term, no gravity DOF); ignore force sets that net to zero and use a simple drag coefficient instead of a full friction model.
- Run full simulation only on visible/near/active objects — freeze or simplify distant and at-rest objects, waking them on force/collision, and manage discontinuities so frozen objects don't stop mid-air or jump on reactivation; let physics objects sleep and avoid clustering them, since touching "islands" all wake in a chain reaction causing CPU spikes, and don't re-apply forces/property changes every frame or objects never sleep.
- Translate objects so the model origin coincides with the center of mass — lets one position/orientation representation serve both simulation and rendering; approximate with the centroid or bounding-box center when exact computation is too costly.
- Compute total torque by summing each force's r×F individually — never add offsets and forces first then cross; offsets can cancel to zero torque even when the object clearly rotates.
- Convert the inertia tensor to world space each step (R·J⁻¹·Rᵀ) before computing angular velocity — the tensor is stored in model space but torque/momentum are in world space.
- Conserve momentum and energy in elastic collisions and special-case infinite-mass and equal-mass — equal masses just swap velocities (billiard balls).
- Make object mass proportional to size (density × radius³) even in 2D — 3D-style masses make bouncing look more physical (realism here serves feel, not simulation).
- Keep mass values relative (around 0.1, never over 10) with ratios under ~1000:1 between colliding pairs — improper mass ratios are the top cause of physics instability; increase solver iterations to suppress exploding joints/ragdolls.
- Keep friction/drag intensity small (≈0–1) — too-large drag overshoots the target velocity and oscillates; pair gravity with drag and reduce bounciness, since gravity without friction speeds objects up unboundedly.
- Match force-application mode to intended feel — mass-respecting modes (Force, Impulse) make heavier objects resist and react less; mass-ignoring modes (Acceleration, VelocityChange) make every object react identically; use VelocityChange for predictable jump height independent of mass.
- Drag lives on the rigidbody, not the surface material — increase drag to simulate air resistance; mass alone won't slow a body; a physics material tunes only friction and bounciness.
- Set max velocity and vary angle (not fix angle) when solving trajectory math, and test boundary cases (v=0, cos θ=0, divide-by-zero) — preserves a larger set of reachable landing points and a mistake here crashes the engine; precompute and reuse trig (store `tan θ`) rather than recomputing.
- Predict collisions by passing an exaggerated velocity vector so the test intersects earlier than actual movement would.
- Avoid inverse trig (asin/acos/atan) in hot paths — they're ~10× slower than sin/cos; the ratio itself (e.g. cos θ) often suffices without recovering the angle; when you do need an angle from a 2D direction, use `Atan2 × Rad2Deg` (order is y then x, result in radians).
- Freeze unwanted rigidbody rotation axes via constraints — keeps physics driving position while preventing tipping/rolling/spinning on angled collisions; preserve a body's vertical velocity when overwriting horizontal velocity, or gravity and jumps get wiped.

### Rasterization & the Render Pipeline

- Follow the canonical pipeline order: local→world, object cull, back-face removal, world→camera, clip, perspective, screen, rasterize — rearrange only with intent.
- Use a master polygon/render list as the single stream fed to the rasterizer, stored via an indirection array of pointers — convert all high-level objects to triangles at some stage, and sort/disable polygons without moving payload.
- Carry per-polygon state flags (active/clipped/culled/backface) and skip flagged polys at every stage — one check avoids wasted transforms downstream.
- Rasterize triangles by interpolating dx/dy down each edge per scanline (split into flat-top + flat-bottom cases) — avoids a per-scanline slope-change branch.
- Pick one fill convention (floor/ceil/round) and apply it consistently — being off by one cracks adjacent polygons and causes overdraw between shared edges.
- Use a depth buffer for hidden-surface removal and submit geometry roughly near-to-far — far fragments fail the early depth test, skipping expensive color computation; order independence frees you from per-triangle CPU sorting.
- Use the painter's algorithm (sort polys back-to-front in CAMERA space, then draw) as a cheap first visibility solution — works for small convex polys; it fails on long, overlapping, interpenetrating, or concave geometry, so escalate to z-buffer or BSP when it breaks. Sort an index/pointer list, not the polygon data; for large outdoor scenes sort whole meshes by center with insertion sort.
- Accept that a z-buffer is just a per-pixel painter's algorithm — it trades overdraw for correctness but still reads/writes every pixel, so cull above it; a complex rasterizer (z-buffer/texture) can be net faster than a simple one because early pixel rejection saves more than the extra inner-loop math costs.
- Render opaque geometry first, then blended geometry sorted far-to-near with depth-write disabled — alpha blending is order-dependent and translucent objects must not occlude in the depth buffer; use commutative add/modulate blend modes (great for particles) to skip the sort entirely.
- Clamp/saturate color sums to the channel max (255 / 1.0) after every additive lighting or alpha-blend operation — overflow wraps to garbage.
- Prefer area-based antialiasing and MSAA over SSAA — point-sampling at pixel centers gives flickering edge colors; MSAA computes one shaded color per fragment but multiple coverage samples, far cheaper than SSAA's per-sample shading; sample partial fragments at the covered-sample centroid, not the pixel center.
- Duplicate collocated vertices to allow per-vertex discontinuities — split vertices for sharp lighting edges (cube corners), texture seams (the can-label U=0→U=1 wrap), and any place attributes must differ on either side.
- Render distant scenery with a skybox (textures on a camera-centered cube, depth/lighting/fog disabled, drawn first) — cheap immersion and player orientation; size texels ~1:1 with screen pixels and clamp texture wrapping to avoid seams.
- Use billboards / camera-facing textured quads for cheap pseudo-3D objects (trees, particles) — full meshes are overkill for distant/simple objects.
- Render impostors (cached textures of complex objects, updated every 5–50 frames) for static clutter — slashes bus bandwidth, lighting, texture changes, and per-object overhead; map onto a bounding box (not a screen quad) for camera-independent depth and parallax, use premultiplied alpha through the two-stage composite, and batch render-target switches to scene end.
- Drive impostor/LOD update by a summed screen-space error (animation, lighting, view angle, distance), boosting the update rate for objects near screen center or under the cursor and relaxing it for ambient scenery — players scrutinize what they look at, not the background; bias humanoid animation heavily since the eye reads motion from a few pixels.
- Never read back the frame/Z buffer mid-frame for effects (e.g. lens-flare occlusion) — it flushes the whole pipeline, runs at slow PCI read speed, and many cards forbid it; solve readback-style problems on the GPU instead by accumulating occlusion into a render-target texel via additive blending, keeping work on-card and pipelined.
- Treat the GPU as a general parallel math engine — use blending modes and texture filtering to add, scale, and average samples without CPU involvement.
- Maximize vertex-cache coherency — modern GPUs cache transformed vertices, so reorder triangles (target ~0.65 vertices/triangle); a higher-triangle method can beat a lower one via cache hits; enable mesh import optimization to reorder vertices for free.
- Prefer triangle strips/fans over triangle lists to share vertices — fewer vertices means less memory and faster rendering.
- Minimize time between Lock and Unlock on vertex buffers and flag write-only buffers to place them in fast video memory — the GPU stalls while a buffer is locked.
- Assemble each 2D frame in an offscreen buffer then block-copy/flip once per frame (double buffering) — drawing directly to the live screen flickers; clear the screen first each frame and never assume the window starts or stays blank.
- Render 2D through a 3D engine where possible — scaling/zoom effects become almost free where any other method is prohibitively expensive; prefer geometric (polygon) sprites over bitmaps (scale-independent, crisp, rotatable).
- Use the active scene's draw-order layers (sorting layers coarse + order-in-layer fine), not Z position, for 2D — keeps camera math simple and avoids surprises with 2D lighting, which sorts by these values; sorting layers affect rendering only, never physics.

### Texturing & Filtering

- Interpolate texture coordinates perspective-correct (projective), never screen-affine — affine UV interpolation makes parallel texture lines bend at triangle edges and skips perspective convergence; Gouraud color can sometimes get away with affine, UVs cannot. **When it flips:** for small, near-screen-parallel polys → affine mapping is fine and cheaper.
- Mipmap every texture and supply a full pyramid down to 1×1 — avoids shimmering/flicker from point-sampling minified textures and improves cache behavior (smaller distant textures fit in cache), often a net performance win. **When it flips:** for textures always rendered at constant camera distance (UI, 2D, near-player FX) → disable mip maps — they add ~33% size for levels never used.
- Use bilinear filtering for magnification and trilinear (linear mipmap + bilinear) for the smoothest minification — nearest-neighbor produces blocky texels; trilinear blends mip levels to hide the level switch. **When it flips:** for pixel art → use point (nearest) filtering, no compression, and a consistent pixels-per-unit — bilinear blurs edges and compression mangles flat colors.
- Use anisotropic filtering for surfaces seen at grazing angles — isotropic mip selection on long-thin texel footprints looks too blurry or too sharp. **When it flips:** for textures never seen at oblique angles → disable it as a needless runtime cost.
- Bias mipmap selection per taste/platform but know the tradeoff — negative bias = crisper + more texels/fragment, positive = smoother + fewer.
- Pack many small images (tiles, sprite frames, glyphs) into one texture atlas and draw all polys using a texture before switching — texture setup (format conversion, upload) is costly, so batch by texture and minimize state changes, cutting draw calls. **When it flips:** don't atlas textures for skinned/animated characters → they can't batch, so it saves nothing but space; watch atlas size against the device texture-cache limit or it thrashes.
- Use 24/32-bit color for final framebuffer output, floats only for intermediate computation — display devices resolve only 5–8 bits/channel, so full-float output wastes storage and bandwidth.
- Remap out-of-range HDR colors with tone mapping or scene-wide scaling, not per-color clamping — clamping desaturates bright colors toward white and loses highlight detail; scene-coherent scaling preserves relative brightness like a camera's auto-exposure.
- Pack material channels into texture maps (diffuse, specular/gloss, glow/emissive) and reuse spare alpha channels — saves GPU memory.
- Clip decals to a box of six boundary planes around the surface, then assign alpha by normal·direction and texcoords by distance from tangent/bitangent planes — projects decals onto arbitrary curved geometry.
- Pack multiple images per texture file using regions/UV coords — faster on consoles/DirectX/OpenGL/WebGL (only UV coords upload per frame) and easier to manage.
- Budget memory bandwidth — fetching an uncached texture costs its full size in bandwidth; reduce texture quality/size if bandwidth-bound, and use mipmaps in 3D scenes to cut VRAM↔cache traffic.
- Limit texture variation per scene to stay under VRAM — exceeding it causes texture "thrashing" (constant evict/refetch), a classic console-to-desktop port killer; preload textures by placing a hidden textured object on the player's route to avoid the blank-texture pop from async VRAM loading.

### Lighting & Shading

- Model lighting as ambient + emissive + Σ(diffuse·(n·l)) + Σ(specular·max(r·v,0)^sp) — keep terms independent so lights can affect channels selectively.
- Always self-shadow the diffuse term with `max(0, L·n)` and explicitly gate specular on `L·n > 0` — without the gate, back-facing surfaces can still produce specular highlights (r·v can be positive when L·n is negative).
- Use per-fragment (Phong) lighting for specular and per-vertex (Gouraud) for ambient/diffuse — specular is highly nonlinear and Gouraud interpolation misses or flashes highlights between vertices as objects move; ambient/diffuse are near-linear and interpolate fine.
- Do work in the vertex shader when the visual result is identical to per-fragment — vertex shaders run far less often; only push to per-fragment what genuinely needs it.
- Flat-shade faceted objects, Gouraud-shade objects meant to look smooth — Gouraud on a cube looks wrong, flat on a sphere looks faceted; accept Gouraud's screen-space color distortion since the eye barely notices it on lighting (unlike textures).
- Perform lighting after model-to-world but before camera-to-perspective (in world or camera space), never in screen space — distance attenuation needs a consistent scale across all objects, and per-object model scale would distort it.
- Approximate the view vector as constant ("infinite viewer") and use the halfway vector with directional lights — makes the specular halfway vector constant per object, computed once as a uniform instead of per-fragment.
- Choose light type by need: directional (no position/falloff, cheapest) for sun, point (distance attenuation) for bulbs, spotlight (cone + distance, most expensive) for flashlights — match shape to fixture, and fake the spotlight when possible.
- Skip spotlight math entirely when a point lies outside the light cone — test `-L·d ≥ cos(θ)` first and early-out.
- Keep point-light attenuation simple — a small linear term usually beats the full constant+linear+quadratic model; quadratic falls off too fast.
- Generate smooth vertex normals analytically when the surface is known, else average incident face normals — analytic best captures the surface; the accumulate-face-normals-then-normalize loop works from raw index lists in one pass.
- Use normal mapping (auto-generated from high-poly source) for fine surface detail — adds real per-fragment normals so bumpy lighting responds to moving lights, without the vertex cost of modeling the detail.
- Author textures fully-lit and modulate with lighting — multiply (modulate) so light darkens the texture, then add specular after the modulate ("modulate with late add") so highlights wash out the surface instead of only darkening.
- Group coincident vertices before deforming a mesh / before Gouraud averaging — moving one of a cluster splits seams and renders back faces transparent; average shared-vertex normals so smooth shading reuses the texture-mapping interpolation machinery.

### Baked vs Dynamic Lighting

- Bake lighting whenever the scene's lighting doesn't change during gameplay — precomputing light/shadow into lightmaps removes most lighting work from runtime and is often the highest-impact optimization for static environments (widely corroborated). **When it flips:** lighting that must change dynamically (day/night, destructible lights, moving sources) → must stay real-time; baked lightmaps are frozen.
- Use baked lighting to gain free indirect light (bounce, color bleed, soft fill) — it captures effects real-time lighting can't reproduce efficiently, at zero runtime lighting cost; bake ambient occlusion into the lightmap even when using SSAO.
- Never bake lighting onto dynamic objects (player shadows, moving props) — a moving object baked as static drags its lightmap along and looks obviously wrong; mark only truly stationary objects Static before baking.
- Set lights to Baked when only static surfaces need them, Mixed for key lights (the sun) that must also light dynamic objects in real time, Realtime only for lights that genuinely move/change — Baked is cheapest but ignores movers; Mixed bakes indirect onto static surfaces while casting real-time direct light on movers.
- Treat real-time lighting/shadows as the single most expensive visual feature and highest-impact optimization target — shadows especially dominate frame cost, and relying entirely on real-time is "a recipe for disaster" outside tiny scenes; bake static lighting (lightmaps) and tune quality per platform, since precomputed lighting is far cheaper than real-time for static scenes.
- Lower shadow distance and expose it as a user quality setting — each shadow caster/receiver is another draw call, so don't render distant shadows; use shadow cascades to keep shadows sharp near camera and cheaper far away, keeping resolution/cascades only as high as needed.
- Tune bake quality with samples/bounces/resolution as the levers — Indirect Samples for smooth bounce, Max Bounces 2 (3 for small enclosed scenes), lightmap resolution by camera distance (~30 texels/unit distant, ~40 close-up); treat the first bake as a baseline and refine.
- Generate lightmap UVs on the model when baked shadows streak up walls or come from impossible directions — imported models often lack lightmap-compatible UV channels; keep lightmap padding ~2 to stop adjacent UV islands bleeding.
- Bake reflection probes instead of updating them per frame in VR — real-time reflection updates are too expensive for the tight VR frame budget.
- Add self-shadowing to characters — a high-value visual cue missing from most games; segment into convex pieces and project to avoid depth-aliasing; prefer priority-buffer shadows for inter-object shadows and depth/volume techniques for self-shadowing (combine hybrids since no single method does both well).

### Shaders & Draw Calls

- Minimize materials to minimize render-state changes — every state change forces costly GPU synchronization and a new draw call; a new draw call is cheap only if render state is unchanged, so group objects sharing materials/shaders to keep the GPU in the same state (widely corroborated).
- Watch batch/draw-call count as a top rendering metric — each draw call is a CPU→GPU command, and too many make the CPU the bottleneck before the GPU is even stressed; diagnose CPU-bound vs GPU-bound first, because the fix differs entirely.
- Mark stationary environment geometry (buildings, roads, set pieces) as Batching Static to pre-combine compatible meshes into far fewer batches — cuts CPU draw-call overhead dramatically. **When it flips:** never mark moving objects static (a baked-in combined buffer assumes the object never moves); never static-batch many identical duplicates (each clone is copied with hard-coded transform, costing N× the mesh memory); and always check memory after enabling, since it can balloon.
- Rely on the SRP/scriptable-pipeline batcher (and GPU instancing) by keeping objects on the same shader variant or sharing one mesh+material — it caches material properties in GPU memory and renders compatible objects back-to-back without state changes, even when colors/textures differ. Aim for shader compatibility, not material identity.
- Use dynamic batching only for many small simple moving meshes (under the vertex-attribute budget) — it has strict vertex limits, doesn't batch skinned meshes, and batch-detection overhead can exceed the draw calls it saves.
- Choose a LOD/VIPM method by the right axis — global vs instance vs streamed memory, CPU cost, API-call efficiency, bus bandwidth, vertex-cache coherency; different objects warrant different methods, and make binned triangles degenerate (don't remove) so triangle order stays free for cache coherency.
- Optimize shaders aggressively — small gains compound across millions of fragments; use the smallest precision (half/fixed over float, especially mobile), prefer built-in helper functions the compiler optimizes well, and don't change precision while swizzling.
- Avoid conditionals/branching and strong data dependencies in shaders — GPUs can't branch-predict (divergent cores process every path), so absorbing redundant math often beats a branch; chained calculations block instruction-level parallelism, so write independent fetches.
- Replace complex shader math (pow/exp/log) and per-pixel-invariant calculations with a precomputed lookup texture or CPU-side material properties/generated textures — sneak data into an unused texture/alpha channel for near-zero cost; think of shaders as raw data transfer, not just visuals.
- Minimize and sequentialize texture lookups in shaders — random-order sampling causes GPU cache misses; reorder textures for sequential access.
- Use shader-based LOD to render distant objects with simpler shaders, and disable unnecessary shader features (extra passes, Z-write, alpha test/blend) and remove unused input/geometry/vertex/fragment data — each consumes fill rate or memory fetches, and this saves across hardware tiers.
- Limit Forward-rendering pixel/point lights and set minor lights to "Not Important," capping pixel light count — each adds a shader pass per object, exploding draw calls; expect the engine to cull excess visible real-time lights past its cap, so manage them deliberately or pick a rendering path built for the load (missing/flickering lights are a warning sign, not a bug).
- Reduce overdraw — pixels redrawn many times silently eat fill rate; use the scene-view overdraw mode to find hotspots, treat resolution as a fill-rate multiplier, and reduce vertex counts to fix front-end (GPU vertex) bottlenecks.
- Use GPU skinning to offload skinning from a CPU-bound app, or disable it if GPU-vertex (front-end) bound — move the cost to whichever side has headroom; reducing polygon count is the main lever for animated meshes (which can't batch).
- Pre-jitter the priority buffer (pack 4 neighbor IDs into RGBA) so one fetch does all four shadow tests — kills ID-aliasing without 4 separate fetches.
- Audit post-processing cost in the frame debugger before committing — a single effect (bloom downsample/upsample chain) can add many render passes.

### Level of Detail & Geometry Budget

- Check polygon/triangle count early when a scene runs slow — every visible triangle scales GPU work with camera view.
- Manage poly count by either lowering mesh resolution outright or using LOD to swap simpler meshes at distance — LOD preserves quality where the player looks while cutting cost where they don't. **When it flips:** for indoor/top-down (RTS/MOBA) scenes → skip LOD; don't pre-optimize with it on faith, since it costs dev time, memory, and CPU and only pays in expansive outdoor/long-camera scenes.
- Author multiple LOD meshes per model (full / medium / minimal) in the DCC tool by hand or decimation — distant simplification is nearly invisible and can cut triangles ~30× (e.g. 28M → 1.1M triangles); add a Culled state so objects too small to matter stop rendering entirely.
- Tune LOD transition thresholds by scrubbing the camera preview to natural distances, and enable cross-fade only on LOD groups whose silhouette/reflective material changes visibly between levels — default thresholds swap too early/late/noticeably; cross-fade hides the instant "pop," and matte materials and fog hide it anyway.
- Accept that all LOD levels stay loaded in memory — LOD trades GPU workload for memory, so measure the memory cost against your target like any other trade.
- Minimize per-instance LOD memory by sharing static global mesh data across all on-screen instances — duplicate only what truly varies per instance.

### Procedural Generation Math & Noise

- Pick a sphere/mesh algorithm by cost: a seamless icosphere has fewer, shared vertices than a polar sphere — fewer vertices removes the need for vertex-grouping fixes and runs faster.
- Never nest extra per-element work inside generation/update loops — looping over all vertices for each moved vertex turns linear work exponential and can hang/crash; cap generation scale to a tested budget.
- Build dynamic terrain from a shared vertex grid with interchangeable index buffers as LOD templates — hardware T&L stays enabled and a height-map drives vertices; use interlocking "body" + "link" buffers and link only downward in detail to stitch different-LOD neighbors without cracks; select terrain LOD by distance and avoid abrupt detail pops at tile boundaries.
- For terrain following, lift/drop objects to the patch height AND rotate so their up-vector aligns with the patch normal — height alone makes objects float flat.

### Random Numbers

- Don't trust the language's built-in RNG and never invent your own algorithm — standard generators are often weak (poor period, correlated low bits, planar clustering); copy a vetted one (Mersenne Twister for quality, multiply-with-carry when memory is tight).

### Engine Architecture for Math/Graphics Systems

- Don't put virtual functions in tiny, heavily-used classes (Vector, Matrix) — the vtable pointer per object plus call indirection (and i-cache miss risk) costs more than it's worth; devirtualize inner-loop calls via cached data and inline accessors.
- Cache loop-invariant calculations and precompute at load time anything that doesn't change with transforms (a polygon's normal length is transform-invariant) — gains speed and accuracy; but don't precompute what you'd then have to transform anyway, since precomputing a normal vector is a wash because you must rotate it each frame.
- Hoist invariant if-tests out of loops by splitting the loop into ranges — the condition is never evaluated inside the hot path; structure conditionals so the common branch is the taken path to avoid pipeline flushes.
- Profile before optimizing, on a release build with debug symbols, on representative target hardware — debug timings mislead; pick fights by measured percentage of frame time and re-profile after every fix; a few lines (a z-buffer clear) may beat reworking 1000 lines of lighting (widely corroborated).
- Choose an efficient algorithm first — no amount of assembly makes an O(n²) algorithm fast; fix the algorithm before the code, and let the optimizing compiler emit FPU code, dropping to hand assembly only for the few tiny, hottest inner-loop functions, not large ones.
- Use lookup tables with linear interpolation for sin/cos/sqrt/trig (with the bias trick for indexing) — ~10–16 cycles vs ~80–140 for the C library, when the table stays in cache; size tables to stay in cache and, if a table won't fit, prefer polynomial approximation (more compute, fewer memory touches); decompose by exponent/mantissa for logarithmic-quantized lookup.
- Lean on the engine's built-in optimized systems (collision, physics, pathfinding, particles, draw-call batching, the game loop) instead of rolling your own — these are pre-solved hard problems.
- Separate data from behavior in data-oriented design — components hold only data (plain value-type structs, no methods/logic), systems hold only logic and are entity-agnostic; lay same-type data contiguously rather than scattered per-object so sequential access is cache-friendly and compiler-optimizable, the main reason ECS/data-oriented design scales to tens of thousands of entities.
- Move per-entity work into parallel jobs and opt hot numeric systems into a native compiler (Burst) — parallelism removes the single-threaded bottleneck; keep job code allocation-free and free of managed types so the compiler can optimize aggressively, and pass frame-context data (delta time, elapsed time, RNG seed) into jobs as explicit fields each frame since jobs can't read static Time/Random APIs.
- Profit from data-oriented/ECS most when per-entity logic is simple and uniform — simple movement scales to 20k+ entities cheaply, while heavy per-entity AI/physics raises cost proportionally; at extreme counts rendering, not gameplay logic, often becomes the bottleneck, so profile to find the true limit and budget accordingly.
- Treat optimization as managing scale, not eliminating cost — a few heavy meshes/lights/UI elements are fine; problems emerge when costs accumulate across a whole scene, so layer multiple targeted fixes (draw calls + shadows + hidden geometry) rather than hunting one magic setting, since each is bigger together than alone.
