# Rendering/Batching, Data Layout, ECS & Scheduling

## Draw Calls, Batching, Culling & Assets

### Draw Calls & Batching Fundamentals
- Treat draw calls / batches as a primary CPU cost — each is a CPU→GPU render command, so too many leave the GPU idle and make the CPU the bottleneck before the GPU is even stressed. (Unity5Opt; Unity6Opt)
- Minimize render-state changes by minimizing materials — each texture/shader/lighting swap forces costly GPU synchronization and waiting for the current batch to finish; share materials across visually similar objects and avoid unique materials without reason. (Unity5Opt; Unity6Opt)
- Reduce batch count to free the CPU — fewer rendering commands means less CPU time per frame in scenes with many objects, and fewer materials give Unity more batching opportunities. (Unity6Opt)
- Treat a very high batch count as the clearest warning sign — it means the CPU is spending too much time submitting rendering work to the GPU; address the highest batch count first. (Unity6Opt)
- Diagnose CPU- vs GPU-bound via the CPU/GPU Usage areas and the Rendering module — CPU-bound = high CPU rendering time with idle GPU (e.g. ~15k draw calls); GPU-bound = GPU time far exceeds CPU; brute-force confirm by disabling batching/atlasing and watching FPS worsen. (Unity5Opt; Unity6Opt)
- Use the Frame Debugger to inspect what each draw call does and find redundant ones — step through draws to spot unnecessary objects, shadow passes, transparency cost, and read vertex counts/mesh names/shader state to see why a batch is larger than expected. (Unity5Opt; Unity6Opt)
- Minimize per-frame data crossing the slow bus — on PC the AGP bus (~500MB/s) is commonly the limiting factor, far slower than CPU↔system-memory and GPU↔video-memory; minimize per-frame data sent across it. (GPGems2)

### Static Batching
- Mark stationary objects Batching Static so Unity pre-combines compatible meshes/materials sharing a material into one mesh at init — no per-batch vertex limit; collapses tens of thousands of draw calls into a few thousand (e.g. 73k→3k batches, +20 FPS). (Unity5Opt; Unity6Opt)
- Apply static batching only to environment geometry that never moves (buildings, roads, obstacles, background) — never to player, enemies, or moving props, whose combined buffer would be wrong. (Unity5Opt; Unity6Opt)
- Never instantiate or move statically-batched meshes at runtime — new statics aren't auto-merged and moving them triggers huge CPU recalculation; all must exist in the original scene. (Unity5Opt; Unity6Opt)
- Budget the static-batching memory cost explicitly — Unity builds one combined vertex buffer storing every batched object's verts separately at its world position while keeping the original shared mesh, so memory can rise sharply (e.g. 170MB→420MB, or 1000 trees = 1000x mesh memory); re-check the Memory module after enabling, especially on mobile/older GPUs with limited VRAM. (Unity5Opt; Unity6Opt)
- Avoid one giant static batch where any visible vertex draws the whole mesh — a single visible vertex renders the entire combined mesh; duplicate materials to force separate static batches in large outdoor scenes (must be done in Editor, before custom init scripts), or use occlusion culling for connected rooms. (Unity5Opt)
- Combine many small never-moving meshes into a single mesh manually only when static batching is unavailable or the mesh must move — equivalent to static batching but generates a new asset (tedious, same partial-visibility risk). (Unity5Opt; Unity6Opt)

### Dynamic Batching
- Enable dynamic batching for large groups of simple, near-identical moving meshes sharing a material — bundles visible meshes into one runtime batch, freeing CPU for AI/physics. (Unity5Opt; Unity6Opt)
- Satisfy all dynamic batching requirements or it silently fails (often hurting performance): same material ref, ≤900 shader vertex attributes, mesh/particle renderers only (not skinned), consistent uniform-or-nonuniform scale, same lightmap, single-pass shader, no real-time shadows, ≤300 meshes & ≤32k indices per batch. (Unity5Opt)
- Mind the 900 vertex-attribute budget per dynamic batch — a 3-attribute shader allows ~300-vertex meshes, a 5-attribute shader only ~180 (an auto-sphere's 515 verts can't batch). (Unity5Opt)
- Avoid negative scales (1 or 3 negatives) if you want dynamic batching — they exclude the mesh from the batch (0 or 2 negatives are fine). (Unity5Opt)
- Don't create many tiny dynamic batches — batch detection/generation overhead can exceed the cost of separate draw calls when each holds only a few meshes; treat dynamic batching as usually less impactful than static batching. (Unity5Opt; Unity6Opt)

### GPU Instancing & SRP Batcher
- Consider GPU instancing for large counts of identical meshes — an alternative to static batching for repeated geometry that avoids duplicating per-instance vertex memory. (Unity6Opt)
- Rely on the SRP Batcher (URP default) to cut per-material CPU overhead — it keeps individual draw calls but caches material properties in GPU memory so they aren't re-uploaded each frame; back-to-back objects sharing a shader variant render without expensive state changes. (Unity6Opt)
- Ensure objects share a compatible shader variant for SRP batching, not identical materials — color/texture differences are fine; incompatible shader variants fragment batches (visible as many separate "SRP Batch" events). (Unity6Opt)
- Tint sprites via SpriteRenderer.color, never renderer.material.SetColor — color writes the per-vertex color attribute and creates no material instance and no extra draw calls, so a scene full of enemies flashing red on hit generates no extra draw calls; it is safe to call every frame on many sprites without breaking batching. (BulletHell)
- Avoid reading renderer.material for per-instance effects — it clones a per-instance material, breaks SRP batching, and leaks memory if not cleaned up; use MaterialPropertyBlock + SetPropertyBlock so many objects share one material asset. **When it flips:** on URP/HDRP, MaterialPropertyBlock is incompatible with the SRP Batcher → prefer SpriteRenderer.color for simple 2D tints to avoid losing batching. (BulletHell)

### Atlases, Textures & Mipmaps
- Atlas small textures into one big texture to cut materials/draw calls and exploit dynamic batching — no quality/memory loss, but no memory-bandwidth reduction (same data pushed). (Unity5Opt)
- Keep atlases within the target device's max texture size — oversized atlases get split, and per-draw-call texture swaps between pieces cause cache misses and memory-bandwidth choking. (Unity5Opt)
- Don't atlas animated (skinned) characters for batching — skinned meshes can't be dynamically batched; each needs a per-object bone transform = separate draw call regardless. (Unity5Opt)
- Use mipmaps for varying-distance 3D textures (~33% larger file) but disable for 2D/GUI/always-near textures — mipmaps cut VRAM↔cache bandwidth and aliasing but waste space when alternatives are never used (use the Mipmaps shading mode to find candidates). (Unity5Opt)
- Keep total simultaneous texture usage below VRAM to avoid thrashing — overflowing VRAM forces back-and-forth refetch (worsened by fragmentation), a common console→desktop port problem; preload textures (hidden object on the player's route, or a hidden material's texture) to avoid blank-texture placeholders during async VRAM load. (Unity5Opt)
- Keep textures within the device's small texture-cache limit on mobile and reuse textures — oversized textures get CPU-downscaled at init (wasted load time, unintended quality); check per-device max (1024² OpenGLES1.1, 2048² ES2.0, 4096² later). (Unity5Opt)
- Make textures square and power-of-2 on mobile — non-square/non-pow2 can't be GPU-compressed and waste bandwidth on padding; if forced non-square, raise compression bitrate for free quality at identical imported size. (Unity5Opt)
- Test platform-specific GPU compression (DXT/PVRTC/ETC/ASTC) only as a last bandwidth resort — the wrong format forces costly CPU recompression and per-device tuning commits you to per-device support. (Unity5Opt)
- Set texture Compression to None only where artifacts matter (clean-edged pixel-art sprites) — compression trades visual fidelity for smaller texture memory and is a memory win in general, so accept it elsewhere. (BulletHell)
- Use procedural texture animation on the GPU instead of canned frame sequences — endless non-repeating fire/smoke/water from 2-3 frames of memory uses a tiny fraction of the storage/bandwidth of prerendered animation. (GPGems2)

### Shader Cost
- Optimize shaders to protect fill rate — a slow stage stalls the whole parallel thread, delaying all future fragments, so small shader wins yield big back-end gains; use built-in mobile shaders even on desktop when quality loss is acceptable. (Unity5Opt)
- Use the smallest precision data types in shaders (half/fixed over float) — GPUs (especially mobile) compute smaller types faster and color values tolerate reduced precision well; avoid changing precision while swizzling (the conversion is especially costly), and pick one precision across the board. (Unity5Opt)
- Prefer Cg/UnityCG.cginc helper functions (abs, lerp, mul, step, Luminance) over custom math — built-ins are better GPU-optimized than compiled custom code. (Unity5Opt)
- Disable unnecessary shader features (multi-pass, transparency, Z-write, alpha test, alpha blend) — each consumes fill rate; approximate the effect without them where possible. (Unity5Opt)
- Remove unused shader input data and don't expose unnecessary material variables — unused inputs still get fetched from memory, and exposed variables block compile-time constant optimization and must be re-pushed each pass. (Unity5Opt)
- Replace complex shader math (pow/exp/log) with a precomputed lookup texture — sneak data into an unused texture/alpha channel for near-free CPU offload; push per-frame-constant or per-pixel-constant work to CPU via material properties or generated textures. (Unity5Opt)
- Minimize texture lookups and order them sequentially — texture sampling is the top GPU memory-access cost; random-order sampling and multi-sample shaders inflict cache misses. (Unity5Opt)
- Avoid conditional/branching statements in shaders — GPUs lack CPU branch prediction, so an if-else makes cores process both paths unless all take the same one; absorb redundant math instead. (Unity5Opt)
- Avoid strong data-dependency chains in shaders — dependent steps serialize fetches; independent fetches let the compiler parallelize across threads. (Unity5Opt)
- Use Surface Shader hints (approxview, halfasview, noforwardadd, noambient) to cut cost — noforwardadd limits to one directional light (single pass, fewer draw calls); noambient removes ambient math. (Unity5Opt)
- Use the lowest-precision shader formats on mobile and avoid format conversions — mobile GPUs are especially precision-sensitive. (Unity5Opt)

### Overdraw & Fill-Rate
- Split GPU diagnosis into front end (vertex/geometry) vs back end (fragment/fill) — different bottlenecks need different fixes; brute-force test for fill-rate bounding by reducing screen resolution (a big FPS jump fingers fill rate). (Unity5Opt)
- Reduce overdraw — use the Scene-view Overdraw shading mode to find pixels drawn repeatedly; overdraw multiplies fill-rate cost. (Unity5Opt)
- Brute-force test for memory-bandwidth bounding by reducing texture quality (Half/Quarter/Eighth Res) — smaller textures ease VRAM→cache transfer; an FPS jump fingers bandwidth, and budget bandwidth per frame (bandwidth ÷ FPS) per core. (Unity5Opt)
- Avoid alpha testing on mobile in favor of alpha blending — alpha testing remains particularly costly on un-optimized mobile GPU chips. (Unity5Opt)
- Use Shader-based LOD (LOD keyword / maximumLOD) to render distant objects with simpler shaders — saves fill rate across varied hardware. (Unity5Opt)
- Render skyboxes first, full-screen, with depth test and write disabled, no clear, no lighting/fog — they always fill the screen and won't intersect scene geometry, so skip the color-buffer clear entirely; size the skybox only so its corners fall inside the far clip plane (absolute size is irrelevant since the camera sits at center). (GPGems2)

### Frustum, Occlusion & Sphere-Tree Culling
- Rely on automatic frustum culling but know its limit — it skips objects outside the view cone but still renders objects inside the frustum that are fully blocked by other geometry, including their lighting and shadows. (Unity5Opt; Unity6Opt)
- Bake occlusion culling so Unity skips geometry hidden behind other geometry — precomputes per-cell visibility (scene divided into a grid; runtime looks up the camera's cell) instead of expensive per-frame tests, yielding big wins (e.g. 70→180 FPS, 8M→1.2M triangles); needs Occluder/Occludee Static flags and costs RAM + per-frame CPU. (Unity5Opt; Unity6Opt)
- Mark participating objects both Occluder Static (can block) and Occludee Static (can be hidden) — in dense scenes most buildings need both so they hide others and are hidden in turn. (Unity6Opt)
- Set Smallest Occluder sensibly (e.g. 5 for a city) and Smallest Hole (e.g. 0.25 for architecture) — too-large occluder means small walls won't occlude; smaller hole gives tighter culling with fewer false positives but slower bakes; reduce both and re-bake to cut pop-in. (Unity6Opt)
- Reserve occlusion culling for view-blocked layouts (dense cities, indoor, corridor, room-based) — it earns its bake cost where solid geometry frequently hides large amounts of scene. **When it flips:** in wide-open scenes the problem is distant visible geometry, not hidden geometry → prefer LOD over occlusion culling. (Unity5Opt; Unity6Opt)
- Use a sphere tree for fast frustum culling, range, and ray queries — no leaf is ever in more than one node (unlike quad/octrees where boundary-straddling objects appear twice), so culling a super-sphere culls all children with one test; add a "gravy"/slop margin around bounding spheres so objects don't detach from their parent as they jitter near the boundary. (GPGems2)
- Update a moving object in the sphere tree with one inline squared-distance check against its parent — if still inside the parent radius (almost always) return immediately; only pierce-through triggers a couple of pointer-swap reinsertions. (GPGems2)
- Fire culling callbacks only on state change (in/out of frustum) and cache last-frame state per node — lets the sim cheaply maintain the exact list of visible objects. (GPGems2)
- Cull shadows, animations, and special effects alongside geometry — culling visible geometry alone is not enough; mark the whole object subtree active/inactive. (GPGems2)
- Prefer bounding-volume (AABB) trees over space-partitioning trees (octree/k-d/BSP) when you want bounded node count — partitioning planes force triangle splits or multi-node inclusion (no size bound); BV trees just stop at one triangle per leaf. (GPGems2)
- Disable non-visible component logic via OnBecameVisible/OnBecameInvisible, and disable far-away objects by distance via a periodic coroutine — skip AI/scripts on offscreen or too-distant objects (not viable for full-simulation games). (Unity5Opt)

### Level of Detail (LOD)
- Use LOD groups to swap to simpler meshes as objects shrink on screen — preserves close-up quality while slashing distant triangle cost (e.g. 28M→1.1M triangles, ~30x), easing vertex/animation load in scenes with large views and camera movement. (Unity5Opt; Unity6Opt)
- Author multiple measurably-cheaper mesh variants (LOD_0 full, LOD_1 medium, LOD_2 minimal) by hand or decimation — verify each level with the triangle counts shown per renderer. (Unity6Opt)
- Enable the Culled LOD state so far-enough objects stop rendering entirely — if an object contributes nothing to the image, render nothing. (Unity6Opt)
- Tune LOD transition thresholds so swaps happen at natural distances, and account for the global LOD Bias multiplier (Quality Settings, default ~2.0) — poor thresholds make objects change too early/late/noticeably, and bias shifts all transition distances so device Quality levels behave differently than the Editor. (Unity6Opt)
- Use Cross Fade mode (optionally Animate Cross-fading) to hide LOD pops — instant swaps pop visibly, worst on reflective materials or changing silhouettes; scale back any LOD/approximation the moment the player notices it pop, since LOD is about getting away with less work invisibly. (GPGems2; Unity6Opt)
- Account for all LOD levels staying resident in memory — only one renders at a time but Unity keeps every level loaded to switch; LOD trades GPU work for memory. (Unity6Opt)
- Don't pre-optimize with LOD where it isn't needed (indoor/top-down/RTS/MOBA) — LOD costs artist time, extra mesh memory, and per-frame distance checks; vertex processing is rarely the modern bottleneck. (Unity5Opt)
- Use View-Independent Progressive Meshing (VIPM) for discrete-object LOD — it beats static LOD and VDPM for visual quality per CPU cost on current hardware; keep used vertices in one contiguous block (bin from the list end) so software T&L only processes live vertices. (GPGems2)
- Order triangles for vertex-cache coherency, not strictly by collapse order — strip/cache-optimal ordering hits ~1.0 vertices/triangle while collapse-order forces poor cache use (vanilla VIPM's main weakness); bin triangles by making them degenerate (move a vertex onto another) rather than reordering, since hardware rejects degenerates cheaply. (GPGems2)
- Cap degenerate-triangle accumulation by rebuilding LOD levels (multilevel skip strips) — too many degenerates still consume bus bandwidth and reject time and per-collapse cost grows, breaking the "less detail = less time" guarantee. (GPGems2)
- Prefer fully-static global index buffers with a sliding render window (sliding-window VIPM) for near-zero per-instance memory and constant per-object CPU cost — LOD change is a table lookup of first-index/tri-count/vert-count with no runtime index editing; "constant time per object regardless of LOD" is the prize. (GPGems2)
- Move unchanged triangles into a static, globally-shared, cache-optimal index buffer and copy only collapse-affected triangles per instance (mixed-mode VIPM) — slashes per-instance index memory on memory-tight platforms. (GPGems2)
- Relax strict QEM collapse order within a small error tolerance (e.g. 10% of avg collapse error) to defer creating a new LOD level — progressive meshing only needs "good enough," dramatically cutting the number of levels and their memory. (GPGems2)
- Pick indexed lists vs strips by the hardware bottleneck — strips minimize index bandwidth, lists maximize triangle throughput; degenerate-joined strips roughly double raw triangle count but most is rejected fast. (GPGems2)
- Apply level-of-detail beyond graphics — vary AI processing frequency by distance to camera/player/action, simplify algorithms for offscreen agents, and collapse many distant agents into one aggregate simulation. (GPGems2)

### Impostors & Distant Scenery
- Use impostors (cached rendered textures on simple proxy geometry) for many static distant objects — raw triangle counts overwhelm the bus, and impostoring reduces texture-change and animation cost that progressive meshing cannot; render distant scenery cheaply (skyboxes/impostors/cube env maps) to give a sense of place economically. (GPGems2)
- Render impostors on a bounding box (12 tris), not a screen-aligned quad — a quad's single depth plane causes Z-buffer clashes; a box gives camera-independent, stable Z for negligible extra cost. (GPGems2)
- Reserve impostoring for slight animations on distant objects and disable it for erratically-moving entities (players) — the eye extracts humanoid motion from a few pixels so reduced effective frame-rate is surprisingly visible, and players are unpredictable. (GPGems2)
- Decide impostor updates by summing screen-space error estimates (animation delta, lighting change, view-angle change, camera distance) against a global, possibly frame-rate-adaptive threshold — update only when error exceeds budget, and give center-of-view/under-cursor objects a lower threshold than scenery. (GPGems2)
- Precompute an animation's max-vertex-displacement-per-second offline to estimate impostor animation error without animating every frame — animating just to measure error is a large part of an object's cost. (GPGems2)
- Batch impostor texture updates to the end of the scene and pack multiple into subregions of one large render target — changing render target flushes caches/state (sometimes the whole pipeline), so minimizing target switches is the main efficiency win. (GPGems2)
- Forward-predict impostor state to its mid-lifetime when updating — onscreen impostors are always stale, so predicting halfway (e.g. 3 frames ahead for a 6-frame update) keeps them closer to correct. (GPGems2)
- Use premultiplied-alpha (ONE:INVSRCALPHA) blending when rendering into and out of an impostor texture — normal SRCALPHA blending squares the alpha and gives wrong results; control opaque alpha output so the background doesn't show through. (GPGems2)

### Lighting & Shadow Draw-Call Cost
- Limit shadow-casting lights — each shadow caster/receiver is an extra draw call and rendering pass; expose Shadow Distance, Resolution, and Cascades as user quality settings (Soft vs Hard cost the same memory/CPU, only a more complex shader). (Unity5Opt; Unity6Opt)
- Disable shadows on Additional Lights globally (URP asset) as the highest-impact single win — removes shadow casting from point/spot lights (e.g. 94→218 FPS, ~50% gain) while the directional light keeps shadows; reserve shadows for lights near the character/key spaces and disable them on decorative facade/rooftop/distant lights. (Unity6Opt)
- Lower shadow distance and use shadow cascades — Unity only renders shadows within a configurable range, so cutting it stops distant shadows wasting resources while cascades keep shadows sharp near camera and cheaper far away. (Unity6Opt)
- Tune per-light shadow Resolution, raising it only on lights near the player/important surfaces — higher resolution consumes more shadow-atlas space and cost, and overflowing the atlas triggers warnings or degraded results. (Unity6Opt)
- Add SSAO to recover depth after removing real-time shadows — darkens creases/contact areas at far lower cost than shadow maps, restoring grounding without per-frame shadow expense. (Unity6Opt)
- Choose the rendering path to fit light count and platform — Forward (few lights; free first directional light but each extra light adds a shader pass per object), Forward+ (best URP default, per-tile light culling for many lights in one pass), Deferred (very many lights, G-buffer overhead, no transparents/AA/animated shadows, only 4 culling-mask layers); cap Pixel Light Count and set minor lights to Not Important. (Unity5Opt; Unity6Opt)
- Prefer Forward/Forward+ on mobile and Deferred on PC/console — match the path's overhead to hardware strength; Deferred can perform worse than Forward+ in small scenes due to baseline G-buffer cost. (Unity6Opt)
- Use Light Culling Masks to limit which objects a light affects — but objects belong to one layer, so don't conflict with physics-layer usage (physics overhead usually trumps lighting). (Unity5Opt)
- Manage the real-time light cap deliberately — Unity culls/prioritizes visible real-time lights past a limit, causing accent/distant lights to flicker out; if a scene needs many dynamic lights, manage them or change rendering path. (Unity6Opt)

### Baked Lighting & Lightmaps
- Bake lighting for static scenes (no day-night cycle, fixed interiors/streets) over real-time lighting/shadows wherever possible — precomputes light/shadow into lightmaps so the GPU reads textures instead of recalculating every frame, often the highest-impact optimization for static environments, and adds cheap indirect bounce/color bleed; relying purely on real-time is a recipe for disaster. (Unity5Opt; Unity6Opt)
- Treat baked lighting as cost-shifting, not cost-removal — it moves cost out of frame time into bake time, disk space, and memory; budget lightmap memory and disk (e.g. 20 lightmaps at 2048² ≈ 213MB). (Unity6Opt)
- Mark only truly stationary objects Static before baking — a moving object baked as static drags its lightmap with it, producing obviously wrong results. (Unity6Opt)
- Choose light modes by need: Realtime only when light must move/change, Baked for static-only (zero runtime cost, no dynamic-object lighting), Mixed for key lights (the sun) that must light both static and dynamic objects. (Unity6Opt)
- Control lightmap storage with compression (prefer High Quality default), keep Max Lightmap Size modest (default 1024) with Fixed Lightmap Size disabled — strong quality-vs-size balance, and flexible packing limits wasted memory. (Unity6Opt)
- Pick Progressive GPU lightmapper when hardware supports it — usually faster bakes than Progressive CPU. (Unity6Opt)
- Tune bake samples per scene (Direct ~32 default, raise Indirect for smooth bounce, lower Environment when the sky contributes little) and keep Max Bounces at 2 (3 for small enclosed scenes) — higher samples/bounces improve quality but lengthen bake time. (Unity6Opt)
- Set Lightmap Resolution to scene scale and camera distance (~30 texels/unit distant outdoor, ~40 closer) — too low looks blotchy, too high inflates bake time and file size; use the Lightmap Resolution checkerboard overlay to find texel hotspots, and override per-object detail via Scale in Lightmap. (Unity6Opt)
- Set Lightmap Padding ~2 to stop light bleeding between atlas UV regions, and fix stray bright/dark artifacts by raising samples, resolution, or padding then re-baking — artifacts are usually insufficient sampling or atlas light leaking. (Unity6Opt)
- Enable Generate Lightmap UVs on imported models showing streaked/impossible-direction lighting — external models often lack UV channels matching Unity's lightmapper. (Unity6Opt)

### Mesh & Geometry Cost
- Check polygon/triangle count first when a scene runs slow — every visible triangle adds GPU work that scales with the camera view; reduce vertex counts by stripping unnecessary Normals/Tangents/UVs, letting Unity optimize mesh layout, and simplifying or culling high-poly meshes. (Unity5Opt; Unity6Opt)
- Enable GPU Skinning to move vertex skinning off the CPU when CPU-bound — but disable it if the GPU front end is the bottleneck, since it's an embarrassingly-parallel task that can crowd front-end budget. (Unity5Opt)
- Watch tessellation/Geometry Shader cost in the front end — it can dominate front-end budget; the only fix is better algorithms or freeing other front-end work. (Unity5Opt)
- Reduce polygon count (artist-led) for animated, un-batchable skinned meshes — the only good way to cut their CPU/GPU cost, since modern detail comes mostly from texturing/shading. (Unity5Opt)
- Expect rendering cost, not sim logic, to dominate once many entities are visible on-screen — at 20,000 entities spawn/movement stays cheap while on-screen rendering becomes the noticeable cost; budget GPU/draw separately from CPU sim. (ECSFundamentals)

### Asset Import & Build Optimization
- Tweak Mesh Compression (Off/Low/Medium/High) as a quick polycount cut, but prefer hand reduction in the 3D tool before import — automated compression is inferior and introduces artefacts. (Unity5Opt)
- Disable Read-Write Enabled on meshes never rescaled at runtime — lets Unity discard the original mesh data; keep it enabled only when instantiating/rescaling dynamically. (Unity5Opt)
- Import/calculate only needed mesh data — strip unused Normals/Tangents/UVs and avoid auto-generating coords you won't use (low smoothing angles multiply normals). (Unity5Opt)
- Enable Optimize Meshes in import settings (call Optimize() for procedural meshes at init) — reorganizes vertex data for cache-friendly read and faster rendering; almost always beneficial. (Unity5Opt)
- Consider baked animations for low-poly meshes — keyframing vertex positions can beat skinned/blended animations on size/memory; test sample rates. (Unity5Opt)
- Reduce texture file size to ease GPU memory bandwidth — test by halving the biggest/most-abundant textures (an FPS jump confirms bandwidth bounding); downscale resolution externally (Photoshop/Gimp) rather than importing oversized PSD/TIFF, since Unity's auto-generation introduces aliasing. (Unity5Opt)
- Watch texture Max Size — Unity automatically downscales large textures if Max Size is too small; raise it only when native resolution is actually needed, since larger textures cost more memory. (Unity5Opt; BulletHell)
- Tune Anisotropic Filtering per texture — disable for textures never viewed at oblique angles (distant sprites, particle textures) to save runtime overhead. (Unity5Opt)
- Consider Sparse Textures / Procedural Materials to cut footprint at runtime CPU cost — Sparse streams subsections from disk (huge file, careful scene design); Procedural generates textures at init (smaller download, more init/runtime cost). (Unity5Opt)
- Use the Editor Log's post-build asset size breakdown to find footprint hogs — usually texture files; spot assets larger than expected. (Unity5Opt)
- Pick a consistent, deliberate Pixels Per Unit per asset class — PPU controls world-space size, so a consistent value keeps relative scale correct and avoids per-asset rescaling work and mismatch. (BulletHell)
- Pack assets into resource files ("lumps") with per-lump compression/encryption flags — simplifies distribution; open dispatches to raw/compressed/encrypted loaders by flag. (GPGems2)
- Stream or demand-load large static data off disk when its layout is linear and collapse-ordered — contiguous VIPM/collapse data makes a streaming system with fallbacks for not-yet-available data easy; make large static read-only data a memory-mapped file where possible. (GPGems2)
- Convert reusable system setups into prefabs and replace prefab instances with LOD-enabled prefabs via Prefab > Replace — centralizes performant configuration so edits propagate from one source and the visible layout is unchanged. (BulletHell; Unity6Opt)

### Workflow & Layered Optimization
- Layer multiple techniques in the right order rather than seeking one magic setting — address the highest batch count first, then lighting, then visibility; combined layered changes (e.g. 36k batches/<1 FPS → <900 batches/~200 FPS) far exceed any single one alone. (Unity6Opt)
- Pick the optimization that fits your actual bottleneck and target hardware — the right technique depends on whether you're CPU-draw-call bound, GPU-fill/shadow bound, or memory bound; the best optimization is invisible to the player. (Unity6Opt)
- Establish a baseline (FPS, batches, triangles, memory) before any change and re-measure after — track the Memory module alongside frame time, since many rendering optimizations (static batching, baked lighting, LOD) trade memory for speed. (Unity6Opt)
- Remember pitfalls are about scale, not individual elements — a few heavy meshes or a little UI is fine; cost compounds across a whole scene and tanks frame rate. (Unity6Opt)

## Data Layout, ECS & Scheduling

### Data-Oriented Layout & Cache Coherence
- Store sequentially-processed data in contiguous, type-grouped chunks and walk it linearly — scattered per-object instances force cache-missing jumps; chunked/SoA layout lets cache lines, prefetch, and demand-loading work across thousands of entities (GPGems2; ECSFundamentals; Unity5Opt).
- Lay out hot data so the inner-iterated axis is contiguous — store the inner loop's axis back-to-back (e.g. LOS strips as horizontal start/stop runs) to minimize cache accesses (GPGems2).
- Keep large reference-type groups separate from value-type groups (SoA over AoS) — one reference field inside a struct array forces the GC to scan every element; parallel primitive arrays let it skip them (Unity5Opt).
- Keep ECS components as data-only value-type structs with no logic or methods — unmanaged structs live directly in chunks for cache-friendly access; managed/reference data or embedded behavior breaks the dense iterable layout (ECSFundamentals).
- Inspect component byte size and chunk density — ECS perf is tied to memory layout, so knowing struct size tells you chunk density and cache behavior (ECSFundamentals).
- Use SIMD-friendly Mathematics types (float3/float2/float4) over Vector3/Vector2 for entity data — they vectorize, are Burst-compatible, and pack tighter (ECSFundamentals).
- Use double only where time-accuracy demands it (ElapsedTime, scheduled timestamps); keep per-frame deltas and most fields as float — double is wider and bloats structs (ECSFundamentals).
- Minimize transform footprint via TransformUsageFlags — request None for logic-only entities (spawners, singletons, controllers) and Dynamic only for entities that actually move; over-flagging static entities bloats chunks and wastes transform-system processing (ECSFundamentals).
- Choose containers for memory/cache behavior, not just big-O — O(log n) set/map hide a large constant plus a malloc/free per node and scatter red-black nodes across memory; a contiguous vector scan is cache-friendly and often wins for game-sized n, so measure (GPGems2).
- Store pointers, not objects, in collections — avoids extra ctor calls on deletion and lets vector deletion shuffle via one fast memcpy (GPGems2).
- Remember iterator cost: ++it on a vector is one pointer increment; on a set/map it traverses a red-black node and likely misses cache (GPGems2).
- Compress tree/node data to fit cache — a compressed AABB tree at 11 bytes/triangle ran only ~10% slower than full float, the smaller set nearly compensating via cache fit (GPGems2).
- Pack per-element flags into bitfields and update with single OR/AND/XOR ops — e.g. 2-bit-per-player visibility in a DWORD makes a query one masked op (GPGems2).
- Make large static read-only tables memory-mapped files when possible — extremely efficient for global never-modified data (GPGems2).
- Suspect cache misses and branch mispredicts when tight, fat-free code still profiles hot — pointer-chasing nonadjacent nodes and unpredictable branches stall modern CPUs far more than the instruction count suggests (GPGems2).
- Eliminate pointer-chasing traversal with direct array indexing where structure is regular — direct-access quadtree lookup via integer XOR + bit-scan avoids node traversal, its cache misses, and its mispredicted branches (GPGems2).
- Iterate contiguous arrays sequentially — data layout governs both iteration speed and GC sweep time (Unity5Opt).
- Enable Optimize Meshes / call Optimize() on procedural meshes — reorganizes vertex data for cache-friendly reads and faster rendering; let Unity optimize mesh layout to minimize cache misses (Unity5Opt).

### Jobs, Burst & Multithreading
- Move per-entity work off the main thread into jobs — a single-threaded Update over thousands of objects is the bottleneck; jobs split work across CPU cores (ECSFundamentals).
- Use ScheduleParallel() to slice matching entities across worker threads — this is where the scaling comes from; each thread gets a slice instead of one core doing all entities (ECSFundamentals).
- Declare job data access as tightly as possible (`in` read-only, `ref` read+write, no modifier read-by-value) — looser access creates scheduler conflicts that block parallel execution (ECSFundamentals).
- Capture frame-global values (DeltaTime, ElapsedTime) once in the system and pass them into the job as fields — jobs can't touch Time.deltaTime, and reading shared state per-entity would serialize (ECSFundamentals).
- Prefer unmanaged systems (ISystem partial struct) over managed (SystemBase) — ISystem lives off the managed heap and Burst-compiles at the system level; drop to SystemBase only when managed references are unavoidable (ECSFundamentals).
- Keep the Burst-compilable subset intact: no managed types, GC allocations, or reflection in jobs — Burst targets numeric, branch-light work and silently can't optimize code outside that subset (ECSFundamentals).
- Use Unity.Mathematics (math.sin, math.length, float3) not UnityEngine.Mathf inside jobs — Mathematics is Burst-compatible and vectorizes to SIMD; Mathf blocks optimization (ECSFundamentals).
- Use Unity.Mathematics.Random, not UnityEngine.Random, inside jobs — only the Mathematics RNG is DOTS/Burst-compatible; the engine RNG breaks Burst compilation (ECSFundamentals).
- Enable Burst globally AND mark each system OnUpdate and each job struct with [BurstCompile] — global enable alone does nothing, and leaving either un-attributed leaves that path running unoptimized managed (ECSFundamentals).
- Expect a one-time JIT pause the first time a Bursted job runs in the Editor — native code generates on first execution; standalone builds compile ahead of time so the hitch disappears in shipping (ECSFundamentals).
- Don't hand-tune assembly for Burst — [BurstCompile] + allocation-free + Mathematics types is enough to unlock the win at scale (ECSFundamentals).
- Use micro-threads (cooperative, ~12 x86 instructions to swap stack+registers), not OS threads or fibers, for many independent AI entities — context switches cost thousands of cycles and each thread/fiber needs >=4-8KB, prohibitive for hundreds/thousands of entities; micro-threads let you write linear per-entity code with state held in PC/stack (GPGems2).
- Prefer stack-copying micro-threads (shared large stack, copied to a resizable backup on sleep) over fixed tiny per-thread stacks — fixed stacks force shallow call depth; copying is near-free (primes the cache) and allows temporarily-deep utility calls between yield points (GPGems2).
- If using fixed per-thread stacks, place guard markers at the far end and check them after each switch — overflow silently corrupts the preceding block and crashes (GPGems2).
- Know micro-thread limits — save/load is hard (stacks hold self-pointers and return addresses) and SEH needs the temp stack inside the real stack's address range; plan around these (GPGems2).
- Move the OS message pump to its own thread and run the game linearly in another — escapes the message-pump's forced FSM structure that turns dozens of subroutines into an unmaintainable state-machine monster (GPGems2).
- Know whether rendering is multithreaded before optimizing the main thread — with multithreaded rendering, graphics-API calls run on a worker thread so cutting main-thread work won't speed rendering; only when single-threaded (CPU-bound, >=50% frame time on API calls) does freeing main-thread cycles help (Unity5Opt).
- Coroutines run on the main thread — they wait/resume without true-threading synchronization headaches but do not offload CPU work off the main thread (BulletHell).

### Update Scheduling, Staggering & Frame Budget
- Set a per-frame budget and measure everything against it — 30 FPS = ~33ms, 60 FPS = ~16ms to compute everything; compare all spikes against these benchmark bars and ignore spikes under them (Unity5Opt).
- Run AI/expensive logic less often than every frame — agents have plausible reaction times, so run decision code every few frames or seconds via timers/coroutines/InvokeRepeating rather than an empty body + bool check almost every frame (GPGems2; Unity5Opt).
- Stagger and randomize each actor's re-run interval within a window — randomize wait times, spread coroutine/burst starts across frames, or cap invocations per frame via a master class so thousands of objects don't all fire (ProcessAI, spawns) on the same frame and peak (GPGems2; Unity5Opt; BulletHell).
- Use two-layer / nested timing (cooldown between bursts, short cadence within a burst) to shape load over time — spreads work instead of dumping all spawns at once (BulletHell).
- Distribute long algorithms (A* pathfinding) across several frames — save state and resume; situations rarely change much over 2-4 frames, lowering per-frame load (GPGems2).
- Replace N per-object Update callbacks with one god-class Update iterating an interface list — every Unity callback crosses the costly native-managed bridge, so keep update logic in managed code; also delete empty Update/Start/callback stubs (including in shared base classes) since Unity invokes them every frame (Unity5Opt; BulletHell; ECSFundamentals).
- Process many entities with one system instead of per-object scripts — duplicating an entity needs no extra script or update loop; the same system scales far better than per-object MonoBehaviours (ECSFundamentals).
- Let IJobEntity generate the query from Execute parameters — Execute(ref BallData, ref LocalTransform) auto-targets entities with both components; a hand-written EntityQuery is unnecessary overhead and error surface (ECSFundamentals).
- Combine multiple per-entity behaviors into a single job/system pass — running movement, direction change, and scale pulse in one Execute avoids re-iterating the same entities and multiple scheduling overheads (ECSFundamentals).
- Guard systems with RequireForUpdate<T>() so OnUpdate is skipped until relevant entities exist — avoids running empty updates and wasting frames where component types appear late (ECSFundamentals).
- Disable one-shot systems after their work, at the TOP of OnUpdate before the work runs — a spawner left enabled instantiates every frame, and disabling at the bottom lets it run one extra frame and double its output; disable-first guarantees exactly-once (ECSFundamentals).
- Use GetSingleton/SetSingleton (guarded by TryGetSingleton before CreateEntity) for one-of-a-kind resources — gives query-free, allocation-free access without an EntityQuery and prevents duplicate singletons under disabled domain reload; reserve full job+query patterns for many-entity collections (ECSFundamentals).
- Prefer event-driven notification over per-frame polling — polling promotes enormous redundant computation; have the ball/arrow notify fielders/targets and use Input-System action callbacks instead of every actor scanning every frame (GPGems2; BulletHell).
- Throttle decoupled messaging with a per-frame time cap (e.g. ~0.167s), deferring the remainder to next frame — prevents one frame choking on too many queued messages (Unity5Opt).
- Sample dependent transforms in Late Update — run camera follow in LateUpdate so it reads target positions after gameplay/physics finish the frame, removing tracking jitter (BulletHell).
- Spread big load operations across frames — prefer LoadSceneAsync over synchronous LoadScene, and disable one-shot systems, to avoid the freeze of doing it all in one frame (BulletHell).

### Simulation Level-of-Detail & Aggregation
- Apply level-of-detail to simulation, not just graphics — vary AI processing frequency by distance to camera/player/action, simplify algorithms for offscreen agents (drop precise pathfinding), and collapse many distant agents into one aggregate simulation (GPGems2).
- Match per-entity logic complexity to entity count — simple movement scales to tens of thousands cheaply, but expensive AI/physics per entity raises cost sharply, so the same count is not equally affordable for all logic (ECSFundamentals).
- Disable non-visible or far-away component logic — skip AI/scripts via OnBecameVisible/OnBecameInvisible (renderer on the same GameObject) or a periodic distance-checking coroutine; not viable for full-simulation games (Unity5Opt).
- Scale back any LOD/approximation the moment the player notices it pop — LOD is about getting away with less work invisibly; visible artifacts mean it's too aggressive (GPGems2).
- Despawn/lock resting objects out of the simulation — remove dynamic objects the player has positioned (e.g. lock penned sheep) and let physics bodies sleep to ease engine load (Unity5Opt).

### Do-Less: Cull, Defer & Eliminate Redundant Work at Scale
- The fastest work is work that never runs — delay construction until proven needed and take an early-out the moment a cheap test proves the work unnecessary (e.g. skip the whole lens-flare computation if an occluder fully covers the sun) (GPGems2).
- Solve only the part of a problem you need now and defer the rest (lazy evaluation) — hierarchical pathfinding computes the room-to-room path, then the micro-path room-by-room, so a redirect throws away uncomputed work (GPGems2).
- Do hard work offline and bake it into data — precomputed BSPs, preanalyzed terrain, lookup tables, and baked lighting cram thousands of hours of analysis into trivial runtime cost; baked lighting/occlusion shift cost out of frame time into bake/memory/disk (GPGems2; Unity6Opt).
- Amortize expensive queries with continuous incremental bookkeeping — keep a structure (influence map, LOS lists) updated as data changes so the query is cheap, spreading cost over many frames instead of one spike; combine paired add/remove updates into one function that only touches the changed region (GPGems2).
- Eliminate redundant calculation by computing once and sharing — pairwise collision is O(n²/2); let one unit pathfind and others roughly follow instead of N identical path requests, and centralize multi-agent coordination in a manager rather than every agent negotiating (GPGems2).
- Maintain a small running list of relevant candidates instead of scanning a large area — a per-player in-LOS list (one DWORD check/unit) beats scanning ~350 tiles by an order of magnitude (GPGems2).
- Cache results of repeatedly-called expensive functions — trade memory for time (e.g. a Bloom filter answers "definitely not computed" cheaply); add these during the optimization stage, not while building features (GPGems2).
- Rethink the problem with an alternate algorithm for order-of-magnitude wins — optimizing specific code yields marginal gains; the real leaps come from a different approach; prefer stateless algorithms (e.g. flocking) where possible to cut memory and react in real time (GPGems2).
- Use frustum culling everywhere but know its limit — it skips objects outside the view cone yet still renders fully-blocked objects inside the frustum, including their lighting and shadows (Unity5Opt; Unity6Opt).
- Bake occlusion culling for view-blocked layouts (dense cities, indoor, corridor, room-based) — precomputes per-cell visibility so the runtime looks up the camera's cell instead of testing per-frame, skipping geometry hidden behind other geometry (e.g. 70→180 FPS, 8M→1.2M triangles). **When it flips:** wide-open scenes where the problem is distant *visible* geometry rather than hidden geometry → prefer mesh LOD over occlusion culling (Unity5Opt; Unity6Opt).
- Tune occlusion bake parameters — set Smallest Occluder sensibly (too large and small props won't occlude, too small and the bake balloons), set Smallest Hole for culling tightness, and reduce pop-in by lowering both then re-baking (Unity6Opt).
- Mark Occluder Static (can block) and Occludee Static (can be hidden) — in dense scenes most buildings need both so they hide others and are hidden in turn (Unity5Opt; Unity6Opt).
- Use a sphere tree for fast frustum, range, and ray queries — no leaf is in more than one node (unlike quad/octrees that double-list boundary-straddlers), so culling a super-sphere culls all children with one test; update a mover with one squared-distance check against its parent and only reinsert on pierce-through, adding a slop margin so it doesn't detach on jitter (GPGems2).
- Prefer bounding-volume (AABB) trees over space-partitioning trees (octree/k-d/BSP) when you want bounded node count — partition planes force triangle splits or multi-node inclusion; BV trees just stop at one triangle per leaf (GPGems2).
- Fire culling callbacks only on in/out-of-frustum state change and cache last-frame state per node — lets the sim cheaply maintain the exact visible-object list; cull shadows, animations, and special effects alongside geometry by marking the whole subtree active/inactive (GPGems2).
- Implement mesh LOD (LODGroup) for scenes with large views and camera movement — swap distant meshes for cheaper variants (verify each level is measurably cheaper) and enable the Culled state so far objects render nothing (e.g. 28M→1.1M triangles); account for all levels staying resident in memory and the global LOD Bias multiplier, and hide pops with Cross Fade. **When it flips:** indoor/top-down/RTS/MOBA where vertex processing isn't the bottleneck → skip LOD, since it costs artist time, extra mesh memory, and per-frame distance checks (Unity5Opt; Unity6Opt).
- Use View-Independent Progressive Meshing (VIPM) for discrete-object LOD on older hardware — it beats static LOD and VDPM for visual quality per CPU cost; keep used vertices in one contiguous block, order triangles for vertex-cache coherency, and prefer sliding-window VIPM (LOD change is a table lookup) for near-zero per-instance memory and constant per-object CPU cost regardless of detail (GPGems2).
- Use impostors (cached rendered textures on simple proxy geometry) for many static distant objects — raw triangle counts overwhelm the bus; render on a 12-tri bounding box for stable Z, decide updates by summing screen-space error against a (frame-rate-adaptive) threshold, give center-of-view objects a lower threshold and scenery a higher one, and forward-predict to mid-lifetime since onscreen impostors are always stale. **When it flips:** erratically-moving entities like players → disable impostoring, since the eye extracts humanoid motion from a few pixels and players are unpredictable (GPGems2).
- Reduce overdraw and draw-call/batch count as primary CPU costs at scale — too many CPU→GPU render commands make the CPU the bottleneck before the GPU is stressed; pitfalls are about scale, not individual elements, so a few heavy meshes or a little UI is fine while cost compounds across a whole scene (Unity5Opt; Unity6Opt; ECSFundamentals).
- Layer optimizations in bottleneck order rather than seeking one magic setting — address the highest batch count first, then lighting/shadows, then visibility; combined targeted fixes (e.g. 36k batches/<1 FPS → <900 batches/~200 FPS) far exceed any single one, and the right technique depends on whether you're CPU-draw-call, GPU-fill/shadow, or memory bound (Unity6Opt).

### Pooling & Allocation at Scale
- Pool any object spawned/destroyed many times per second (projectiles, particles, enemies, weapons) — Instantiate/Destroy churn produces allocations, GC spikes, and frame-time stutters that scale with spawn rate; pay the allocation cost once at startup, then toggle active state (SetActive / cache request) at runtime (GPGems2; Unity5Opt; BulletHell).
- Spawn entities at scale via runtime instantiation in a loop (EntityManager.Instantiate / pool Get), not hand-authored thousands of objects — manual duplication clutters the scene and doesn't scale; runtime instantiation keeps the editor and bake light (ECSFundamentals; BulletHell).
- Size pools per source, not globally — give heavier sources larger pools (e.g. enemy default 20/max 40 vs player 10/max 20) and tune defaultCapacity to steady-state, maxCapacity to the realistic ceiling, so the common case never allocates while memory stays capped (BulletHell; Unity5Opt; GPGems2).
- Re-initialize and fully reset pooled objects on every Get, not in Start — reused instances skip Start and carry stale state (velocity, hit flags, lifetime timers, Rigidbody2D velocity that Unity zeroed on disable), so set per-launch state explicitly on activation (BulletHell; Unity5Opt).
- Bound the lifetime of every free-traveling spawned object — give projectiles a release timer (reset on both spawn and collision) so shots that never hit are returned instead of accumulating off-screen and wasting memory (BulletHell).
- Initialize pools before any consumer needs them and cache the unwrapped pool reference once — build the pool in Awake so other scripts' Start can request from it, and cache `_pool` once so each spawn doesn't traverse the wrapper (BulletHell).
- Maintain stack discipline on a cache so the pool stays one contiguous block — free X only after everything allocated after X, improving locality and simplifying frees (GPGems2).
- Project frame cost forward by worst-case scenario, not current state — reason about "hundreds of projectiles per second" or "more enemies" and size pools/systems for the worst expected load; verify wins at scale, since Burst/jobs/pooling show little difference at a few entities and only pay off at thousands (BulletHell; ECSFundamentals).

### Branchless & Computation-Over-Comparison in Hot Loops
- Prefer computation and bit tricks over comparison-heavy branchy code in hot loops — comparison code compiles to many data-unpredictable branch/jump instructions that stall the pipeline (GPGems2).
- Use branchless/conditional-load idioms in clamps and sign tests — an integer-unit float clamp ran <5 cycles vs ~18 for compare-and-branch; use integer-unit ops on float bit patterns for sign, comparison, clamp, and abs (float abs is just masking the sign bit) (GPGems2).
- Compare squared magnitudes instead of magnitudes/distances — CPUs multiply fast but compute square roots slowly, so use sqrMagnitude vs distance² for any sqrt comparison (Unity5Opt).
- Prefer a single fast memory-clear over searching open/closed lists — with far fewer nodes than tiles, one array lookup replaces list searches and removes the closed list entirely (GPGems2).
