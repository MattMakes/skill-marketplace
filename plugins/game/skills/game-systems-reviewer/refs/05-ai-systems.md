# AI & Behavior System Architecture

## AI & Behavior System Architecture

### Architecture: Layering & Decoupling Decision / Animation / Driver
- Separate high-level decision logic ("skills"/what) from low-level capabilities ("behaviors"/how) so different characters reuse the same behaviors — make skills tailored and behaviors widely shared (The Last of Us Hunters/Infected shared most behaviors, only two were Infected-specific). (GameAIPro2)
- Apply Separation of Concerns: each system has one purpose and no overlapping responsibility — overlapping gameplay vs. animation vs. driver state machines silently fuse into unmaintainable monoliths. (GameAIPro2; GDWorkshop)
- Insert an actuation layer (animation controller + animation behaviors) between decision-making and animation — sense/think/act layering lets you swap actuators without touching deciders. (GameAIPro2)
- Never let gameplay code reference animation control parameters or animgraph topology directly — that data dependency means every animgraph tweak breaks gameplay; push the coupling as far from gameplay as possible. (GameAIPro2)
- Treat each AI pattern (FSM, sensors, pathfinding, flocking, BT, fuzzy) as a composable layer, not a silo — real agents combine them (sensor feeds an FSM transition; fuzzy feeds a BT node). (UnityAI)
- Keep the data-feeding/sensing script ignorant of decision logic — the AI script writes `distanceFromPlayer`/`isPlayerVisible`; the state machine decides; this decouples sensing from deciding. (UnityAI)
- Pull varying behavior into its own family of interchangeable classes behind an interface (fly/quack, damage types, AI steering) — the host delegates to whichever implementation it holds. (HeadFirstPatterns)
- Quality of an agent is bounded by the quality of information it gets from the world — starve a sensor and the agent idles, loops, or picks bad cover; feed the decision system enough data first. (UnityAI)

### Decision & Utility Systems
- Compute each option's utility in-game at decision time, not as fixed a-priori weights — only situational scoring yields responsive, dynamic behavior. (GameAIPro2)
- Offer two utility modes — absolute (always pick max; optimal but predictable) and relative/weight-based-random (pick proportional to weight; adds variation but risks dumb low-weight picks) — then combine into dual-utility: a rank coarsely categorizes options (only the top category is eligible) and weight-based-random picks within it, killing both predictability and occasional stupidity. (GameAIPro2)
- Let weight ≤ 0 mark an option invalid — a clean designer kill-switch independent of rank. (GameAIPro2)
- Screen out options far below the best weight before the random draw — prevents the RNG from selecting plausible-but-stupid choices. (GameAIPro2)
- Reserve enormous ranks for must-never-be-overridden actions (dying = rank 1,000,000) — guarantees critical behaviors trump everything. (GameAIPro2)
- Prefer hand-authored heuristic functions over opaque cognitive models — designers need simple controls with predictable effects, not academic falsifiability. (GameAIPro2)
- Decide deliberately where you sit on the authorial-control vs. autonomy axis per game — they are fundamentally at odds; emergence is a tunable, not a universal good. (GameAIPro2)
- Don't equate smarter AI with better AI — predictable, rule-based automata let players plan and strategize; complex minds make outcomes incomprehensible. Use simple AI unless fiction-driven interaction dominates. **When it flips:** when the fiction demands a believable mind, route around the no-real-mind problem with insane/inhuman/recorded characters, dialogue trees, or real players instead of faking cognition. (DesigningGames)
- Use 1-ply search (simulate one action, evaluate the result) before authoring rules — a simulate-and-evaluate engine often needs less hand-authoring and auto-adapts when designers retune damage/buffs; shift static evaluation from "suggest actions" to "evaluate states after an action" once search is added, and find each game's search sweet spot against CPU/memory. (GameAIPro2)

### Finite State Machines
- Implement attributes/behaviors as explicit finite state machines with defined transitions and triggers — it forces complete thinking, auto-forbids illegal transitions, and cuts debugging. (AoGD3; AoGD2; UnityAI; GameAIPro2)
- Model behavior as a fixed set of states with exactly one active at a time, connected by transitions — mirrors real-world state (water: solid/liquid/gas) and is easy to visualize and reason about. (UnityAI)
- Decompose an FSM into States, Transitions, Rules (trigger conditions), and Events (what checks rules) — separating these keeps the machine extensible as states grow. (UnityAI)
- Drive transitions from data parameters (float/bool/int/trigger), not hard-coded branches — callers only set values; the FSM/controller owns the transition logic and decides when conditions hold. (UnityAI; Build3DUnity; Platformer2D)
- Nest sub-states/substate machines to break a complex state into sub-behaviors — Pac-Man "Chasing"→"Scanning/On Tail/Through Tunnel", or Patrol→MovingToTarget/FindingNewTarget — without bloating the top-level graph. (AoGD3; UnityAI)
- Use multiple parallel transitions between the same two states for OR conditions — one transition ANDs all its conditions, so add a second for "out of range OR out of sight". (UnityAI)
- Use an "Any State" transition for a shared exit condition instead of wiring it from every node — add it once rather than N duplicates. (UnityAI)
- Run per-state logic via lifecycle hooks (enter/update/exit; or onStart/onEnd/onDraw/onUpdate) — setup, per-frame work, and cleanup live with the state, keeping its code self-contained; a ~70-line FSM lasts a whole project. (UnityAI; PolishedGameDev; RPGDirectX)
- Encapsulate each state as its own class implementing a common State interface and let the Context delegate to the current state — far better than giant conditional/switch blocks tied to a state variable; explicit state objects make states and transitions readable. (HeadFirstPatterns; GPGems2; Unity2DCookbook)
- Decide deliberately where transitions live: fixed transitions in the Context, dynamic/runtime-dependent transitions in the state classes — and route transition decisions through Context getters so states don't tightly reference each other. (HeadFirstPatterns)
- Clients should never change a Context's state directly — the Context owns its transitions; outside callers requesting raw state changes break invariants. (HeadFirstPatterns)
- Share stateless state objects as static singletons across many Contexts — works only if states keep no per-context data; otherwise pass the Context into each handler. (HeadFirstPatterns)
- Keep transition rules simple and logically chained (a clean Patrol→Chase→Shoot loop with distance/visibility gates) — complexity hides bugs; keep the FSM only as complex as gameplay requires (a slime needs one looping state, no params). (UnityAI; Platformer2D)
- Expose a small stable "exported class" the entity advertises (dead/scared/active) separate from internal FSM state — script/interaction code keys off the stable set while the internal FSM grows organically during production without breaking handlers. (GPGems2)
- Recognize FSMs scale poorly — states and transitions multiply combinatorially, and hand-rolled switch-based machines become unreadable accidental complexity; when manual wiring gets unwieldy, migrate to behavior trees. (UnityAI; GPGems2)
- Implement game-object AI as a state machine so any agent can be suspended mid-update — essential once you have more than one AI entity. (GPGems2)

### Behavior Trees
- Use behavior trees when FSMs get unwieldy — flow is defined by node hierarchy/order rather than a web of manual transitions, so BTs scale to complex/compound behavior. (UnityAI)
- Standardize every node to return exactly one of Success / Failure / Running — a uniform contract lets any node compose under any parent; build them from a single abstract Node base with one `Evaluate()` method. (UnityAI)
- Make evaluation asynchronous via the Running state — a "please wait" return lets a tree span multiple frames and never block the main loop, which is essential when many agents think simultaneously. (UnityAI)
- Use Sequence nodes as AND (all children must succeed, fail-fast on first failure, propagate Running) and Selector nodes as OR (succeed on first child success, fail only if all fail, short-circuit the rest). (UnityAI)
- Use Decorator nodes (exactly one child) to transform a child's result — Inverter (NOT), Repeater (loop until condition), Limiter (cap attempts to avoid infinite loops) — wrapping behavior without subclassing; don't overload one decorator with too much logic, prefer a sequence when it grows. (UnityAI)
- Keep leaf/action nodes the only place real game logic lives — pass logic in via a delegate so one generic ActionNode reuses across behaviors. (UnityAI)
- Treat unevaluated nodes as holding their default state — short-circuiting selectors/sequences leave later nodes unevaluated, so never read an unevaluated node's state as a real result; choose enum ordering and defaults so untouched nodes don't report false success. (UnityAI)
- Add a plug-and-play hint layer (Hinted-execution BTs) that dynamically reorders a base tree's selector priorities via positive/negative/neutral hints instead of editing the proven tree — revertible, low-risk late-production prototyping; expose hints by naming selector branches (harmless and inert unless a high-level tree is present). (GameAIPro2)
- Stack behavior controllers as layers running top-down, each hinting the layer below before it executes — a tree receives all its hints before it runs, so its branches are pre-sorted. (GameAIPro2)
- Evaluate buy-vs-build for BT frameworks — off-the-shelf plugins add visual editing, runtime debugging, serialization, and data-oriented trees; roll your own only when time/budget/control justify it. (UnityAI)

### Production Rules & Planning
- Use a production system only when decisions hinge on many non-quantifiable factors, must react fast to state changes, encode expert knowledge that resists a clean algorithm, and have independent actions — otherwise it's overkill. (GameAIPro2)
- Before coding a production system decide all of: scope, rule representation, authoring method, LHS matching, no-rule fallback, multi-rule selection, RHS design, and tuning method — skipping any one causes documented postmortem problems. (GameAIPro2)
- Always handle the "no rule matched" case explicitly (default rule, fill-in rules, or constrained backward chaining) — otherwise the AI stalls, factories stop, characters freeze. (GameAIPro2)
- Keep RHS actions cheap, conflict-free, re-entrant, and minimally interdependent — minimizes conflict resolution and avoids restarting running actions every call; add escape-hatch custom conditions/actions from day one. (GameAIPro2)
- Prefer contextual deictic variables ("unit", "map", "player") bound at query time over free predicate-logic variables — eliminates search/unification cost and keeps condition checks near-constant-time. (GameAIPro2)
- Track per-rule execution counts, RHS success rate, LHS-variable match counts, and lists of never-fired and over-fired rules — the universal indicators for tuning any rule system. (GameAIPro2)
- Use weighted/dynamic scripting that raises the selection probability of rules that succeed and lowers failed ones via partially-supervised training, then lock the database — a self-tuning competitiveness loop; manually weed out over/under-fired rules afterward. (GameAIPro2)
- Use forward breadth-first GOAP-style planning with actions as editable text files — nonprogrammers iterate offline without recompiling, and complete search returns the shortest plan so NPCs get no redundant actions. (GameAIPro2)
- Abstract away sub-problems in planning (one action that "magically" reaches a location or solves a puzzle, delegating execution to a routine) — keeps the planning state space tractable. (GameAIPro2)
- Encode action predicates so preconditions and effects overlap only once in a shared-position array and record where parameters occur — enables fast unification by checking equal values at recorded positions. (GameAIPro2)
- Use a finite-domain constraint solver for configuration/PCG tasks (room contents, character builds) with forward checking, backtracking, and undo — declarative constraints are faster to author/re-author than ad-hoc algorithms and are already correct; visit most-constrained variables first, shuffle value order for variety. (GameAIPro2)

### Fuzzy Logic
- Replace binary yes/no decisions with degree-of-truth floats (0..1) only when nuance matters — fuzzy values model "warm/hurt/critical" ambiguity binary thresholds can't capture; weigh the cost, since fuzzy is more expensive than binary and predictable binary may fit cheaper. (UnityAI; GPGems2)
- Define membership functions/sets and compute degree of membership for each — overlapping sets capture gray areas (at 65% health Bob is simultaneously 0.375 "hurt" and 0.125 "healthy"); remember fuzzy values are degrees of set membership, not probabilities, so they need not sum to 1.0 and may overlap. (UnityAI; GPGems2)
- Run the full pipeline: crisp input → fuzzify → infer (apply human-like rules) → defuzzify → crisp output — the inference step is where the agent decides what vague data means, and defuzzifying keeps downstream systems simple by replacing nests of if/else with a few readable rules. (UnityAI)
- Author membership curves as editable assets (animation curves) for designer tuning — triangle/linear sets by default but allow bell curves and trapezoids; evaluate the curve at the input value to get truth. (UnityAI)
- Feed any number of inputs into a fuzzy controller (health + mana + enemy strength + ally proximity) — fuzzy systems are generic, so add as many factors as the decision warrants. (UnityAI)
- Give each agent its own set definitions for free personality variation — "critical" below 40 for cautious Bob, below 20 for reckless Jim; same system, unique behavior, optionally randomized. (UnityAI)
- Pipe fuzzy output into FSMs, behavior trees, or chained controllers (nested fuzzy controllers form a tree), and use it beyond decisions to scale how much/how fast/how long an action runs (nitro duration, fuel use), plus dynamic difficulty/matchmaking. (UnityAI)
- Adapt a finite-state-machine class to fuzzy by supporting multiple simultaneous current states each with a degree-of-membership — drop the transition arrays since you can be in several states at once; use it when a decision has more than two discrete outcomes (health, throttle/brake, NPC anger). (GPGems2)
- Use the Combs Method to turn fuzzy rule combinatorial explosion (sets^variables) into linear growth (sets×variables) — build rules per-variable-to-output from the start; it ORs (max) where traditional rules AND (min). (GPGems2)

### Perception & Sensing
- Model perception as an Aspect/Sense pair — senses scan for specific aspects (a perception sense looks for an "Enemy" aspect, a smell sense for "brain") behind a base Sense interface with `Initialize`/`UpdateSense` hooks, so new sensor types plug in without touching existing code. (UnityAI)
- Run sensing periodically on a detection-rate/interval timer, not every frame — accumulate elapsed time and only detect past the interval; throttling is the primary lever for keeping many agents affordable. (UnityAI; GameAIPro2)
- Prefer cheap tests before expensive ones in sensing — angle/distance/overlap check before the raycast, so the costly operation runs only when it matters. (UnityAI)
- Model vision as a cone (field-of-view angle test first, then raycast for line-of-sight occlusion), not a single line — a cone reads more naturally; combine/improvise sensor shapes (boxes for smell, cylinders for vision) freely. (UnityAI)
- Make perception fidelity fall off with distance and periphery, and shape the vision sweet spot to widen-then-narrow with distance (coffin/cone hybrid) — a plain cone wrongly makes distant lateral objects detectable, so make angle of view inversely proportional to distance and clamp peripheral detection. (UnityAI; GameAIPro2)
- Abandon Boolean sees/doesn't vision for graded identification certainty over zones, interpreted as certainty not probability — a hard 10.000 m vs 9.999 m threshold is exploitable and inexplicable, and a probabilistic model has the "eventually sees everything" pathology. (GameAIPro2)
- Require the target to be seen for 1–2 s in the sweet spot before detection, or show an explicit stealth meter — use a detection timer that increments when seen and decrements when unseen, with thresholds varying by combat/stealth state, for a forgiving readable window. (GameAIPro2)
- Apply identification bonuses/penalties for movement and camouflage — moving objects are easier to spot; camouflaged ones can fall below the certainty floor. (GameAIPro2)
- Raycast to multiple body bones with weighted thresholds, or a single context-dependent point (chest in stealth to favor the player, head in combat) — single-point is more predictable for players reading cover safety. (GameAIPro2)
- Drive reaction time by context (~0.2 s simple, ~0.4 s go/no-go, longer for weak stimuli/aiming/attention lapses) — picking a single number ignores cognitive reality. (GameAIPro2)
- Generate logical events (logical sounds, contextual events) decoupled from real audio/physics — designers control what's sensed at what range per character type without touching the underlying media; occlude logical sounds with walls and scale broadcast radius by source speed and listener sensitivity. (GameAIPro2)
- Compute sound distance along the area-connectivity graph (sum of choke-to-choke distances), not Euclidean — Euclidean lets agents "hear through walls"; the area path is a cheap accurate approximation. (GameAIPro2)
- Interpret the same raw event differently by context ("see dead body" in a search vs. a warzone; "see player" on a reachable vs. unreachable rooftop) — map raw events to context-qualified events before the behavior system picks a response. (GameAIPro2)
- Favor player perception over simulation accuracy but bound it by plausibility — halve hearing for offscreen distant NPCs to feel fair, yet keep around-the-corner NPCs responsive enough to stay believable. (GameAIPro2)
- Maintain a model of what the player knows and only call out enemies the player can actually see — calling out an unseen/ducked enemy makes the buddy look stupid; AI callout requirements are stricter than human intelligence. (GameAIPro2)
- Prefer event-driven behavior over polling — agents that react to events instead of re-checking every frame cut AI processing dramatically. (GPGems2)
- Drive AI behavior off proximity-graded sensory cues — the Wumpus gave odor strength relative to distance; distance-graded perception is a lightweight, legible AI/feedback system. (GDEssentials)
- Give critters cheap perception (let them read other critters' positions/velocities to seek the player or evade bullets) — modest information-gathering, not deep AI, makes enemies feel alive. (SWEngGames; GDWorkshop)
- Use omniscience deliberately as a controlled cheat — let agents read hidden state (player health, item locations) when the simplest solution beats simulating real perception. (UnityAI)
- Require rigidbodies for collision/trigger events on otherwise-static sensors and filter by aspect on trigger — Unity won't dispatch trigger events without one, and missing it silently breaks perception. (UnityAI)
- Provide debug gizmos (OnDrawGizmos) to visualize sensor ranges/cones/rays in-editor — seeing the cone and hit lines during play is essential for tuning and catching glitchy behavior. (UnityAI)

### Knowledge Representation & Deferred Decisions
- Maintain probability/possibility distributions over unobserved game state instead of simulating it — lets the AI defer decisions (where an NPC is, whether it grabbed the health pack) and create opportunistic, seemingly-planned behavior cheaply. (GameAIPro2)
- Update possibility maps consistently with the player's observations and instantiate only when the player would observe a possible state — a skillful player can still foil the AI by careful observation, keeping it fair. (GameAIPro2)
- Fork a possibility map to defer a binary decision (pick up key / unlock door / collect health) — but cap forking to avoid combinatorial explosion; even brief deferral gives the AI more information later. (GameAIPro2)
- Factor game state into independent elements with one map each; use joint maps only when factorization fails — joint maps grow exponentially, so some factorization is mandatory. (GameAIPro2)
- Use forward and backward inference over a dependency/tech graph (seeing a Pikeman implies a Barracks; a Barracks raises Pikeman likelihood) — a Bayes-network-like way to estimate hidden enemy assets without cheating. (GPGems2)

### Influence Maps & Spatial Reasoning
- Build influence maps from each unit propagating influence that decays with distance, summed per cell — combined overlap reveals concentration, contested zones, frontiers, choke points, weak spots, and control, answering group questions cheaply. (GameAIPro2; GPGems2)
- Keep enemy and ally influence separate rather than subtracting — a hotly-contested tile and a quiet tile both net to zero under subtraction, losing critical information. (GameAIPro2)
- Propagate combat influence by travel time, not raw distance — influence represents the ability to reach a fight in time to matter; use discontinuous formulas for ranged/artillery units. (GameAIPro2; GPGems2)
- Pick a falloff/propagation curve deliberately (exponential, or constant 0.6–0.8) with a minimum-value cutoff — with floats influence never reaches zero and would otherwise spread everywhere; use nonlinear/lookup-table curves so designers author influence shape directly. (GPGems2; GameAIPro2)
- Account for terrain in propagation (multiply falloff by per-cell passability and flood-fill, or precompute shortest paths) — stops influence leaking over impassable mountains; track unit types (flying/ground/sea) separately and spread ranged influence extra cells without diminishing. (GPGems2)
- Make influence-map cells fairly large (fit 10–20 standard units across), or partition into homogeneous regions that are not-too-big/small, roughly equilateral, and mostly convex — smaller cells waste computation/memory and rarely make the AI smarter. (GPGems2; GameAIPro2)
- Retain multiple spatial representations (tiles for low-level pathing/collision, rectangles for compact storage, regions/navmesh polys for high-level reasoning) — different jobs want different granularities. (GameAIPro2; GPGems2)
- Combine cell stats into a computed "desirability value" via a weighted sum per decision (attack, defend, explore, placement) and expose modular map operations (Add, Multiply, Normalize, Inverse, GetHighest) so behaviors compose "recipes" — `Add(enemyThreat) * Multiply(allyThreat) * Multiply(interestTemplate)` finds the battlefront near you. (GameAIPro2; GPGems2)
- Multiply by a personal-interest template to prioritize nearby results and zero out distant ones — "yes that's interesting, but too far to care." (GameAIPro2)
- Precompute normalized "templates" of propagated influence and stamp them into base maps with a strength multiplier, assembling on small working maps centered on the agent — eliminates per-agent-per-frame sqrt/distance work and iterates only locally relevant cells. (GameAIPro2)
- Add mobile units to the map by projected future position (dead reckoning) and choose a refresh strategy (periodic full recompute every 1–10 s, or demand-based lazy evaluation per queried cell) — keeps the map accurate between infrequent refreshes at strategy pacing. (GPGems2)
- One knob flips stance: weight enemy forces > own for a defensive posture, own > enemy for aggressive — define the frontier as any boundary where adjacent cells flip sign. (GPGems2)
- Let influence maps cheat plausibly: give the AI partial knowledge to mimic human intuition rather than perfect or no knowledge — undetectable cheating that prevents the "empty stronghold" anticlimax and yields emergent flanks and diversionary attacks. (GameAIPro2)
- For huge/3D/fine spaces use point-based infinite-resolution influence (sum of differentiable falloff functions, k-d tree range queries, gradient descent for optima) — memory linear in sources and unlimited resolution, but O(n) query cost and lossy updates; in 3D action games use navmesh polygons as cells and mesh links as propagation avenues. (GameAIPro2; GPGems2)
- Track spatial characteristics for tactics — scent-of-death (deaths per region), high-traffic areas, avenues of approach, chokepoints (bounded-depth BFS), cul-de-sacs (single passable neighbor) — these distinctions drive ambush, defense, and flank decisions; boost defense/counterattack priority in a region right after winning or losing a fight there. (GameAIPro2)
- Represent terrain for AI reasoning with waypoints (250–2500) denser than navigation needs, decomposing each location's tactical value into local, group-membership, directional-relation, and focus properties — far less detail than polygons, expresses inter-location relations, and supports precomputed cover/concealment reasoning. (GPGems2)
- Do heavy spatial/terrain analysis (O(n³) waypoint ratings, BSPs, trained nets) offline/between missions/on a background thread and store small per-node tables — cheap to read at runtime; correct for dynamic terrain rather than discarding precomputed results. (GPGems2)
- Improve waypoint ratings with captured gameplay data (add damage dealt, subtract damage received) — reinforcement-style correction yields adaptive AI nearly for free since the AI already thinks in waypoints; tag waypoints visible from threats with extra A* cost for cover-respecting paths. (GPGems2)
- Store extra spatial metadata in navmesh triangles (crouch-only, forested, cover) and scale pathfinding cost by effort — the navmesh is always under the agent's feet; recycle discarded voxels with alternate agent params (crouch/prone/swim) to extend its coverage. (GameAIPro2)
- Visualize intermediate reasoning output projected onto the terrain (or exported to a spreadsheet) — essential to tune and verify heuristic terrain algorithms. (GPGems2)

### Pathfinding & Navigation
- Represent the navigable world in a traversable structure (grid, waypoints, or navmesh) before pathfinding — A* needs a graph, and choosing the representation is the first and most consequential step. (UnityAI)
- Implement A* with open/closed lists as priority queues, scoring nodes F = G + H (cost-so-far + heuristic-to-goal) and storing G/H/parent — always pop the lowest-cost node; reconstruct the path by walking parent pointers from the goal and reversing. (UnityAI)
- In A*, keep only the shortest path to each intermediate point (array indexed by node, single lookup, no closed list needed) — prevents exponential search-tree growth; critical for scalability. (GPGems2)
- Prefer navmesh over waypoint graphs for environment-rich worlds — convex polygons encode walkable area (safe near cliffs/bridges), reuse across agent types, and avoid the huge waypoint counts and wall-clipping of node-to-node movement; or drive locomotion through the engine's NavMeshAgent so the system owns avoidance/repathing/surface constraints. (UnityAI; CertProgrammer)
- Use points-of-visibility (convex-corner) pathfinding built on expanded geometry (Minkowski difference) for a minimal search space and direct paths — one expanded model serves both collision and pathfinding, guaranteeing characters can't get stuck; consider only silhouette/around-corner sections. (GPGems2)
- Re-bake navigation after any static-geometry change and mark only intended geometry as Navigation Static — treat nav data as a build artifact that goes stale when obstacles move; use NavMeshObstacle Carve (off "Carve Only Stationary") so moving obstacles re-cut the mesh live. (UnityAI)
- Expose navmesh bake params as designer knobs (agent radius, height, max slope, step height; per-area cost; off-mesh links; drop/jump thresholds; voxel size) — these define what an agent fits through, climbs, and routes around, and trade bake accuracy for speed. (UnityAI)
- Use raycast-normal obstacle avoidance only for local steering, not true pathfinding — adding hit-normal × force dodges what's directly ahead but can't solve mazes; reserve it for crowd-style "just avoid neighbors", filtered by layer masks to obstacle layers only. (UnityAI)
- Augment pathfinding with a congestion map (crowd density + aggregate direction as traversal cost) so agents pick faster less-crowded routes — generate congestion-aware flow fields with Theta* to share line-of-sight checks across all agents with a shared goal. (GameAIPro2)
- Continually maintain candidate cover/post sets via round-robin pathfinds and timesliced raycasts on previous frames, scored by composable runtime-reloadable criteria — so the ideal post per selector is always ready with zero delay when an NPC switches state; reject cover whose path runs toward the player. (GameAIPro2)
- Cost flanking paths by a fixed shape rotated with the combat vector, not by an exposure map — exposure maps flicker frame-to-frame; the combat-vector shape produces stable wide-then-around routes. (GameAIPro2)
- Give the AI ~2–3 s of cheated last-known-target knowledge after losing sight — a cheap effective "intuition" that avoids the navmesh-extrapolation-into-a-prop problem. (GameAIPro2)
- Preprocess static uniform-cost grids (JPS+ jump-point/wall distances) or subgoal/n-level graphs when walls don't change — trades a static map for up to two orders of magnitude speedup over A* with full optimality. (GameAIPro2)
- Escalate pathing sophistication only as needed: impatient-seek that cruises out of wall-stalls → waypoint-following with a maze-blocks test → full A*/breadth-first — and bound "smarter" pathfinding cheaply (e.g. only 2 attempts to pick a better direction), since large challenge gains come from small AI improvements. (SWEngGames; PCGUnity)
- Keep NPC/monster AI to a small named behavior set (stand, wander, route, follow, evade) selected by one AI field, with simple distance-math steering (follow if farther than threshold, evade if closer, else stand) — "appear intelligent" with a handful of rules instead of heavy AI. (RPGDirectX)
- Always handle the no-path / goal-not-found case explicitly — A* must detect an empty open list with current ≠ goal and report failure rather than returning a bogus path. (UnityAI; GameAIPro2)

### Steering, Movement & Flocking (Emergence)
- Compute steering as desired_velocity − current_velocity (Reynolds' trick), then divide by mass for acceleration — far more responsive than steering toward the desired direction; heavier mass yields lazier turning and smooth, tunable motion. (UnityAI; SWEngGames)
- Model forces as plug-in objects summed in a virtual feelforce, prioritized/dithered rather than blindly summed — naively adding "avoid obstacle" + "flee bullet" can cancel to zero and hit both; gives gravity/drag/seek/evade as composable parts without a subclass per combo. (SWEngGames)
- Replace fragile, coupled steering with context steering when entities are closely watched and physically constrained — write *why* (interest/danger context maps) not *how* (a final vector) and let a behavior-agnostic processor merge; store context as a low-res 1D array treated like an image (blur, hysteresis, per-entity LOD by resolution). (GameAIPro2)
- Build a navigation pipeline of sequential behaviors that each correct the previous one's velocity (path-follow → wounded → collision-avoid) — modular and reusable, with the last behavior having final say. (GameAIPro2)
- Use an arrival radius around waypoints and slow velocity proportionally to remaining distance near the final waypoint — agents rarely hit a point precisely, and ramping speed down eases them to a stop rather than overshooting; or use MoveTowards for predictable constant-speed approach that lands exactly on target. (UnityAI; Build3DUnity; BulletHell)
- Interpolate rotation toward the desired heading (Slerp/RotateTowards) rather than snapping — gradual turning reads as natural motion and decouples facing from instantaneous velocity. (UnityAI)
- Get emergent group behavior from three simple per-boid rules — Separation, Alignment, Cohesion computed against neighbors within a radius and summed as weighted contributions — producing complex lifelike global motion with no central controller, scripting, or offline animation. (UnityAI; GPGems2; IntroGameDesign)
- Expose per-rule weights (center/velocity/separation/cohesion/randomize) and add a small randomize term to break mechanical lockstep — knobs let designers dial flock tightness, responsiveness, and organic noise without code changes. (UnityAI)
- Add a fifth "survival" steering rule (eat/avoid being eaten) plus per-agent randomized parameters (sight range, speed, hunger) — individual variation produces novel emergent group dynamics and more realistic crowds. (GPGems2; SWEngGames)
- Enforce min/max speed clamps on every boid and (optionally) offload translation/steering to the physics engine — caps runaway acceleration from summed forces and keeps the flock coherent and stable. (UnityAI)
- Constrain axes (freeze Y) to repurpose the same three flocking rules for fish/herds/2D/ground animals — one model drives birds, insects, and ground crowds with movement-axis tweaks. (UnityAI)
- For humanoid crowds, lean on the navmesh agent's built-in avoidance rather than rolling your own, with randomized per-agent speed — Unity does the heavy lifting and yields different runs each time; hand-rolled avoidance multiplies cost across hundreds of agents. (UnityAI)
- Pick the right group model per use case — flocks (emergent local rules, only forces needed), formations (strict top-down slots, need slot assignment), social groups (density-driven abreast/V/lane) — assign formation slots by spatial sort (ith sorted entity → ith sorted slot), not greedy nearest, to avoid crossing paths and circling. (GameAIPro2)
- Beware emergence is a double-edged sword: unpredictable and hard to test exhaustively (predators can wipe out prey and collapse an ecosystem) — reserve it for non-critical entities not pivotal to game completion. (GPGems2)
- Vary enemy competence randomly (even add "dumb" enemies that do the wrong thing) and desynchronize identical agents by randomizing shoot timing — unpredictability sustains tension and avoids a boring lockstep "firing-squad" effect. (SWEngGames)

### Coordination: Blackboards, Tokens & Group Control
- Use a blackboard as shared scratch memory for cross-behavior and cross-agent communication — define global, group, and local scopes so logic stays independent yet coordinated. (GameAIPro2)
- Use a global coordinator object to assign exclusive roles (Flanker, Approacher, OpportunisticShooter) via request/acknowledge/release — guarantees only one agent flanks, only one must be shooting, etc. (GameAIPro2)
- Use action tokens to cap how many agents perform an action simultaneously (grenades, move-and-shoot) — each action owns N tokens; designers parameterize cooldown and whether the count scales with crowd size. (GameAIPro2)
- Build a virtual non-physical "group entity" anchor rather than electing a leader for group navigation — cleanly separates group-level decisions from individual behaviors, nests recursively, and keeps behaviors simple and parallelizable with read-only previous-frame state. (GameAIPro2)
- Factorize the costly path query at the group level (one query for the whole group), tuning cost so falling back to a narrower formation is comparable to a longer path — groups reconfigure to fit corridors. (GameAIPro2)
- Let a group-behavior system handle events first and pause/resume its members — interrupted conversations branch to a group investigation and seamlessly rejoin via authored breakout/rejoin lines. (GameAIPro2)
- Prevent animation twinning with a shared blackboard storing animId, time, location, and priority, enforcing per-priority delay (~1 s normal, ~300 ms reaction) — add location so on-screen-separated agents may still share animations. (GameAIPro2)
- Decentralize ambient life into Smart Zones that own roles (main/supporting/extra), behaviors, a synchronization timeline, and triggers — moves complexity out of global control into self-contained zones that cast nearby NPCs. (GameAIPro2)
- Give NPCs collusion: dual goals that pursue their in-world objective AND serve the designer's pacing (fleeing pirate ships that lead players to islands; Façade characters tracking a tension curve). (AoGD2; GDWorkshop)

### Fire-and-Forget Orders & Realization
- Use fire-and-forget animation orders that return a handle — gameplay issues an order, queries status via the handle, and never micromanages animation lifetimes or transitions; update a behavior's order by issuing a new order that merges with the running one. (GameAIPro2; CertGameDev)
- Give behaviors shared ownership (smart pointer) so they outlive the issuing state — gameplay and animation update at different rates, and a behavior stays alive while a handle or queue references it. (GameAIPro2)
- Model command-driven units as a brain queue of task objects processed front-first and destroyed on completion, falling to a never-completing default idle task — and keep the queue blind to who enqueues (player, scripted NPC, high-level AI, network packets all push identically). (GPGems2)
- Make a cyclic task (Patrol) identical to its non-cyclic form (Move) plus a "cyclic" flag that re-queues instead of destroying — one flag covers waypoint patrol loops. (GPGems2)
- Encapsulate a request as a Command object binding a receiver to an action with one execute() — decouples the invoker (input handler, button, AI) from the doer, and lets you build queues, schedulers, undo (per-command undo() + history stack), and replay on top. (HeadFirstPatterns)
- Treat animation as the language the AI speaks — the AI is only as good as the animations it chooses and how appropriately it uses them; invest in behavior realization, not just decision logic. (GameAIPro2)
- Use canned multi-character dialogue ("barks") to broadcast mental state, intent, and coordination — dialogue conveys behavior that was never even implemented ("I need reinforcements!"); tier barks (specific → generic → minimal) and cycle down as the player learns to avoid repetition. (GameAIPro2)
- Extend animation coverage with motion correction (independently correct displacement, orientation, speed) rather than authoring every variant — 3 start animations + correction gives 360° coverage; decouple extracted motion from the pose update so you can correct each independently. (GameAIPro2)

### AI Scheduling, LOD & Frame Budgeting
- Optimize AI as a budgeted citizen sharing the frame with rendering, physics, audio, animation — cap its cost and pick AI complexity to match the game ("as simple as the game needs, but not simpler"; Pac-Man's tiny FSM fits perfectly). (UnityAI; GameAIPro2)
- Run the AI less often than every frame and randomize each agent's callback window — creatures have reaction times anyway, and randomizing prevents synchronized processing peaks. (GPGems2; GameAIPro2)
- Schedule rules/conditions by a frequency timer (per-rule overridable, default once per game-day) rather than every frame — only run rules when they're due, and keep condition checks constant/near-constant time so the AI engine is invisible in the profiler even on weak hardware. (GameAIPro2)
- Build dynamic LOD by swapping cheaper behaviors/animation drivers at distance (full IK on-screen, dummy state tracking offscreen; aggregate many distant agents into one simulation) — possible only because behaviors are decoupled and swappable at runtime without gameplay's knowledge; scale back if it shows. (GameAIPro2; GPGems2)
- Rank agents by relevance to the player (distance, visibility, being aimed at, recent damage) and give the most interesting behaviors to the highest-ranked — focus the budget where the player will notice; gate behavior on on-screen realization. (GameAIPro2)
- Distribute long calculations (A* pathfinding) across frames by saving/resuming state and solve only the part you need now (hierarchical room-to-room first, micro-path per room as entered) — lowers per-frame load and discards unbuilt work on redirects. (GPGems2; GameAIPro2)
- Amortize expensive queries by continuously updating a data structure as data changes rather than gathering on demand, and batch expensive updates (rebuilding k-d trees, recomputing regions, sampling queues) into one pass — spreads cost over many frames so each query is cheap (influence maps, LOS lists, fog-of-war). (GPGems2; GameAIPro2)
- Restrict expensive per-character systems to the few that need them (runtime cover-edge generation for buddies only, one navigation pathfind per frame) — cap, timeslice, or round-robin costly queries. (GameAIPro2)
- Recompute paths only every ~10–20 updates, and re-path/re-detect only every N seconds via interval timers — re-pathing every frame is the dominant cost; throttling is the primary lever for supporting many agents. (SWEngGames; UnityAI)
- Periodically re-check for a higher-priority runnable behavior and preempt the active one — otherwise a sleeping unit gets murdered before its behavior finishes; the preempted behavior's cleanup restores a clean state. (GPGems2)
- Game AI gets ~10% (rarely >20%) of the machine and must hit near-real-time — choose techniques whose time/memory you understand, since richer environments make individual checks (LOS, perception) more expensive faster than hardware grows (Halo 3 did fewer LoS checks than Halo 2). (GameAIPro2)
- Cull off-screen / out-of-bounds dynamic agents that can't be regenerated cheaply — enemies that wander onto invalid space keep taking turns and slowing the sim. (PCGUnity)
- Use micro-threads (cooperative stack-swap with WaitOneFrame yields) to write AI as straight-line code, structured as priority-selected behavior modules — state lives implicitly in the program counter + stack, eliminating the giant `m_state` switch; preempt by highest-priority IsRunnable behavior. (GPGems2)

### Data-Driven Wiring & Tooling
- Never refer to concrete character types in code; define each type by a set of skills, behaviors, and tuning data — adding/removing a type means editing data, never hunting code branches; resist adding "just one" type-specific check, since it proliferates and erodes the design. (GameAIPro2)
- Make difficulty a data-tuned threshold, never a code branch on character type — drive adaptation off a player model (skill/emotion/style) rather than just adding enemies, tuning per-character response thresholds when memory/perf caps headcount. (GameAIPro2)
- Keep resource-source and behavior conventions in data, not code ("gold comes from the ground" is a rewritable rule, not an engine fact) — and store behavior logic in assets (ScriptableObjects) separate from scene instances for reuse, reaching runtime components through a passed-in owner reference. (GameAIPro2; UnityAI)
- Expose all tunables via inspector/serialized fields (speed, mass, radius, weights, durations, set thresholds) — designer-editable fields are the difference between iterating in seconds vs. recompiling. (UnityAI; GPGems2; SWEngGames)
- Treat AI behavior as content PCG can manipulate — generate/swap whole behavior sets (skip-turn → no-skip, simple-chase → wall-avoiding) instead of only scaling raw numbers. (PCGUnity)
- Build instrumented runtime/memory measurement and live rule editing/reloading into AI tools from the start — iteration speed on the LHS/behaviors is the dominant cost; live-edit-then-rerun a scenario is invaluable. (GameAIPro2; GPGems2)
- Provide editor-time visualization (gizmos, debug-draw lines, colored state boxes, grids, paths, sensor cones, crowd destination/heading/avoidance arrows) for every system — render runtime structures so designers see and tweak the invisible without a debugger. (UnityAI; GameAIPro2; EditorScripting; GPGems2)
- Provide debug menus that drive high-level AI decisions from a controller (teleport, repeat-move, select behavior/demeanor) and dummy implementations (a dummy animation controller that completes/fails orders) — replacing skills/animation with manual input isolates whether a bug is in decision or realization. (GameAIPro2)

### Robustness & Believability
- Make characters "not stupid" before making them smart — eliminating glitches (running into walls, twinning, staring at walls) earns more attributed intelligence than clever decisions; keep code simple and modular specifically to isolate those glitches. (GameAIPro2)
- Maintain a prioritized skill/behavior list tested high-to-low each tick with a guaranteed-valid fallback last — prevents the AI from ever entering an uncontrolled/frozen state; run skills until completed or interrupted by a higher-priority skill for clear interrupt semantics. (GameAIPro2)
- Give NPCs that can't reach the player something intelligent to do (cover connecting choke points via an environment-connectivity model) — nothing is worse than feeling smart for flanking an NPC that's just staring at a wall. (GameAIPro2)
- Match motion qualities to evolved perception (short fast movements read as aggressive; gaze direction signals intent; creep-then-pounce, not pounce-then-creep) and set up context before the action — players shape-fit sparse motion into learned behavioral models and build internal narratives from abstract shapes. (GameAIPro2)
- Communicate intent clearly enough to read, and cut features you can't communicate — a blind Clicker using invisible echolocation confused players and was abandoned despite being clever. (GameAIPro2)
- Give every AI a diegetic reason to exist (guard, patrol, task) — placement without purpose (guarding empty crates, staring at a car) breaks the simulation's believability. (LevelDesign)
- Hold friendly/escort AI to a higher reliability bar than enemy AI, and keep buddy AI close to the player so its actions are no dumber than the player's and failures are self-attributed — broken ally paths force babysitting and invert the fun. (LevelDesign; GameAIPro2)
- Avoid cheating on principle (no teleporting buddies to keep up) so you're forced to solve edge cases realistically — teleport only when the camera hides it; the small details from honest solutions are what make a character feel alive. (GameAIPro2)
- Always make enemies beatable — there's no game the moment they're impossible; the player, not the computer, should feel like the hero. (SWEngGames)
- Validate guessed model parameters (queue rates, influence constants) with a fast standalone test app over many timescales, and add spam/oscillation detection where order-merging hides bugs — don't trust hand-tuned stochastic parameters, and don't let the fix that hides visual glitches also hide gameplay bugs from QA. (GameAIPro2)
- Implement undo as a stack of (variable, old-value) entries for any system that speculates and backtracks (constraint solving, search) — cleanly reverts a bad choice and its propagated effects. (GameAIPro2)
- Before blaming AI for a failure, eliminate environmental causes (invisible wall blocking a path, map hole breaking the script) — a faulty agent and a faulty world look identical; categorize AI defects as pathfinding vs. NPC-behavior. (QATesting)
- Watch NPC/AI strength as a balance lever — over-qualified AI allies make the game too easy, weak ones too hard; AI behavior directly shifts difficulty, so tune it as part of balance. (QATesting)
