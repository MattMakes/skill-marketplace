# Data-Driven Design, Tooling, Robustness & Testing

## Data-Driven Design & Authoring Tooling

### Separate Data From Behavior (One System, Every Entity)
- Separate data from behavior — store state in data-only components/structs and run logic in shared systems, so one system serves many entity kinds and both sides stay independently testable. (ECSFundamentals; EditorScripting; GPGems2)
- Let systems query entities by component signature (the capability they carry), not by object reference or concrete type — the same movement/damage system processes players and enemies as long as both carry the required components, maximizing reuse. (ECSFundamentals; GPGems2; HeadFirstPatterns; AdvancedCSharp)
- Never refer to concrete character/entity types in code; define each type by a set of skills, behaviors, and tuning data — adding or removing a type then means editing data, never hunting code branches. (GameAIPro2)
- Resist adding "just one" type-specific code check — that one check proliferates and erodes the data-driven design; sit with the designer and fix the rule in data instead. (GameAIPro2)
- Make difficulty (and other per-character knobs) a data-tuned threshold, never a code branch on character type — keeps it configurable per character without code changes. (GameAIPro2)
- Keep resource/source conventions in data, not code ("gold comes from the ground" should be a rewritable rule convention, not a hard-coded engine fact). (GameAIPro2)
- Separate logical behavior from audio-visual behavior — one behavioral class (a Door, a spell's data-alteration component) can drive any number of visual flyweights without caring about model size or animation count. (GPGems2; RPGDirectX)
- Provide a generic Property/PropertySet layer (name → field, hashed) so tools (in-game editor, save, network) operate on any object without per-type rewrites — derived types just register extra properties; this decouples the stored name from the internal field name. (GPGems2)
- Make the engine assemble behavior from reusable pieces at runtime (vary strategies/reactions/params per entity) so data-driven scripting works without code bloat from scripts-compiled-to-C++. (GPGems2; SWEngGames)
- Distinguish definitions (templates: a Master List record) from instances (live objects with current stats, position, AI) — one definition spawns many tracked instances, and only instances change during play. (RPGDirectX; GPGems2)

### Externalize Tunable Data Into Config/Assets
- Never hard-code game-related data (dialogue, stats, item/spell/character defs, placements, balancing numbers) in source — externalize it so changes don't force a recompile of a huge project. (RPGDirectX; EditorScripting; GameMechanics)
- Move tunable system parameters (gravity, music, difficulty knobs, weapon/enemy tables) out of behavior classes into standalone data assets/tables separate from logic — values become swappable and reusable. (EditorScripting; IntroGameDesign; SWEngGames)
- Move every balancing magic number into a config file/asset tweakable without recompiling — programmer recompile round-trip is the enemy of tuning; mid-game live tweaking is best, level-restart next best. (PolishedGameDev; GPGems2; SWEngGames)
- Hoist every tunable into a named static initialized at the top of one file (never a raw magic number in logic) and group interdependent tunables together — type-checked, self-documenting, and editable without recompiling dependent headers; prefer statics over `#define` because they get type checking, avoid wide recompiles and namespace collisions, and can change at runtime. (SWEngGames; ProgramArcade)
- Store level-varying parameters in parallel arrays with a single `setLevel()` that plugs them all in — one call swaps a whole tier of tuning. (SWEngGames)
- Provide typed config accessors (`getOptionAsInt`/`getOptionAsBool`) with min/max clamping and always supply defaults for missing keys — validate so a 0-second respawn can never ship from a typo, and defaults are a safety net, not optional. (PolishedGameDev)
- Layer config sources by priority (config file < local storage < command-line/URL params) — most-specific source wins, with defaults underneath. (PolishedGameDev)
- Prefer authored data sets over computed formulas for values management will tweak arbitrarily (per-screen min/max durations) — rebuilding a formula per arbitrary request is wasted time. (PolishedGameDev)
- Persist UI/option state (music/sound toggles, selected targets) between sessions — choose persistence scope by who/what the setting belongs to: per-developer prefs in editor prefs, per-project shared state in data assets. (PolishedGameDev; EditorScripting)

### ScriptableObjects vs Text/XML/Binary — Picking the Format
- Use serializable engine data-container objects (ScriptableObjects) instead of XML/JSON/plaintext when the engine can serialize natively — you skip writing parsers and get editor integration for free. (EditorScripting; Unity5Opt; UnityAI)
- Author content (level layouts, room maps, enemy rosters) and persist world/save state in a structured serialization format (XML or equivalent) when humans must hand-edit it — a defined schema makes content/save robust and human-editable. (IntroGameDesign; RPGDirectX)
- Use text data formats during development (human-readable, flexible, shareable constants) then compile to binary for shipping — best of both: easy authoring plus much faster loads and smaller size. **When it flips:** for bulk fixed-size records the engine random-accesses, store binary master lists as sequential files reachable by `seek(sizeof(record) * index)`, and keep plain text only where humans edit (triggers, action templates). (GPGems2; RPGDirectX)
- Run a C-style preprocessor (`#include`/`#define`/macros) over data/script files and share the same header between code and scripts — magic numbers become named constants that can't drift out of sync between code and data. (GPGems2)
- Reference data by integer index, not by name/text, in scripts and runtime structures — number lookups process faster and shrink saved/transmitted data. (RPGDirectX)
- Make every list size a named macro/constant (`NUM_SPELL_DEFINITIONS`) — adjust capacity in one place. (RPGDirectX)
- Store data assets as Force Text (YAML) and enable visible `.meta` files — enables human-readable diffing/merging in source control and bulk editing outside the editor. (Unity5Opt)
- Use ScriptableObjects to store game data that needn't be instantiated at runtime and load via `Resources.Load` — gives fine-grained control over which data is in memory. (Unity5Opt)
- Know your serializer's exact limits (primitives, engine objects, enums, structs, lists/arrays of those — but not statics, read-only values, properties, or dictionaries) and design data structures within that set, or you'll need custom inspectors/serialization (fake dictionaries via paired lists). (EditorScripting; Unity5Opt)
- Decouple "is serialized" from "is visible": serialize private fields via attribute, hide serialized publics when needed — control persistence and exposure independently. (EditorScripting)

### Make Config First-Class, Shareable, and Reusable
- Make data assets first-class shareable references: one settings asset referenced by many entities means editing it retunes every consumer at once — ideal for themes/difficulty tiers (all easy levels share one gravity/feel preset). (EditorScripting; GameDevUnity)
- Let configuration live independently of the objects that consume it (no scene/entity attachment) so it can be authored, versioned, and reused on its own. (EditorScripting)
- Store appearance/behavior in a materials/database keyed by ID or pointer that entities reference — decouple surface/behavior properties from geometry so one material/record repaints many. (Tricks3D; GPGems2; RPGDirectX)
- Carry per-instance config (patrol endpoints, target scene, speed, damage) on serialized fields so prefab instances differ without new scripts — one script + Inspector values yields varied behavior. (Build3DUnity; Platformer2D; BulletHell)
- Drive level/scene targets and content graphs by serialized data (a `sceneToLoad`/`nextSceneName` per flag) rather than branching in code — each instance picks its destination, so the same prefab composes arbitrary level graphs. (Build3DUnity; Platformer2D)
- Categorize/tag system content (an enum category per piece) so tools can filter, group, and surface the right items — a category field turns a flat asset pile into a navigable palette. (EditorScripting; GPGems2; RPGDirectX)
- Store reusable data (materials, configs) as shared assets so many objects reference the same data in memory; edit once, every consumer updates — share by reference, not by copy. (GameDevUnity; EditorScripting)

### Expose Tunables So Designers Iterate Without Recompiling
- Expose every tunable that affects feel (speeds, accelerations, gaps, forces, heights, smoothing, pool sizes, spawn probabilities, attack-pattern timing) as a serialized field, never a hard-coded constant — designers tune in the Inspector without recompiling, and per-instance overrides become possible. (Unity2DCookbook; BulletHell; CSharpForUnity; Platformer2D; Build3DUnity; GameDevUnity; PCGUnity; IntroGameDesign; AdvancedCSharp; PatternsUnity6)
- Prefer `[SerializeField] private` over `public` for tunables — keeps the value editable in the editor while preserving encapsulation, so other scripts get no read/write access; never make a field public just to show it in the Inspector. (Unity5Opt; AdvancedCSharp; CSharpForUnity; Platformer2D; Build3DUnity; GameDevUnity; BulletHell)
- Split "behavior" (code) from "values" (Inspector) as the default workflow — the script defines what happens, serialized fields define how much, so balancing is a no-recompile loop. (GameDevUnity; IntroGameDesign; CSharpForUnity)
- Default serialized tuning fields to sensible starting values so a system works out-of-the-box and the designer only adjusts deltas — and remember newly-added serialized fields default to 0 on existing prefabs, so always assign starting values or a "working" system silently does nothing. (GameDevUnity; BulletHell)
- Build a generic "tweaker" so designers adjust variables live with near-zero overhead and transparency — exposing a variable should take under ten lines, the variable's users shouldn't know the tweaker exists, and it stores only a pointer to the real variable plus type info and optional min/max range. (GPGems2)
- Organize tweakables into named categories/instances browsable in an in-game console with specialized input widgets (angle dial, etc.) — fast iteration on balance. (GPGems2)
- Save tweaked values back to a header both debug and release `#include` (first instance only) — lets you tweak only in debug yet ship the tuned constants. (GPGems2)
- Parameterize behavior methods (`IncreaseScore(int amount)`, `AddGold(int amount)`) instead of hardcoding magnitudes even when current callers pass a constant — one flexible method serves many situations and future-proofs the system without API changes. (AdvancedCSharp; CSharpForUnity; Build3DUnity; Platformer2D)
- Plan to balance from the start: build in exposed, runtime-tunable parameters for the values you know you'll need to adjust, ideally changeable live, ideally via a content system that lets you keep tuning post-ship — about half of development is balancing and tiny values matter. (AoGD3; AoGD2; DesigningGames; GameMechanics)
- Encapsulate probabilities and ranges as named tunables and call them out as "experiment with this value" (a reusable min/max Count helper standardizes "between X and Y") — make odds editable and discoverable rather than buried constants. (PCGUnity; IntroGameDesign)
- Don't let players self-balance core values — conflict of interest makes them trivialize challenge; player-set difficulty levels are the safe exception. (AoGD3; AoGD2)
- Drive the interface itself from data (widget positions/sizes per platform, relative `x_align`/`x_offset` not absolute coords) loaded by detected resolution/DPI — for cross-platform this is mandatory, not optional. (PolishedGameDev)

### Wire Content and References Through the Editor, Not Code
- Wire prefab/asset and cross-object references through serialized slots assigned in the editor rather than hardcoded paths or runtime `Find` lookups — designers swap content without touching scripts, and explicit injected references are clearer than hidden global singletons. (Unity2DCookbook; CSharpForUnity; Platformer2D; PatternsUnity6; Build3DUnity)
- Use Unity's serialized-reference wiring (`[SerializeField]` on private fields) to connect systems at author time, preferred over public fields because it preserves encapsulation while exposing to the Inspector — but null/wrong-reference risk makes it team-fragile, so move to shared access points or events as dependents multiply. (Unity5Opt; PatternsUnity6)
- Use prefabs as configurable templates: build a GameObject with all components/behavior once, then instantiate copies at runtime — one authored source, many runtime copies, and edits to the asset propagate to every non-overridden instance. (Unity2DCookbook; CSharpForUnity; Build3DUnity; GameDevUnity; Platformer2D; BulletHell; IntroGameDesign)
- Support per-instance overrides so individual instances diverge on specific properties while structural changes still propagate — get shared base design AND local variation; but design override policy explicitly because an overridden property may not be replaced by later asset edits. (GameDevUnity; Build3DUnity; Platformer2D)
- Edit the prefab asset (Prefab Mode / Overrides > Apply All), not a scene instance, for changes that should apply to all copies — instance edits silently diverge. (BulletHell; Platformer2D; CSharpForUnity)
- Convert configured spawner/pool/camera/player systems into prefabs once working — reuse a complete, configured system across scenes without rebuilding it. (BulletHell; Build3DUnity; CSharpForUnity)
- Author level content with brush/tile tools and lightweight tile data (ScriptableObjects in a sparse grid) instead of hand-placing GameObjects — faster, grid-aligned, far cheaper memory, and easier to edit later. (Platformer2D; ProgramArcade)
- Build a new level by dropping in prefabs and tweaking instance values, not rebuilding systems — varied routes/speeds/placement make levels feel different "without requiring any new systems." (Build3DUnity; Platformer2D)

### Custom Editors, Inspectors & Authoring Tools
- Build authoring tools the moment a system's content creation turns repetitive or error-prone — manual copy/paste of system instances wastes time and corrupts data at the worst moment; build a dedicated editor for every master data list (items, spells, characters, scripts, triggers). (EditorScripting; RPGDirectX)
- Cost-justify every tool before building: the time it saves later must exceed the time to make it, or it's net negative. (EditorScripting)
- Design tools for the actual user (designer/artist), involve them early, and mock up the GUI first — a tool nobody can use solves nothing. (EditorScripting)
- Separate the data-authoring tool from the runtime system, and keep tool code in a separate assembly/folder, so the game ships without editor code and a tool bug can't break the shipping build (and vice versa). (EditorScripting)
- Keep editor data structures identical to runtime structures (same struct) — write once, load directly; modifying the editor means modifying the shared struct. (RPGDirectX)
- Expose data-asset values through their own inspector so designers tune them directly with the same validation/drawers as any component — config should be as safe to edit as runtime state. (EditorScripting)
- Provide a menu/command to mint new config-asset instances on demand (name + path) so designers spawn new tuning presets without touching code. (EditorScripting)
- Use PropertyDrawers (with `SerializedProperty`) to separate inspector display from data logic — gains built-in undo/redo/multi-edit and reusable per-field rendering; use the serialized-property API (not raw object access) when you want free undo support and rich attribute-driven metadata. (Unity5Opt; EditorScripting)
- Enforce dependencies and constraints declaratively with attributes — `[RequireComponent]`, `[Range]`, `[SerializeField]`/`[HideInInspector]`, `[FormerlySerializedAs]` (rename without data loss). (Unity5Opt)
- Render a sub-system's own editor inside a host tool (compose editors) so editing a child entity reuses its existing inspector rather than reimplementing it — compose authoring UIs like you compose components. (EditorScripting)
- Customize new-script templates to remove empty Update stubs — prevents the empty-callback overhead from being authored in by default across the team. (Unity5Opt)
- Build small editor/automation tools for tedious authoring (e.g. waypoint entry) when scale demands — manual entry is fine for a few points but custom tooling pays off as data volume grows. (UnityAI)
- Mark authored objects dirty after edits so the engine persists and redraws them — without an explicit dirty flag your tool's changes silently fail to save. (EditorScripting)
- Centralize look-and-feel in a shared style asset (skin), not scattered per-control style code, and centralize all text rendering behind a style wrapper capped at a few styles per screen — one stylesheet-like asset keeps appearance discoverable, testable, and consistent, and changes propagate instantly. (EditorScripting; PolishedGameDev)

### Validation & Designer Guard-Rails at the Authoring Boundary
- Validate and clamp every parameter a system consumes at the authoring boundary (force/time/size ≥ valid range) — a custom inspector is the cheapest place to make invalid system states unreachable; validate via `OnValidate`/setters. (EditorScripting; Unity5Opt; RPGDirectX)
- Surface type/usage errors inline where the value is edited (help boxes on misuse) rather than failing silently at runtime — fail loud, fail at author time. (EditorScripting)
- Type and constrain each authored field (text/bool/int/float/multiple-choice with min/max or choice list) in the template so the editor enforces valid values at authoring time. (RPGDirectX)
- Build custom editor tooling and init-time guards/warnings to prevent and surface systemic mistakes — duplicate-object warnings, data validators, and "only one of this manager exists" checks stop casual errors that cost hours of analysis later. (Unity5Opt; EditorScripting)
- Enforce structural invariants in code instead of trusting users (lock transforms, hide pieces, restrict editing) — assume users will break any constraint you merely document. (EditorScripting)
- Gate irreversible/destructive system operations (a resize that destroys content) behind explicit confirmation, and disable controls whose action is currently meaningless — make illegal operations visually impossible, not just rejected. (EditorScripting)
- Re-initialize/repair backing data lazily on tool open (rebuild arrays if null/empty) so corrupted or fresh state self-heals instead of crashing the tool; when a step can corrupt data mid-development, force a clean rebuild before testing. (EditorScripting)
- Prefer a UI that only permits valid input over post-hoc validation (drop-lists for units, ranged steppers) and validate by white-list — prevents buying -1 bullets, and is shorter and more future-proof than blacklisting. (PolishedGameDev)
- Drive sound/asset lookup by naming convention so the engine derives metadata (normalization group, surface type, variation count) from the filename, and report an error in dev mode whenever required data is missing — convention over configuration eliminates metadata and surfaces missing files early. (PolishedGameDev; RPGDirectX)

### In-Editor Visualization, Gizmos & Telemetry for Tuning
- Render runtime system structures (grids, waypoints, ranges, rays, bounds, sensor cones, node states, paths) as visual aids in the editor so designers see and tweak the invisible — a good visual aid is worth more than a thousand lines of debug logging. (EditorScripting; UnityAI; GameAIPro2)
- Color/encode state into the visualization (in-bounds green / out red) so correctness is read at a glance — make the system's validity self-evident visually. (EditorScripting; GPGems2)
- Drive visualizations from the same parameters the system uses (size from columns×rows) and let them update live as the underlying object changes — never hand-maintain a separate visual model; the authoring view must be a true mirror, not a stale snapshot. (EditorScripting)
- Provide a visualization overlay for any precomputed/baked system (texel density, visibility cells, light culling, LOD swap points) — designers tune what they can see; blind tuning produces blotchy or unstable results. (Unity6Opt)
- Visualize intermediate reasoning/analysis output projected onto the terrain (or exported to a spreadsheet) — essential to tune and verify heuristic algorithms. (GPGems2)
- Visualize crowd/agent internals while running (destination arrow, heading arrow, avoidance grid, neighbors) — divergence between destination and heading exposes how the system is reshaping behavior, which is critical for tuning. (UnityAI)
- Surface live telemetry (updates/sec, score, health, entity count) on screen, smoothed by a rolling average, and add an autorun/"plays-by-itself" mode plus a hidden God-mode flag — designers and players need to see runspeed and state, and self-testing reaches late-game scenarios without a human. (SWEngGames)
- Provide runtime inspection windows that list every component type, its fields, memory size, which entities/systems touch it, and system execution order/timing/live counts — visibility into data layout and data flow is how you debug emergent behavior in a large system graph. (ECSFundamentals)
- Expose a runtime toggle to disable/enable individual systems live, and provide debug menus that drive high-level AI decisions manually — flipping a system off and watching behavior stop isolates which system owns a behavior, and replacing skills with manual input separates a decision bug from an animation bug. (ECSFundamentals; GameAIPro2)
- Generate previews/thumbnails of system content asynchronously, polling until ready, rather than assuming they exist on the first frame — editor previews aren't available immediately after load. (EditorScripting)

### Edit-Time Simulation & Live Tuning Loops
- Allow chosen components to run their update logic at author time (execute-in-edit-mode) to preview system behavior without entering play — but know edit-mode callbacks fire differently, and force a repaint when external events change tool state since editor GUIs don't redraw continuously. (EditorScripting)
- Exploit Play Mode for live tuning — inspector edits apply instantly and revert on stop, so experiment with values freely, then bake the winners; but never rely on Play-mode changes as permanent since the editor restores pre-play state on stop. (BulletHell; GameDevUnity; CSharpForUnity; Unity5Opt)
- Persist designer experiments made during play by routing runtime tweaks through a data asset so the discovered values survive exiting play mode — the painful "I found the magic number but I was in Play mode" loss is a data-architecture failure. (EditorScripting)
- Run the design process as a tight build/test/notice-what-feels-wrong/change/retest loop and expose the dials that make that loop fast — most learning and tuning happens there, so keep iteration cheap and values editable; treat game feel as a tuning problem (mass, force, friction, increment), not a coding problem. (CSharpForUnity; Platformer2D; IntroGameDesign; Build3DUnity)
- Build in adjustable parameters editable live or via an external text/config file (LOOP's data-driven editor, Spore's creature editors) — data-driven tuning lets designers refine variables while engineers build the rest, and commits the team to a daily working build so everyone feels the system's current state. (GDWorkshop)
- Reflect authoring edits back into baked/runtime data live — changing an Inspector value and re-baking should immediately update runtime data, tightening the iteration loop. (ECSFundamentals)
- Caution: live mid-game setting changes are easy to add but dangerous — changing respawn to 30s while in-flight objects hold 18s, or shrinking a TTL below its current value, can manifest as phantom bugs. (PolishedGameDev)
- Pick a fast-loop engine with live scripting so you can recode while running (mix a fast static low-level language with a slow dynamic high-level one) to maximize loops/day — and lower the cost of testing so you can plan to a shorter horizon and take risks that surface unplannable designs. (AoGD2; DesigningGames)

### Authoring/Baking Layer (Edit-Convenience vs Runtime-Lean)
- Use an authoring (editor-facing) layer that bakes into runtime data — designers edit familiar Inspector fields, gizmos, and serialization while the runtime consumes optimized, stripped-down structures; run baking as an explicit build step between the two formats. (ECSFundamentals; Unity6Opt)
- Mirror runtime component fields in the authoring component and copy them across in the baker — gives designers tunable values without coupling the runtime struct to editor concerns; drop the authoring layer entirely when a component has no editor-facing values. (ECSFundamentals)
- Bake references by converting editor handles (GameObject prefabs) into runtime handles (Entity references) — systems operate only on runtime types, so resolve all references at bake time, not runtime. (ECSFundamentals)
- Declare at bake time exactly which capability sub-components an entity needs (e.g. transform usage Dynamic vs None) and tag logic-only entities (spawners, singletons, controllers) as needing no spatial data — attach only required components so entities that never move/render waste no memory. (ECSFundamentals)
- Shift expensive, static computation out of the per-frame loop into a precomputed bake (lighting, visibility, terrain analysis), but only when the underlying inputs are truly static — treat baking as a cost transfer into bake time, disk, and runtime memory, not a free win. (Unity6Opt; GPGems2; Tricks3D)
- Expose sample/quality knobs on any baker (samples, bounce count, resolution) plus a fixed default with per-object overrides, and validate the data layout the baker depends on (e.g. lightmap UVs) — bake artifacts (blotches, leaks) are tuning signals, and wrong input channels produce nonsensical output. (Unity6Opt)
- Generate collision/derived data offline in the asset pipeline (transparency → outline → bit-packed mask) rather than computing it in-engine — prepares data in exactly the form the engine needs, and the benefit scales with object complexity. (PolishedGameDev; GameMath)

### Asset & Content Pipeline Automation
- Hook the import pipeline to auto-apply correct settings to incoming assets by convention (path/filename rules), with pre-process hooks to configure input and post-process hooks to transform output — never rely on humans to manually configure every asset, and read-modify-write existing settings rather than constructing fresh ones. (EditorScripting)
- Encode content conventions (folder structure, naming) as machine-readable rules the pipeline enforces — conventions only scale when automation, not discipline, upholds them. (EditorScripting)
- Automate repetitive content-pipeline steps with scripts (export scripts, asset post-processors reading custom attributes, XML-driven animation splitting) and externalize clip metadata to a machine-read file — hand-typing import data into the Inspector invites human error. (Unity2DCookbook)
- Query the asset database programmatically (find by type, GUID → path → load) to discover all instances of a system's content automatically — never hardcode content lists that drift from reality. (EditorScripting)
- Attach object metadata in the asset pipeline (material type for ricochet sound/decal, animation event frames, transition refs) so the game is modifiable without code changes by any discipline, and expose tuned parameters in your level editor in-world (Super Mario Maker style). (PolishedGameDev)
- Ship pipeline-critical automation as a precompiled library, not loose scripts — so a compile error elsewhere can't silently disable import processing and produce mis-configured assets. (EditorScripting)
- Version, name, timestamp, and multitrack every authored asset so any iteration can be recovered — new tool/plugin versions silently break old settings; reproducible asset history is part of maintainability. (QATesting)
- Choose proven, well-documented, tool-supported, non-proprietary file formats over locked ones (FBX over native, PNG over PSD) and start with a dead-simple ASCII format you can graduate later — leverage existing modelers/editors and let collaborators without the source tool use the asset. (Tricks3D; Unity2DCookbook)
- Build a reusable parser/tokenizer class with helper functions rather than ad-hoc reads per format — file loading is a recurring need across many formats. (Tricks3D)

### Data-Driven Input, Scripting & Action Authoring
- Define gameplay actions (Move, Jump, Fire) in a data asset and bind physical inputs to them, instead of polling hard-coded keys — scripts react to the abstract action firing, so rebinding, multiple devices, local multiplayer, and touch cost nothing. (Build3DUnity; Platformer2D; BulletHell; GameDevUnity)
- Group related actions into Action Maps (one context per gameplay mode) so whole input sets enable/disable together — clean context switching as the game grows. (Build3DUnity; Platformer2D)
- Route input through a bridge component (Player Input → Invoke Unity Events) to call public script methods on action fire — fully decouples the input asset from the controller; the script never references key names. (Build3DUnity; Platformer2D; BulletHell)
- Prefer a constrained "Mad Lib" script system (pick from predefined actions with typed blanks) over a full compiled language when the action set is small — gets a working scripting engine running fast, covers ~90% of game logic, and the editor enforces valid values at authoring time. (RPGDirectX)
- Make the engine accept scripts for most in-game data (items, characters, triggers, routes, level-entry, combat) and derive the script filename from the event by convention — keeps the engine open and recompile-free with no central registry. (RPGDirectX)
- Use forward GOAP-style planning with actions as editable text files, and keep a grammar's interpreter separate from its rules — nonprogrammers iterate offline without recompiling, and fast rule add/change is the whole power of grammars (fusing rules into branching control flow loses it). (GameAIPro2)
- Score and select runtime behavior with composable, runtime-reloadable criteria (LISP-defined post selectors) multiplied into one rating, and build instrumented runtime/memory measurement and live rule editing/reloading into AI tools from the start — iteration speed on rules/behaviors is the dominant cost, so live-edit-then-rerun a scenario is invaluable. (GameAIPro2)
- Drive complex/articulated motion from external data (keyframe meshes or skeletal motion files) and author character behavior with a scripting/opcode VM instead of hard-coded logic — once the engine reads motion/behavior data, any animation or behavior is just editable data, no recompile. (Tricks3D)
- Build animation logic visually in a state-graph tool (states are clips, arrows are transitions, typed parameters drive conditions) so designers author the logic and code only sets parameters; reuse one controller across objects via override controllers that swap only specific clips. (Unity2DCookbook; UnityAI; Unity5Opt; Build3DUnity; Platformer2D; BulletHell)
- Author membership/easing curves as editable assets (animation curves) for designer tuning — visual curve editing lets non-programmers reshape fuzzy sets or speed-control functions; evaluate the curve at the input value. (UnityAI; GameMath)
- Expose modular system operations as composable "recipes" (influence-map Add/Multiply/Normalize, audio interpolation between keyframed states driven by one game value) so behaviors compose without code — most of the intelligence lives in the propagation/generation weights, so spend tuning effort there. (GameAIPro2; GPGems2)

### Spreadsheets, Telemetry & Simulation as Tuning Consoles
- Use the spreadsheet as your primary balancing and probability tool throughout the project, not just at the start — build damage tables, probability distributions, and weapon stats there, keep the model live so changing inputs recomputes derived columns instantly, and chart distributions so imbalance is visible at a glance. (IntroGameDesign; Challenges; GDWorkshop)
- Maintain spreadsheets whose structure mirrors the game's subsystem structure (interconnecting tables per subsystem), laid out jointly with programmers — they're both the design starting point and the tuning endpoint. (GDWorkshop)
- Model mechanics in an abstract visual diagram language (Machinations: pools, sources, drains, converters, traders, gates, registers) before or instead of writing code, and set the model's abstraction/scope deliberately — model only the mechanics that matter. (GameMechanics)
- Run automated simulated playtests: add artificial players with scripted strategies (rusher vs turtle) and run thousands of iterations in seconds to gather statistics, then tune numeric values (costs, rates) and re-simulate until win-rates/game-length match goals — measure balance empirically, don't guess. (GameMechanics; AoGD3; AoGD2)
- Instrument the live game to collect play data (win rates by map/matchup), then pair the telemetry with designer intuition and top-player replays — use stats to distinguish real imbalances from perceived ones, but don't be a slave to the data. (GDWorkshop; DesigningGames; QATesting)
- Use metrics for fine-tuning beyond playtest resolution and engineer clever metrics for hard-to-observe data (position/health/death graphs, an "I just saw lag" button, recorded match movies) — superior knowledge, not superior coders, makes superior tuning. (DesigningGames)
- Build expressive-range analysis for any generator: define measurable content metrics, generate a large sample, and visualize the distribution (histogram/heatmap) — reveals generator bias and lets you compare versions after small changes. (GameAIPro2)
- Track playtest data and outcomes in tables (probability, progression, logged results) and feed them back into tuning — telemetry-informed tuning beats guessing. (IntroGameDesign)
- Build a data-export/replay tool when the profiler window is capped, and instrument your own systems with custom profiler markers (BeginSample/EndSample) that compile out of release builds — without markers an entire update method reads as one opaque block, and chunked logs let you inspect long-term behavior. (Unity5Opt; Unity6Opt)

### Build, Provenance & Release Automation
- Make the build a single scriptable command-line step from the start (even a few lines) and release it to the team early — scriptable equals automatable equals ship-any-day; automate multi-target builds behind one action that iterates enabled platforms and outputs to organized per-target paths. (PolishedGameDev; EditorScripting)
- Drive build configuration (company/app/version/bundle id, included scenes) from code/the project's single source of truth rather than hardcoding or setting by hand — settings set manually drift between builds, and the scene list is the single source for what ships. (EditorScripting; Build3DUnity; Platformer2D; GameDevUnity)
- Stamp builds with traceable provenance (VCS commit hash + date) by code-generating a build-info source file before compiling — a broken build must map back to an exact commit. (EditorScripting)
- Bundle build configuration into switchable profiles (target platform + scene list + scripting defines + overrides) so you can keep dev and release profiles and swap without editing global settings. (GameDevUnity; Unity5Opt)
- Run a two-phase build (per-file processing, then whole-filesystem aggregation per SKU), keep target output regenerable and out of source control, and quarantine third-party engines pinned to a known-good revision — isolates upstream breakage until a lead promotes new versions. (PolishedGameDev)
- Keep config files out of source control (commit only `.example` stubs) and never commit API keys/secrets — each dev keeps a private local config; secrets widen the security perimeter. (PolishedGameDev)
- Validate assets in the build tools (square/power-of-two textures, format support, size limits) and chain distribution into the build (auto-upload per platform) — the sooner a bad file is caught the fewer systems it disrupts, and one-step build-and-deliver shortens the feedback loop to playtest. (PolishedGameDev; EditorScripting)
- Register every loadable scene in the build list (index 0 launches first) — a scene file in the project is not in the build; an unregistered or misspelled name fails silently with a runtime error. (Build3DUnity; Platformer2D; BulletHell; GameDevUnity)

### Tool Reuse, Distribution & Maintainability
- Treat a genuinely reusable tool as its own independent project/repository from the start, packaged under a root folder named for the tool — so it can evolve, be versioned, and be consumed without dragging host-project coupling. (EditorScripting)
- Prefer version-control submodules over manual package exports for tools shared across a team — submodules keep every project's copy updatable and let bug fixes flow back, whereas exported packages rot and require manual re-distribution. (EditorScripting)
- Generalize utilities with generics (find-all-assets-with-component-T, enum-to-list-T, a pool generic over a poolable contract) to maximize reuse across systems instead of copy-specializing per type. (EditorScripting; Unity5Opt)
- Leverage existing engine assets and Asset Store/library solutions for well-trodden systems (pooling, audio management, atlasing, LOD, behavior-tree editing) rather than reinventing — but build one from scratch once to understand the internals well enough to extend it; evaluate buy-vs-build by time/budget/control. (Unity5Opt; UnityAI; IntroGameDesign)
- Aim for code clean enough to re-skin — truly data-driven levels, loosely-coupled scripts, and no engine-side edge-case hacks are the test of whether the engine is sellable/licensable separately. (PolishedGameDev)

### Modding & Player-Authored Content
- Treat modding/authoring as a supported interaction mode and expose rules, art, and data to players — modding is "just playing the game in another way," and building systems that let players author content extends the system's life far beyond shipped content. (TheoryOfFun; GDEssentials)
- Use player-generated content (opponents, maps, contributed characters) as an endless source of new content to refresh the possibility space — but other players reintroduce the mastery problem, so gate by skill. (TheoryOfFun; GDWorkshop)
- Allow house-rule modifiability where possible — players hacking your rules is a sign of a deep, extensible system, not a flaw, so fold the good emergent "laws" back into the design. (IntroGameDesign; AoGD3)
- Expose the rules to the player when emergence is the point — surfacing tunable rules turns a simulation into a sandbox, and giving players authoring tools is itself procedural generation that often yields a more immersive experience than randomization. (GDEssentials; PCGUnity)

## System Robustness, Testing & Verification

### Defensive Boundaries & Input Validation
- Validate and clamp every parameter a system consumes at the authoring boundary (force time/size ≥ 0/1, config min/max, respawn never 0) — the cheapest place to make invalid states unreachable, so a typo never ships. (EditorScripting; PolishedGameDev; GPGems2)
- Bounds-check and validate every index, ID, and asset reference before use (clamp flag indices, validate sound/spell numbers, confirm the referenced asset/player exists) — out-of-range or dangling references crash; guard them at the boundary, not at the cascade. (RPGDirectX; ProgramArcade)
- Convert and validate external/user input to the correct type at the boundary before math — raw input is text, so adding two inputs concatenates; coerce and guard where data enters the system. (ProgramArcade)
- Place defensive validation high in the call stack at cheap entry points, never in low-level math/animation hot loops — per-method checks everywhere make the game unplayably slow. (PolishedGameDev)
- Treat a single bad numeric value (one NaN, one bad ref) as a whole-system hazard and validate at the boundary — in shared/ECS-style systems it cascades across every entity the system touches. (ECSFundamentals)
- Clamp resource gains to their caps inside the grant function (don't exceed max health) — keeps the economy from overflowing no matter how many sources fire at once. (PCGUnity)
- Keep defensive stats bounded so an entity never becomes untouchable (cap agility/defense/resistance) — uncapped defensive values break the combat loop. (RPGDirectX)
- Normalize composite/diagonal input vectors and direction vectors before driving movement — guards against unintended speed amplification and keeps speed a tunable scalar, not a leak from distance. (VersionControl; CertProgrammer)
- Remap raw oscillation/random output into a safe usable band (e.g. -1..1 → 0.2..1.5 for scale) — unmapped ranges produce invalid states like zero/negative scale. (ECSFundamentals)
- Account for sprite size and origin in boundary tests (bounce at `screen_height - sprite_height`, place the pivot at the feet) — testing against the raw edge lets entities leave the screen or mis-detect ground. (ProgramArcade; Platformer2D)
- Bounce by negating the relevant velocity component when a boundary is crossed, never by negating position — flipping position teleports the object instead of redirecting it. (ProgramArcade)
- Guard incremental/step movement with a boundary check before applying it (clamp at the edge) — step-based movement otherwise runs off or clips into walls. (CSharpForUnity)

### Null, No-Path & Edge-Case Handling
- Null-check resolved components before calling into them, and use optional-component lookup (`GetComponent<Health>()?.TakeDamage`) so a hit on a non-damageable collider is a safe no-op — a hit can return any collider; act only when the expected capability is present. (BulletHell; CSharpForUnity; UnityAI; GameDevUnity; AdvancedCSharp)
- Always null-check (or null-conditional `?.Invoke()`) an event before raising it, and subscribe/unsubscribe symmetrically in enable/disable lifecycle hooks — prevents firing into nothing, NullReferenceExceptions, and leaked dead subscribers across recompiles. (EditorScripting; BulletHell; PatternsUnity6; GameDevUnity)
- Expect and handle dangling references when a tracked target is destroyed (enemies targeting a dead player) — left unhandled they spew NullReferenceExceptions; decide deliberately between disabling vs destroying the target, and have each side of a two-way link null the other on death. (BulletHell; SWEngGames; RPGDirectX)
- Use a null-object default (a NoCommand, a "null channel" that fires callbacks immediately, return empty arrays not NULL) so caller code stays branch-free and robust against empty slots/failed subsystems. (HeadFirstPatterns; PolishedGameDev)
- Guard every operation that throws on empty/invalid collections — check Count/existence before Dequeue/index, and ContainsKey before Add — these raise InvalidOperationException; branch instead of crashing. (AdvancedCSharp; PCGUnity)
- Guard a lookup against empty/invalid neighbors before indexing (check adjacent count > 0, break when none) — "no neighbors" means "edge reached," not a crash. (PCGUnity)
- Use early-return guard clauses for invalid input: check the failure condition, log a friendly message, and return before touching the risky call. (AdvancedCSharp)
- Distinguish benign expected failures from real errors and skip them gracefully (a client that never set its info, a destroyed-player message during host setup) — treat normal edge cases as skips, not errors. (RPGDirectX)
- Write rules to close the loopholes the basic objective leaves open (Monopoly "do not pass Go") — an unstated edge case becomes an exploit or an argument. (GDWorkshop)
- Clear structures to known defaults in constructors and on reset (flags FALSE, pointers NULL, counts 0) — predictable starting state avoids garbage-driven bugs; lazily re-initialize/repair backing data on tool open so corrupted or fresh state self-heals instead of crashing. (RPGDirectX; EditorScripting)
- Make every init function return a success/failure code and check it at each step, aborting and releasing on first failure — a half-initialized system is a crash waiting to happen. (RPGDirectX)
- Guard the death threshold (`<= 0`) and prefer inclusive boundary comparisons (`<=`, `>=`) for state thresholds — exact-equality checks miss the boundary when a step overshoots, letting HP drift into meaningless negatives or counters run away. (BulletHell; GameDevUnity; CertProgrammer)
- Add a one-hit guard flag (one target per projectile) and a brief invulnerability window (SAFEWAIT) against same-frame double damage — overlapping frames otherwise multi-hit and double-spend damage. (BulletHell; SWEngGames)
- Guard against repeated/duplicate event firing (overlapping triggers, overlapping hit flashes, multi-phase input) with a flag, phase check (`context.performed`), or by canceling the prior coroutine — rapid events otherwise produce inconsistent state. (BulletHell)
- Every while/search loop must have a guaranteed exit (bail counter) and every recursion a base case — "never go into a while loop without making sure you get out"; unbounded self-calls exhaust the stack and crash. (SWEngGames; ProgramArcade)
- Order a search/loop's guard to check "still in range" before "matches key" — testing the element before the bounds check indexes past the end. (ProgramArcade)
- Collect items for deletion in a separate list and delete after the loop; never mutate a collection mid-iteration — removing mid-iteration corrupts indices, and adding a listener mid-dispatch throws an enumeration exception. (PCGUnity; Unity5Opt)
- When removing one node from a linked list, null its Next before deleting so a recursive destructor doesn't free the rest of the list — a classic teardown hazard. (RPGDirectX)
- Have spawned/transient objects self-destruct when off-screen, out of bounds, or on state exit, and release pooled objects on every exit path (expiry AND impact) — leaked objects accumulate, degrade performance, and break pools. (IntroGameDesign; BulletHell; UnityAI)
- Guard ECS-style systems to update only when relevant data exists (`RequireForUpdate<T>`) — skips empty-work frames and prevents crashes when a component type isn't present yet. (ECSFundamentals)

### Graceful Degradation & Failure States
- **Fail loud, hard, and fast in development; degrade quietly in production** — stop on missing assets, out-of-range coords, or bad metadata during dev so problems can't linger, then switch the same assertions to warn-and-return-a-sensible-default (or throw) via per-build macro expansion when shipping. (PolishedGameDev; EditorScripting)
- Build defensive system responses for failure states as a required, testable feature: on data corruption, warn and suggest recovery; on disconnect, pause; provide safe defaults when a load fails (high score = 0 if the file is missing) — graceful failure handling is not an afterthought. (QATesting; ProgramArcade)
- Wrap operations that can fail at runtime (file I/O, parsing, network) in try/except and absorb them gracefully — disk-full, deleted/moved files, yanked drives, and bad input are normal conditions, not crashes; catch specific types first with the bare catch-all last, and pull diagnostics from the exception object. (ProgramArcade)
- Use exceptions for abnormal conditions only, never as routine control flow — the happy path should raise nothing; convert recoverable edge cases (empty queue) into handled, observable feedback (a log), not a crash. (ProgramArcade; AdvancedCSharp)
- Detect device/resource absence and degrade instead of crashing: count joysticks and branch on zero so a missing controller degrades gracefully; detect missing audio with a build-time source scan plus a runtime placeholder baked into the binary so it can't itself go missing. (ProgramArcade; PolishedGameDev)
- Verify any required dynamic collider/platform exists before relying on it — a platform without a collider drops the player through and can cause an eternal game-over loop; treat the collider as required, not optional. (Build3DUnity)
- Add a fall-out-of-bounds safety net (reload when Y drops below a tuned threshold) — prevents falling forever; tune so the fall reads before the reset. (Build3DUnity)
- Design systems to contain their own faults (sandboxing/self-healing) so a fault can't corrupt the environment — this shifts QA from "testing for failure" toward "testing for greatness." (QATesting)
- Treat unassigned-reference and null-reference exceptions as wiring/config defects, not logic bugs — trace to the missing Inspector assignment or initialization and assign/guard there rather than patching symptoms. (CertProgrammer; Unity5Opt)
- Be willing to disable a flaky feature rather than ship it ("developer gold-plating") — robustness over feature count; quality/scope is usually the only constraint corner you control. (SWEngGames)
- Add physical backstops for directions a joint/constraint doesn't bound (a rear collider so drawers can't be shoved through the cabinet back) — a limit only constrains the directions you explicitly constrained. (VRUnity)

### Invariants, Asserts & Structural Guarantees
- Enforce structural invariants in code, not documentation — lock transforms, hide pieces, restrict editing, and surface type/usage errors inline where the value is edited; assume users will break any constraint you merely document, so fail loud at author time. (EditorScripting)
- Validate method inputs with assertions that warn-and-continue in dev but return a predetermined sensible value (or throw) in production — different macro expansions per build keep dev loud and release safe. (PolishedGameDev)
- Make singleton/manager uniqueness a loud invariant: throw if zero or more than one instance exists, lazily create on first run if absent, and add init-time guards/Editor warnings — if you don't explicitly disallow duplicates, someone creates them and corrupts shared state and telemetry. (ECSFundamentals; Unity5Opt)
- Never store the same fact in two places ("no forgery") — derive count from the array's size each frame rather than a counter that can desync; recomputing is cheap, keeping two copies in sync is bug-prone. (SWEngGames)
- Hide state behind accessors/properties even for trivial fields so you can add a coupled invariant later (keep velocity = speed×tangent) without touching call sites — and use getters/setters to validate and react to state changes on assignment. (SWEngGames; IntroGameDesign; UnityAI)
- Let the owner of state own its transitions — clients must never request raw state changes on a Context directly, or they break the invariants the owner enforces. (HeadFirstPatterns)
- Control initialization and update order explicitly (Awake → OnEnable → Start, FixedUpdate for physics) and refresh dependent flags before the check that reads them — undefined order between objects and stale state cause intermittent air-jumps and hard-to-find bugs. (PatternsUnity6; CertGameDev; GameDevUnity; IntroGameDesign; Platformer2D)
- Resolve concurrency invariants deliberately: guard Singleton getInstance() against multi-thread double-creation, guard shared producer/consumer memory with critical sections, and prefer one controlled simulation array over one-thread-per-object — undefined concurrency corrupts shared state and ordering. (HeadFirstPatterns; RPGDirectX; SWEngGames)
- Clamp dt to a max (~0.1s) and a min (1/refresh), and never divide by deltaTime without a sanity check — huge timesteps teleport entities through walls and tiny first-frame deltas make results blow up. (SWEngGames; GameDevUnity)
- Clamp/`Clean()` near-zero velocities, denormals, and Zeno-style asymptotic lerps — snap when "close enough"; tiny residuals cause micro-jitter, denormals trigger 10-100x FPU slowdowns, and asymptotic lerps never quite arrive. (GameMath; IntroGameDesign)
- Never compare floats with exact equality; use epsilon tolerance, prefer LengthSquared/DistanceSquared comparisons, and reformulate to avoid catastrophic cancelation — exact float compares and small-differences-of-large-numbers silently destroy correctness. (GameMath)
- Maintain a prioritized AI skill list tested high-to-low each tick with a guaranteed-valid fallback last — prevents the agent from ever entering an uncontrolled or frozen state. (GameAIPro2)
- Keep tool code physically separated from game code (separate assembly/folder, precompiled pipeline library) — a tool bug then can't break the shipping build, and a compile error elsewhere can't silently disable import processing. (EditorScripting)

### Determinism & Reproducibility
- Seed the PRNG with a fixed value in Debug builds (and at game start) but randomize the seed in Release — reproducible randomness lets you reliably re-trigger a bug in the same spot while shipping still gets variety from one mechanism. (SWEngGames; GameMath; PolishedGameDev; PCGUnity)
- Treat all software RNGs as deterministic PRNGs you control, not true randomness — exploit that determinism for attract-mode demos, instructional replays, and regression tests. (PolishedGameDev)
- Drive procedural generation from a stored seed so the same seed reproduces the same content — you can then discard generated content and regenerate on demand. (PCGUnity)
- Keep the number of RNG calls identical between runs and gate randomness behind a fixed time-step accumulator — calling random a different count desyncs deterministic playback. (PolishedGameDev)
- Know that Unity's Random is a shared global singleton; use `Random.InitState(seed)`, a private System.Random, or a job-compatible value-type RNG for deterministic/parallel results. (BulletHell; ECSFundamentals)
- Make the game deterministic for replay/optimization/bug-repro: never change game state in rendering functions, avoid uninitialized data, approximate async events, and route ALL input (keyboard/mouse/joystick/network/time) through one system that records every frame — enables crash-repro (save the buffer even on crash), replays, and lockstep multiplayer (transmit input, not state). (GPGems2; PolishedGameDev)
- Keep simulation in one controlled array with deterministic ordering and resolve pull/conflict ordering explicitly — OS threads schedule erratically, and undefined resolution order makes the simulation non-reproducible. (SWEngGames; GameMechanics)
- Run all physics on a fixed timestep in FixedUpdate, separate from render cadence — physics integration is deterministic and frame-rate-independent only when force is applied on the same fixed cadence the solver steps at. (GameDevUnity; CertGameDev; CertProgrammer)
- Watch for state leaking across runs when fast-iteration mode skips full reset — disabled domain reload persists static fields/subscriptions between sessions; toggle it back on as a diagnostic when second-run behavior differs. (ECSFundamentals)

### Testing Systems & Verification Strategy
- Test at every stage, not just the end — embed QA inside the sprint loop and verify content/systems as they are built; bugs caught early are far cheaper than bugs masked late. (QATesting; LevelDesign)
- Gate "done" on independent verification — a feature is not done until both its owner and QA sign off; gate completion on verification, not the author's word. (QATesting)
- Verify in stages and know which stage you're in: functionality first (a stranger plays start-to-finish unaided), then internal completeness (no loopholes/dead ends), then balance, then fun, then accessibility — don't try to fix everything at once. (GDWorkshop; QATesting)
- Make functionality testing the baseline — actual results must match expected behavior for every feature (selectable/playable character, a load that actually loads, a completable game, nothing crashable); fun is out of scope here, correctness is in scope. (QATesting)
- Stabilize the code before balancing — crashes and freezes make balance measurement impossible; you can't tune a system on an unstable base. (QATesting)
- Exercise negative and edge cases, not just the happy path — design "edge negative" cases that mimic how real players push the system; obvious positive cases catch only surface bugs. (QATesting)
- Never reproduce a feature the way the developer demoed it — use the keyboard if they used the mouse, take the other path; flexibility and high-reaction-time testers surface subtle interaction bugs. (QATesting)
- Rotate testers across areas and introduce fresh playtesters continuously — familiarity hides bugs and veteran skill masks first-time difficulty; verify critical paths with more than one person. (QATesting; Challenges)
- Know each genre's weak spots and weight verification there — bugs are genre-specific (verify every puzzle multiple times in adventure/horror, nav/pathing in shooters); faulty nav is the top immersion-breaker, so treat path correctness as a hard QA gate. (QATesting; LevelDesign)
- Verify progression cannot dead-end — a progression break (can't open the door to the next area) halts the player while the system runs; ~99% are scripting failures, and numerous full playthroughs are the only reliable detector. (QATesting)
- Guard against progression deadlocks from consumable keys/resources by providing renewable sources (Zelda's replenishing pots) — running out of the gating resource softlocks the player. (GameMechanics; PCGUnity)
- Verify alternate paths as rigorously as the main path — in open systems, interlocking side quests and customizable stats create insidious cross-dependencies where the worst bugs hide. (QATesting)
- Build and verify systems incrementally with debug-log stubs before adding real logic — confirm the input→method→manager path end-to-end first, then swap in behavior; isolates wiring bugs from logic bugs and localizes each failure to the change that caused it. (Build3DUnity; BulletHell; CSharpForUnity; Platformer2D; GameDevUnity; IntroGameDesign)
- Test AI/systems in isolation via dummy implementations and debug menus (a dummy animation controller that completes/fails orders, a scripting harness issuing the AI's own orders, manual decision drivers) — proves the logic with animation/other layers removed from the equation. (GameAIPro2)
- Make AI "not stupid" before making it smart, keeping code simple and modular to isolate the glitches (wall-running, twinning, wall-staring) that make characters look dumb — maintainability directly buys robustness and the ability to remove failed experiments cleanly. (GameAIPro2)
- Validate guessed model/stochastic parameters with a fast standalone test app across many timescales — don't trust hand-tuned queue rates or influence constants without observing their behavior. (GameAIPro2)
- Verify a merge is semantically correct, not just syntactically combined — naively accepting both sides can apply movement twice; hand-edit to the intended single result. (VersionControl)
- Verify min-requirement/collision matrices from authoritative docs rather than guessing, and disable layer pairs that never collide (sanity-check every pair) — system behavior has nonobvious prerequisites. (Unity2DCookbook; Unity5Opt)
- Use a frame debugger to verify a multi-pass system's ordering and correctness, not just its cost — confirm passes run in the intended sequence and nothing renders too early/late. (Unity6Opt)
- Assume no software is flawless and design/test for robustness, not a zero-bug ideal — stable products merely mask defects so well they're hard to find. (QATesting)

### Soak, Autorun, Stress & Combinatorial Testing
- Soak/stress-test by leaving the system running for days — memory leaks and rounding/accumulation errors are invisible in short sessions; robustness includes time, not just inputs. (QATesting)
- Build an autorun/"plays-by-itself" mode plus randomize-parameter and God-mode hooks for automated black-box testing — lets the game stress-test itself and reach late-game scenarios without a human at the controls. (SWEngGames)
- Automate the repetitive, deterministic checks (stress, load, install, permutation, content/appearance) and reserve humans for judgment — automation can't measure fun, finesse, or how to make a system better. (QATesting)
- Demand automated/exhaustive verification for combinatorial systems — in a deep upgrade economy (Forza), check each upgrade's effect AND that no upgrade conflicts with any other; the permutation count exceeds human capacity, so script it. (QATesting)
- Verify every economy item alone, then in combination — a new sword must add the damage it claims and a new engine upgrade must be felt; test the converter in isolation and the full interaction matrix. (QATesting)
- Use dynamic tools for buffer overruns, memory leaks (every alloc needs a dealloc, even in GC languages), and coverage to prove tests exercise the whole code base. (PolishedGameDev)
- Ship a debug memory manager active only in debug builds that tracks leaks (entries left at exit), bounds violations (sentinel padding like 0xDEADCODE), allocation-type mismatches, and actual-vs-allocated usage — guides optimal memory footprint and catches delete/delete[] mismatches that skip destructors. (GPGems2)
- Verify physics as a whole subsystem feeding gameplay and animation — a physics defect cascades, so verify breakables (must break, must not float) and dynamic behavior (a struck object must decelerate and stop, not drift forever). (QATesting)

### Regression Prevention & Re-Verification
- Regression-test by re-hunting old, supposedly-fixed bugs against the latest build a few times a week — fixes routinely spawn new defects, so re-verify previously-closed bugs continually. (QATesting)
- After any nontrivial mechanic change, playtest the WHOLE game, not just the one system — one tweak ripples through interlocking systems (over/underpowered spells, dominant professions). (Challenges)
- Re-run data collection and net training after late-game tuning changes the world's behavior — a trained net silently degrades when the behavior it learned from shifts. (GPGems2)
- Read-modify-write existing import/build settings (read → mutate → set) rather than constructing fresh ones — preserve fields you don't intend to change to avoid unexpected regressions. (EditorScripting)
- Keep a continuous version-controlled history of system states (including import/processing settings under version control) so any change is traceable to when, by whom, and why — provenance is what makes regressions diagnosable, and rollback makes risky tweaks cheap. (VersionControl)
- Drive builds from source control with build config (version/bundle id) set from code, not manual uploads or hand-set fields — reproducible, repo-tied builds keep behavior consistent and prevent drift between builds. (CertGameDev; EditorScripting)
- Version, name, and timestamp every authored asset so any iteration can be recovered — new tool/plugin versions silently break old settings, so reproducible asset history is part of maintainability. (QATesting)
- Pin the exact build version to every bug report and write reproduction steps precise enough to replay on another machine across time zones — one missing detail or wrong version makes a bug bounce back as "can't reproduce." (QATesting)
- Drive a defined bug lifecycle state machine (Open → Assigned → Resolved → Verified → Closed) with sign-off on every close — testers re-run original plus alternate steps; a false "verified" can cost millions in the field. (QATesting)

### Balance Verification & Live Tuning
- Treat imbalance as a bug, not a matter of taste — no side (human or AI) and no option should dominate; anything "not by design" is a defect, and every distinct option must pull its weight and stay viable. (QATesting)
- Make difficulty a monotonic curve and verify EVERY difficulty setting, not just normal — "easy" not too easy, "hard" not too hard, "medium" a gradual rise. (QATesting)
- Apply "purity of purpose" — give each component a single clearly-defined mission so tweaking one element changes one aspect, making balancing methodical instead of a guessing game. (GDWorkshop)
- Hunt and kill dominant/degenerate strategies — once a dominant strategy is found the game is solved and dies; they hide in emergent tool interactions and players will find them, so rebalance to restore meaningful choice. (AoGD3; DesigningGames)
- Use the doubling/halving method and guess exact values before testing — big swings (not ±10%) make a variable's effect felt immediately, and each precise guess+result sharpens future estimates. (AoGD3; AoGD2)
- Plan to balance from the start: expose tunable, ideally runtime-changeable parameters and keep tuning post-ship — half of dev time goes to balancing and tiny values matter (Halo sniper 0.5→0.7s). (AoGD2; AoGD3; SWEngGames)
- Hoist every tunable into a named, type-checked constant (statics over #define / magic numbers; share a preprocessor header between code and data) so values can't drift out of sync and can change without wide recompiles. (SWEngGames; GPGems2)
- Verify PRNGs and shuffles are actually uniform — biased shuffles silently favor outcomes and break balance. (Challenges)
- Don't let players self-balance core values (conflict of interest trivializes challenge) — offer difficulty levels as the safe exception. (AoGD3; AoGD2)
- Use dynamic/rubber-band difficulty cautiously and ideally invisibly — adaptive scaling lets players credit their own skill, but experts decode and exploit it (play badly for an easy stretch) and it spoils a fixed-challenge mastery; prefer subtle mechanics (MarioKart trailing-player odds) over crude speed clamps. **When it flips:** in competitive/high-skill games, balance at the top of the range explicitly and avoid silent adaptation entirely. (AoGD3; AoGD2; GDWorkshop; Challenges; UnityAI; GameMechanics; DesigningGames)
- Watch playtesters for systemic warning signs and map each to a fix — bored (too much luck / too few decisions), bored off-turn (low interaction), confused (too complex), one player dominating (too skill-heavy). (Challenges)
- Re-derive dependent variables whenever you resize a system — a bigger grid changes unit count, time, and contention; scope changes cascade through coupled systems, so balance proportionally. (GDWorkshop)

### Telemetry as Verification
- Instrument live games to collect play data (Blizzard's Battle.net race-vs-race win rates by map) and use stats to distinguish real imbalances from perceived ones before patching — pair the data with designer intuition and direct feedback from top players. (GDWorkshop; CertGameDev; Challenges)
- Use metrics for fine-tuning beyond playtest resolution (Half-Life position/health/death graphs, fighting-game win-rate sampling) — they reveal sub-threshold imbalances and rare edge cases at scale, and engineer clever metrics for hard-to-observe data (a "I just saw lag" button + recorded match movies). (DesigningGames)
- Track playtest outcomes in tables (probability, progression, logged results) and feed them back into tuning — telemetry-informed tuning beats guessing. (IntroGameDesign; Challenges)
- Expect to keep balancing after launch and enter beta intentionally incomplete (~90% of units) — a million players at higher skill and volume surface imbalances and exploits no internal test predicted, but distinguish a true flaw from natural metagame evolution that self-corrects. (GDWorkshop)
