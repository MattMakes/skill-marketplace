# Simulation Loops, Scheduling, Lifetime & Performance

## Simulation, Update Loops, Scheduling, Spawning & Lifetime

### The Game Loop
- Structure every game as one continuous real-time loop (input → AI/logic → render → sync), not event-driven sequential code — games are simulations that "make the movie as they go." (Tricks3D)
- Identify and design around the core game loop — the repeated series of player actions — as the spine every other system feeds and reinforces. (CertGameDev)
- Structure the whole runtime flow as init systems → load config/data → set default state → main loop → cleanup → release systems — skipping cleanup leaves the system in a bad state. (RPGDirectX)
- Split the per-frame loop into pre-frame, per-frame, and post-frame stages (timing/input, update/render, sync/present) — distinct phases keep timing and rendering responsibilities clean. (RPGDirectX)
- Wrap every engine subsystem in its own class with a uniform lifecycle (Init/Create, per-frame Update/Render, Shutdown/Free) — predictable composition and teardown across all systems. (RPGDirectX)
- Provide a reusable application framework that owns window creation, engine init, the per-frame loop, and shutdown — start new projects from a base instead of retyping boilerplate. (RPGDirectX)
- Compose the macro game loop from scenes wired by data-driven transitions (Menu → Level1 → Level2 → Menu) — a small explicit scene graph reflects start/play/progress/restart rhythm. (Build3DUnity)
- Reuse the engine's solved game-loop infrastructure (collision, physics, pathfinding, particles, draw batching) so you rebuild systems, not infrastructure. (IntroGameDesign)

### Frame-Rate Independence & Delta Time
- Make all movement, animation, and physics time-based by multiplying rates by elapsed/delta time, never per-frame — entities move at the same real speed regardless of frame rate (100fps vs 30fps machines), and frame-locked motion breaks across hardware. (RPGDirectX; Tricks3D; IntroGameDesign; Unity2DCookbook; Build3DUnity; BulletHell; Platformer2D; GameDevUnity; ECSFundamentals; VersionControl)
- Drive motion by real elapsed time dt, never a fixed per-frame constant — `pos += dt*vel` keeps apparent speed identical across slow and fast machines; `pos += vel` makes the game unplayable on a faster CPU. (SWEngGames)
- Time all flip-book/animation and lifetime logic off elapsed seconds, never off update/cycle counts — "never do anything on the basis of cycle counts, always use the time." (SWEngGames)
- Respect a global time scale: setting timeScale to 0 freezes delta-driven motion for a clean pause; use unscaled delta time for UI/pause-menu animation that must keep running while paused. (GameDevUnity)
- Guard against extreme delta time (tiny first-frame values, huge hitches): never divide by delta without a sanity check, or results blow up. (GameDevUnity)
- Trigger frame-synced sounds on the rising edge (frame A→A+1), never "on frame A" — at differing frame rates the animation system may render the same frame twice. (PolishedGameDev)

### Fixed vs Variable Timestep
- Decouple physics from frame rate with a fixed timestep, applying forces/velocity/rigidbody writes only in the fixed-step loop (FixedUpdate) — variable timesteps produce inconsistent collisions across machines, replays, and multiplayer, and physics integration is deterministic only on the fixed cadence the solver steps at. (Unity5Opt; Unity2DCookbook; Build3DUnity; GameDevUnity; CertGameDev; CertProgrammer)
- Clamp dt to a max (~0.1s) — huge timesteps make motion jerk and entities teleport through walls; lie and cap it rather than simulate a giant leap. (SWEngGames)
- Cap physics catch-up with a maximum allowed timestep to prevent the "spiral of death" where each long physics update spawns another — if you hit the cap regularly, optimize physics rather than raising it. (Unity5Opt)
- Budget physics processing per step in both best and worst case — heavy fixed-step work steals from rendering and gameplay and stutters the frame rate. (Unity5Opt)
- Tune fixed-step frequency early and rarely, with heavy testing — higher frequency catches fast collisions but costs CPU; lower frequency frees CPU but lowers the max trackable velocity, and it's coupled to all fixed-step logic. (Unity5Opt)
- Smooth visible motion between physics steps with rigidbody interpolation when rendering is faster than the physics step — and pick one fix (same-loop OR interpolation), not both. (Build3DUnity; BulletHell; Platformer2D)
- Gate randomness behind a fixed time-step accumulator and keep RNG call counts identical between runs — calling random a different number of times (twice at 0.1s vs once at 0.2s) desyncs deterministic playback. (PolishedGameDev)
- Watch the accumulator pitfall: repeatedly adding a tiny delta to a large running total silently adds zero once exponents diverge — rescale or batch small contributions. (GameMath)
- Synchronize to a target frame rate (30 fps min, 60 ideal) with timing/wait, capping the loop — uncapped frame rate is unusable, burns all CPU, and is wasted past ~60 since screens can't update faster. (Tricks3D; ProgramArcade; PolishedGameDev)
- Treat the frame-rate cap value as the governor, not a sleep — raising it makes the game run faster, lowering it slower; tune it as a system knob. (ProgramArcade)
- Target a consistent frame rate and never let new code/data drop below it — fix the offending code/data immediately before continuing other work. (PolishedGameDev)
- Treat the target frame rate as a continuous, enforced production constraint, not a deferred end-of-project task — serious performance issues found in the last two months may be too structural to fix. (QATesting)
- Choose frame rate by need: 60 fps for high-skill rapid-input shooters/racers/fighters, 30 fps for art/narrative/turn-based; treat control latency (3–4 frame pipeline minimum) as a system constraint and evangelize for the target against per-frame-budget pressure. (DesigningGames; QATesting)

### Update Ordering & Script Execution Order
- Order each timestep deliberately (Adjust → Listen → Move → Update → Collide → Clean-up → Animate → Draw) — wrong order produces order-dependent behavior; this order makes player input feel immediate and processes deaths/births before drawing. (SWEngGames)
- Make the master step() non-virtual and forbid overriding it — the update ordering is delicate, so games can't accidentally break it. (SWEngGames)
- Separate update loops by timestep/role: per-frame gameplay/input in the variable loop, physics in the fixed loop, post-movement/camera-follow in a late loop — matching each subsystem to the correct cadence avoids jitter and one-frame lag. (CertGameDev; Unity2DCookbook; Build3DUnity; GameDevUnity; AdvancedCSharp)
- Use the engine's lifecycle hooks deterministically: self-contained setup in Awake, cross-object references in Start (others have finished Awake), per-frame logic in Update, cleanup/unsubscribe in OnDestroy — never call these yourself. (GameDevUnity)
- Resolve same-frame init/fire races explicitly with Awake-vs-Start, explicit init order, or guards — undefined order between objects causes intermittent, hard-to-find bugs. (IntroGameDesign; PatternsUnity6)
- Use Script Execution Order only for genuinely time-sensitive systems (e.g. audio); needing it to fix logic usually signals fragile tight coupling. **When it flips:** for complex genuine ordering needs, assign priorities visually via Project Settings rather than scattering attributes. (Unity5Opt; PatternsUnity6)
- Store import/processing settings including script execution order with the asset under version control — system behavior depends on these, so they must be reproducible across machines. (VersionControl)
- Order guard checks correctly within a tick (clamp/reset relative to the input that mutates the value) — placement of the check vs the mutation determines whether the reset ever triggers. (CertProgrammer)
- Disable a one-shot system at the very TOP of its update, before doing the work — disabling at the bottom lets it run one extra frame and double its effect (e.g. spawning twice the entities); self-disable-vs-side-effect order is load-bearing. (ECSFundamentals)
- Let an ECS framework auto-discover and schedule systems into named phases (e.g. a Simulation group) rather than hand-wiring update calls per object — central scheduling enables intentional, inspectable ordering, grouping, and parallelism the hand-wired approach can't. (ECSFundamentals)
- Reuse one shared system across all entities of a type instead of per-object update scripts — one job over N entities beats N independent update loops for performance and maintainability. (ECSFundamentals)
- Provide a systems view showing execution order, group membership, timing, and live entity counts — confirm systems run in the expected order and find where cost concentrates. (ECSFundamentals)
- Keep update loops doing one clear thing per object; route per-frame movement, spawning, and bounds-checking through dedicated scripts/helper functions — overloaded update methods become unmaintainable. (IntroGameDesign; Unity2DCookbook)
- Give the render loop and the update loop separate RNGs — sharing one with a variable render-per-update ratio makes the generator's state indeterminate and breaks replay/multiplayer. (GPGems2)
- Route all input (keyboard, mouse, joystick, network, time) through one input system that records every frame — enables bug repro, replays, optimization measurement, movie capture, and lockstep multiplayer (transmit input, not state). (GPGems2)
- Reset all transient per-frame state flags (culled, clipped, backface) at the start of each frame — stale flags from last frame corrupt this frame's pipeline decisions. (Tricks3D)

### Scheduling & Staggering Updates
- Stagger periodic systems so timed events don't all fire on the same frame — randomize wait times, spread coroutine starts across frames, or cap invocations-per-frame in a master scheduler; otherwise N objects sharing a frequency spike together. (Unity5Opt)
- Schedule rules/periodic work by a frequency timer (e.g. once per game-day, per-rule overridable) rather than every frame — only run work when it's due. (GameAIPro2)
- Schedule periodic randomized state changes via a per-entity "next-change timestamp": compare elapsed time against the stored time, then roll a new value and a new future timestamp — cheap, stateless-per-frame variety. (ECSFundamentals)
- Cap, timeslice, or round-robin costly per-character queries and restrict expensive systems to the few agents that need them (e.g. one navigation-map pathfind per frame). (GameAIPro2)
- Distribute long calculations (A* pathfinding) across several frames by saving/resuming state — lowers per-frame load; works for any algorithm of unspecified duration. (GPGems2)
- Keep behavior-tree/AI evaluation asynchronous so it never blocks the main loop — spreading evaluation across frames keeps frame time stable when many agents think at once. (UnityAI)
- Use coroutines for logic that unfolds over time (spawn waves, attack bursts, timed flashes, fades, delays, multi-step spells) instead of polling timers in Update — straight-line timed code on the main thread with full API access and no threading hazards. (BulletHell; IntroGameDesign; CertProgrammer)
- Suspend coroutines with the engine's typed wait objects (`WaitForSeconds(n)`), not raw numeric yields, so timing is explicit and correct. (CertProgrammer)
- Express recurring vs one-time scheduling declaratively: a repeating-invoke primitive for periodic ticks, a single timed invoke for one-shots — separate "what to call" from "when," and use `nameof(Method)` over string literals for compile-time safety. (CertProgrammer; PatternsUnity6)
- Use turn/coroutine scheduling for ordered turn-based updates (player turn → enemy turn) — a placeholder enemy turn from day one keeps the turn loop working before enemies exist. (PCGUnity)
- Build queues, schedulers, thread pools, and job systems on commands — a command packages computation as a first-class object that can be invoked later, on another thread, far from where it was created. (HeadFirstPatterns)
- Funnel incoming network callbacks into a message queue (ring buffer) and process a capped number per frame — never process network data inline; the server never bogs down on bursts. (RPGDirectX)
- Use a Queue when items must be processed strictly oldest-to-newest (FIFO) — command sequencing, event scheduling, input/action buffering. (AdvancedCSharp)
- In ECS, schedule a job once and let it fan matching entities across worker threads, declaring the tightest access (read-write/read-only/by-value) per parameter so the scheduler runs more jobs in parallel — and pass per-frame inputs (delta, elapsed, RNG seed) in as data since jobs can't reach global/static APIs. (ECSFundamentals)
- Keep simulation objects in one controlled array, not one-thread-per-object — OS threads aren't truly parallel and schedule erratically; an array gives deterministic, reproducible ordering. (SWEngGames)
- Use an editor update tick only for genuinely asynchronous needs (waiting on preview generation) and short-circuit it once satisfied — don't burn the tick re-doing completed work. (EditorScripting)

### Simulation Level-of-Detail / Update Frequency by Relevance
- Run full simulation only on relevant objects (visible/near-player/active), use simplified or no simulation elsewhere, and wake objects on force/collision — but manage the discontinuities (don't freeze a falling object mid-air) so transitions stay invisible. (GameMath)
- Apply LOD to AI: scale processing frequency by distance to camera/action, simplify or swap to cheaper behaviors off-screen (full IK on-screen, dummy state tracking off), and represent many distant agents with one aggregate simulation — get away with less work without the player noticing, and scale back if it shows. (GPGems2; GameAIPro2)
- Favor player perception over simulation accuracy, but bound it by plausibility — halve hearing for offscreen distant NPCs to feel fair, yet keep around-the-corner NPCs responsive enough to stay believable. (GameAIPro2)
- Set the abstraction/scope/level-of-detail of a model intentionally — model only the mechanics that matter; abstraction is a design choice, not an accident. (GameMechanics)
- Carry per-entity LOD through data resolution (e.g. steering interest/danger maps as low-res arrays) so detail scales by map resolution per entity. (GameAIPro2)
- Treat AI as a budgeted citizen sharing the frame with rendering, physics, audio, and animation — cap its cost to hit a steady frame rate alongside everything else. (UnityAI)
- Exploit the physics sleep system but guard against waking storms — sleeping objects cost almost nothing, but islands of touching sleepers wake in chain reactions causing CPU spikes; despawn/lock settled objects and avoid per-frame forces that prevent sleep. (Unity5Opt)
- Throttle active audio with a pooling/management system that caps simultaneous clips and reuses idle sources — each active source costs CPU. (Unity5Opt)
- Support dynamic scalability when player count is variable — scale spawned creatures, items, and gold to the number of players present so a zone stays competitive, never trivial or a slaughter. (Challenges)
- Periodically re-check for a higher-priority runnable behavior and preempt the active one — otherwise a long-running behavior blocks timely response; the preempted behavior's cleanup restores a clean state. (GPGems2)

### Spawning Systems
- Centralize dynamic creation (enemies, pickups, projectiles, effects) through dedicated spawner systems rather than hand-placing — runtime object generation is everywhere; a uniform spawn path keeps it manageable and owns when/where things appear plus the runtime references they need. (IntroGameDesign; BulletHell; ECSFundamentals)
- Spawn all runtime content from prefabs/templates (data + component templates), authored once and instantiated many — centralizes definition so balance edits propagate everywhere and configs travel between scenes. (IntroGameDesign; BulletHell; CSharpForUnity; GameDevUnity; ECSFundamentals)
- Drive spawning from data: a spawner component/variable holds the prefab reference, count, frequency, and offsets, read at spawn time — data-driven config scales difficulty and density by tuning numbers, with no code changes. (IntroGameDesign; PCGUnity; ECSFundamentals; CSharpForUnity; PatternsUnity6)
- Distinguish definition (the template) from instance (ID, current stats, AI, position) — one definition spawns many tracked instances. (RPGDirectX)
- Fully configure spawned objects before they go live: set position/rotation/scale at spawn, reset transforms to known defaults, and snap to configured start state — so instances spawn without hidden offsets that corrupt scripted behavior. (Unity2DCookbook; Platformer2D)
- Inject runtime-only references (like a pool created at startup) into spawned objects via an Init method called right after instantiate — the editor can't assign a runtime object, so the spawner passes it post-spawn. (BulletHell)
- Replace repeated manual spawn calls with a loop the moment a pattern repeats, refactoring the spawn action into its own function first — seven hardcoded calls is unmaintainable; a `for` loop over a configurable count is scalable, and the loop index drives spawn variation (the seed of procedural layout). (CSharpForUnity)
- Parameterize spawn counts and spacing instead of hardcoding — the same system produces a dense row or a sparse line by data alone. (CSharpForUnity)
- Schedule delayed one-shot spawns with a timed invoke carrying both method and delay — separate "what to call" from "when" so spawn timing is data, not control-flow. (CertProgrammer)
- Convert one-shot spawn systems to self-disable after running once — prevents a per-frame update from spawning indefinitely. (ECSFundamentals)
- Randomize spawn intervals instead of a fixed tick — variable rhythm feels organic rather than mechanical. (BulletHell)
- Reparent spawned instances under a holder transform — keeps the hierarchy organized and lets you activate/deactivate or destroy a whole generated structure in one operation. (PCGUnity)
- Co-locate a spawner and the pool it feeds on one object — centralizes the spawn system and guarantees the reference exists. (BulletHell)
- Spawn on a ring (normalized random circle vector × radius) rather than filling the disc — keeps spawns a fixed distance from center while randomizing direction, so entries feel unpredictable but never appear on top of the player. (BulletHell)
- Know your RNG's bounds semantics (float Range inclusive both ends, integer Range max-exclusive) and prefer engine-integrated RNG for gameplay — tune spawn/stat ranges to the actual distribution. (CertProgrammer; BulletHell)
- Treat spawn point + spawn orientation as a first-class system — the spawn frame is the player's first read of state and sets tactical footing; constrain spawn-facing toward a landmark/objective/pickup and never face a wall (wasted reorientation is fatal in PvP). (LevelDesign)
- Make spawns consistent with world/story continuity across map transitions, and tie environmental spawners to diegetic set dressing that justifies them — preserves world coherence and hides the seam. (LevelDesign)
- Spawn the next procedurally-generated piece relative to the player's position/direction so a reachable target always exists — guarantee solvability and never generate an impossible gap. (Unity2DCookbook)
- Generate to an intermediate data structure first, then realize it by spawning prefabs — separating the generator (abstract data) from the builder (visuals) makes the system testable, seedable, and swappable without touching spawn code. (PCGUnity)
- Tag logic-only entities (spawners, singletons, controllers) as needing no spatial data — strips transform overhead from entities whose world position is irrelevant. (ECSFundamentals)
- Use a child transform as a spawn/attachment point rather than hardcoding an offset — animate the child to keep the spawn point visually correct across poses. (BulletHell)
- Use the Singleton pattern only for true global managers (game state, spawner, score), enforcing uniqueness in Awake (destroy the duplicate) and lazily creating on first access — avoids overwrite races and static-init-order crashes. (IntroGameDesign; SWEngGames; PatternsUnity6; ECSFundamentals)

### Factories
- Centralize object creation in a factory that maps a type request to the right concrete subclass/prefab/configuration — adding a new type touches one place, callers stay decoupled from concrete types, and a Simple Factory pulls scattered `new` statements into one spot. (IntroGameDesign; HeadFirstPatterns; SWEngGames; GPGems2)
- Pair each abstract interface with a factory that constructs the concrete type — callers include only the interface + factory headers, never the implementation, cutting recompiles and blocking illicit downcasts. (GPGems2)
- Let an entity's constructor read its own class-specific params directly from the level-file stream, loading each flyweight on first request and cloning (Prototype) for further instances — the factory needs zero knowledge of subclass internals. (GPGems2)
- Use Factory Method (inheritance — subclasses decide the product) to vary one product; use Abstract Factory (composition — handed a factory) to vary a coordinated family of related objects, e.g. matched terrain/props/enemies for a theme. (HeadFirstPatterns)
- Treat the factory as the standard tool for honoring Open-Closed and Dependency Inversion at the creation boundary — flag creation smells (a variable holding a concrete-class reference, a class deriving from a concrete class) and restructure toward a factory. (HeadFirstPatterns)
- Relate pooling to the Factory concept but keep the distinction: pooling reuses existing instances, a factory creates new ones — choose reuse when churn (not novelty) is the cost. (PatternsUnity6)
- Split a god-object manager into focused services (LevelLoader, ScoreManager, EnemySpawn) instead of one manager doing loading + score + spawning — separate concerns let you change one without disturbing others. (PatternsUnity6)

### Object Pooling
- Pool any object that spawns and dies frequently (bullets, projectiles, particles, enemies, platforms, effects) instead of instantiate/destroy each time — pay the allocation cost once at startup, then toggle active state; repeated alloc/dealloc causes GC spikes, frame hitches, and memory churn, worst on mobile and dense scenes (effectively mandatory on mobile). (BulletHell; Unity5Opt; PatternsUnity6; CertProgrammer; Unity2DCookbook; Platformer2D; ProgramArcade)
- Understand the real cost being avoided: instantiate clones the prefab + children, allocates objects, registers with the scene, and runs Awake/OnEnable; destroy queues removal and GC — at dozens/hundreds per second this becomes allocation spikes, GC stutter, and frame-time hitches. (BulletHell)
- Pre-spawn the expected peak count of each prefab at scene init (inactive) — shifts instantiation cost off the gameplay-critical path to load time, the whole point of the system. (Unity5Opt; PatternsUnity6; CertProgrammer)
- Despawn by deactivating (SetActive(false)) rather than destroying — one call disables collider, rigidbody, rendering, and most subsystem interaction while keeping the instance in memory for reuse. (Unity5Opt; Platformer2D; PatternsUnity6; CertGameDev)
- Reset ALL per-life state on reuse (velocity, angular velocity, hit-flags, timers) so a recycled instance behaves identically to a fresh one — stale state from the previous life causes subtle reuse bugs, and disabling a rigidbody zeroes its velocity so motion must be re-applied or recycled objects spawn dead-on-arrival. (Unity5Opt; BulletHell)
- Reset stateful poolable state during Despawn, not Spawn — spawn-time invocation order across a GameObject's components is undefined, so resetting on spawn can clobber another component's intentional init. (Unity5Opt)
- Reposition pooled objects on retrieval — reused instances retain the transform from their last active state, so spawn position must be reapplied (instantiate used to do this implicitly). (PatternsUnity6)
- On despawn, explicitly stop coroutines and deregister from custom systems (message bus, etc.) — SetActive(false) does not stop coroutines or custom-system registration. (Unity5Opt)
- Make pooling generic over a poolable contract (e.g. New() for first creation, Respawn()/reset for recycled state) so any type fits one pool implementation. (Unity5Opt)
- Keep poolable components self-contained and minimize components that reach across and mutate siblings — cross-component pooling logic is a top source of confusing bugs. (Unity5Opt)
- Back the pool with fast keyed structures (Dictionary<prefab,pool> for spawn lookups, Dictionary<gameObject,pool> for despawn lookups) and cache each instance's poolable-component array at instantiation — so the system scales to thousands of prefabs without iterating pools or acquiring components at runtime. (Unity5Opt)
- Right-size pools per prefab through testing — too few forces runtime allocation (defeating the system), too many wastes memory; instrument inactive-time to detect over-prespawning. (Unity5Opt)
- Preallocate and cache frequently created/destroyed objects via a template cache / free list instead of constant new/delete, maintaining stack discipline to keep the cache contiguous; override global new/delete to redirect small allocations into preallocated blocks and avoid heap fragmentation. (GPGems2; Tricks3D)
- Recycle off-screen/collected objects back into play (reset to a fresh position) instead of destroying and reallocating — keeps a constant object count and steady performance. (ProgramArcade; Unity2DCookbook)
- Track recycled objects in a small fixed array/window (e.g. 3 background panels, prev/actual/next platform) and translate them rather than create unbounded — constant memory regardless of run length. (Unity2DCookbook)
- Use object pooling/reuse (Free to reset without full Shutdown) for repeatedly-used controllers and meshes — avoid teardown/reinit churn between uses. (RPGDirectX)
- Leverage existing Asset Store / library pooling solutions for this well-trodden system — but build one from scratch once to understand the engine internals well enough to extend it. (Unity5Opt)

### Object Lifetime Management & Cleanup
- Make objects own their own lifecycle end: each entity decrements its own counter, runs its own off-screen/out-of-bounds recycling, and calls destroy on itself — rather than an external manager reaching in; award/notify before destroying so side effects (score) aren't lost. (GameDevUnity; ProgramArcade; CSharpForUnity)
- Have spawned objects self-destruct when off-screen or out of bounds — leaked objects accumulate and degrade performance. (IntroGameDesign)
- Give transient entities (bullets, fragments, projectiles) a fixed lifetime so they self-expire — bullets older than ~3s die even if they never hit anything, returning to the pool and capping the active population so off-screen objects don't accumulate. (SWEngGames; BulletHell)
- Have pooled objects release themselves on every exit path — both natural expiry (lifetime timer) and impact — guaranteeing return to pool with no leaks. (BulletHell)
- Cap how many of a thing one shooter keeps active — shooting beyond the cap recycles the oldest rather than blocking the gun, so the player is never left defenseless. (SWEngGames)
- Never instantly destroy a damaged entity — turn on a dying flag / fixed lifetime and play a death act (shrink, shatter, explosion) before delete; "things shouldn't happen abruptly." (SWEngGames)
- Defer all add/delete/spawn/replicate structural changes to a service-request queue drained once per cycle at a safe point — never mutate a collection you're iterating. (SWEngGames)
- Decouple effect lifetime from the object that triggered it: spawn a self-destructing effect/audio prefab at the dying object's position so the trigger object can vanish immediately, and let the effect terminate itself (destroy when audio finishes / on state-machine exit) so no external lifetime manager is needed. (Unity2DCookbook; UnityAI)
- Centralize destruction/secondary-effect triggers at well-defined lifecycle points (projectile-hit, explosion-end) — natural hooks for damage, particles, score; keeps effect wiring discoverable and extensible. (UnityAI)
- Toggle whole entities with SetActive — activation is the clean lifecycle switch for spawning/despawning and pooling, distinct from disabling a single component. (CertGameDev)
- Run per-state logic via lifecycle hooks (enter for setup, update per frame, exit for cleanup like resetting rotation/clearing flags) — keeps state code self-contained. (UnityAI)
- Define and enforce standard lifecycle entry points across all objects (constructor, startGame, startLevel, update, draw, postDraw) with consistent signatures — inheritance or discipline guarantees a common vernacular and complete coverage. (PolishedGameDev)
- Subscribe in OnEnable and unsubscribe in OnDisable — ties subscription lifecycle to active state and prevents events firing into disabled/destroyed targets (critical for pooled objects). (PatternsUnity6)
- Load an object's assets in its constructor at game-load time; if created mid-game, have another object preload its assets — prevents memory fragmentation and mid-game allocation/GC stalls. (PolishedGameDev)
- Clear structures to known defaults in constructors and on reset (flags FALSE, pointers NULL, counts 0) — predictable starting state avoids garbage-driven bugs. (RPGDirectX)
- Persist cross-scene runtime objects with DontDestroyOnLoad and small saved values with durable storage — choose by lifetime (in-memory continuity vs durable across sessions); guard DontDestroyOnLoad singletons with an Awake duplicate check or a scene reload spawns a second survivor. (CertProgrammer; PatternsUnity6)
- Be cautious with live mid-game lifetime/setting changes — changing respawn to 30s while in-flight objects hold 18s, or shrinking a TTL below its current value, manifests as phantom bugs; validate config with typed accessors and min/max clamping so a 0-second respawn never ships. (PolishedGameDev)

### Allocation & GC Discipline in the Loop
- Design for GC avoidance first, concealment second — mark-and-sweep cost scales with heap size and can freeze gameplay; allocate little and control lifetime tightly. (Unity5Opt)
- Avoid per-frame allocate/free churn of transient objects: prefer arrays/fixed structures in hot paths, reserve a reusable storage pool and reset a count each frame, and avoid unbounded object growth — destroy/recycle spawned objects to keep frame cost stable. (IntroGameDesign; Tricks3D)
- Delete empty Update/Start/callback stubs — the engine hooks every declared callback and pays a native↔managed bridge cost per object per frame; thousands of empty Updates wreck the frame rate. (Unity5Opt)
- Prefer stack-allocated value types/structs for short-lived, scope-local data and data blobs passed between systems that don't outlive the scope — they deallocate for free at scope end and stay invisible to the GC. (Unity5Opt; GameDevUnity)
- Favor value-type, allocation-free, reference-free code in hot systems — the native compiler only optimizes a numeric, GC-free, reflection-free subset; staying inside it unlocks large speedups. (ECSFundamentals)
- Never read tag/name strings at runtime or build strings with +/+= in hot paths — use CompareTag (no allocation, validates against the tag table, catches typos), StringBuilder/string.Format for assembly, and avoid boxing value types — each duplicates strings/boxes on the heap and attracts the GC in callbacks firing every frame. (Unity5Opt; CSharpForUnity; Platformer2D)
- Avoid foreach over Mono generic collections and engine API calls that return arrays on hot paths — they heap-allocate an enumerator/array; call once and cache, and reuse large temporary work buffers instead of reallocating. (Unity5Opt)
- Ship a debug memory manager in debug builds (overload new/delete, log file+line, sentinel padding, record allocation type) to track leaks, bounds violations, and delete/delete[] mismatches — every alloc needs a matching dealloc, including in GC languages. (GPGems2; PolishedGameDev)
- Start with oversized static arrays to dodge allocation issues early, then move to dynamic allocation only once sizes genuinely vary widely — premature dynamism adds cost without payoff; don't build linked lists for simple fixed-size always-present data. (Tricks3D)
- In ECS/search code, preallocate node memory with a dirty bit for cheap init and avoid runtime allocation, storing operator sequences instead of full state copies; reuse one preserved working buffer to avoid alloc churn. (GameAIPro2)
- Micro-optimize hot update/timing paths (store reciprocals to multiply instead of divide, skip redundant re-Play if already playing) — small wins compound in per-frame loops running thousands of times per second. (PCGUnity)
- Clamp/Clean near-zero residual velocity, acceleration, and denormal values after integration — tiny residuals cause distracting micro-jitter, and denormals trigger slow assist microcode (10–100× slowdown) on some FPUs. (GameMath)

### Physics Integration in the Loop
- Treat physics state as an initial-value problem and prefer semi-implicit (symplectic) Euler as the default integrator — step velocity explicitly then position with the new velocity; it conserves energy, stays stable, is cheap, and adapts trivially to rotation. (GameMath)
- Prefer stability over correctness in games — a semi-implicit method that loses a little energy and damps to equilibrium beats an accurate method that spins out of control; avoid stiff springs that wreck explicit integrators. (GameMath)
- Derive motion by turning differential laws into per-step update rules (`accel = force/mass`, `vel += dt*accel`, `pos += dt*vel`) — treat force as input, position as output, and split the equations across phases (compute acceleration in update, integrate velocity/position in move) since acceleration can change from collisions/forces/input mid-step. (SWEngGames; GameMath)
- Handle dynamic fast/thin objects with swept-volume or path tests, not frame-by-frame static tests — objects moving more than ~half their thickness per frame tunnel through walls; trigger sweeping only when relative velocity warrants it. (GameMath)
- Decouple animation from frame rate by storing sparse keyframes and resampling at runtime, interpolating between samples — slashes memory and keeps playback frame-rate independent. (GameMath)
- Interpolate toward targets/headings rather than snapping, matching the primitive to the data: Lerp/MoveTowards/feedback-Lerp for positions and easing, Slerp for orientation along the sphere arc — and clamp or snap Zeno-style asymptotic lerps when "close enough" to avoid endless tiny updates. (IntroGameDesign; Build3DUnity; Platformer2D; UnityAI; CertProgrammer; GameMath)

## System Performance & Scalability

### Profiling Discipline (Measure First)
- Never optimize a system without profiler proof it is a bottleneck — premature optimization wastes effort, and a "simple" line can generate large machine code; profile before you touch anything and ask "will the user notice?" (Unity5Opt; Unity6Opt; Tricks3D; GPGems2; PolishedGameDev; IntroGameDesign; GameAIPro2)
- Drive every optimization as a measure-fix-measure scientific loop: define target metrics (FPS, memory, draw calls), record a baseline, change ONE variable, then re-measure to confirm the gain and surface trade-offs — without a recorded "before" you can't judge impact, and multi-change experiments make attribution impossible. (Unity6Opt; Unity5Opt; Tricks3D; PolishedGameDev)
- Form a hypothesis before each test and predict the outcome, then verify — turns each experiment into calibrated instinct; treat a surprising profiler reading as signal that reveals a hidden system cost, not as failure. (Unity6Opt)
- Profile against a standalone release build on the target device, not the Editor — Editor overhead (UI, debug hooks, ~376 vs 156 bytes per MonoBehaviour) and JIT/observer effects yield wildly unrepresentative data; always validate final numbers on target hardware, and compare Release-vs-Release / Debug-vs-Debug. (Unity5Opt; Unity6Opt; GPGems2; SWEngGames)
- Begin runtime measurements only after the system reaches steady state and account for the observer effect — Scene init (Awake/Start, physics/render warmup) distorts the first second, and the profiler itself adds CPU/memory cost; reproduce a suspected bottleneck under non-profiling conditions before committing a fix. (Unity5Opt; Unity6Opt)
- Run a pre-analysis checklist and reduce noise before reading data — verify the script is present the right number of times, minimize code changes, disable VSync (its WaitForTargetFPS spikes mask real CPU spikes), silence exception spam, deactivate irrelevant objects; most "bottlenecks" are setup mistakes. (Unity5Opt)
- Build profiling into the engine early as a real, low-overhead system (<5% enabled, <1% disabled) that is frame-based (per-frame counters, not accumulated averages), per-engineer customizable, and compiles out under an #ifdef — accumulated samples hide the frame-by-frame bottleneck shifts that characterize games; profile the profiler itself. (GPGems2; Unity5Opt; Unity6Opt)
- Instrument your own systems with custom profiler markers (BeginSample/EndSample) that compile out of release builds, wrapping each expensive section separately — without markers an entire update method reads as one opaque block; leave them in to re-profile later at zero runtime cost. (Unity6Opt; Unity5Opt)
- Use a relative timeline with benchmark bars (not absolute spike height), attribute cost across threads (main vs render), and switch to a hierarchical call-tree view to find the dominant subsystem — auto-rescaling axes make trivial spikes look threatening; only spikes crossing the FPS budget matter. (Unity5Opt; Unity6Opt)
- Use brute-force culling as a diagnostic — disable one system/object (or drop screen resolution / texture quality) and watch performance; a big gain from a small change localizes the bottleneck and pinpoints the limited back-end stage. (Unity5Opt)
- Build a data-export/replay tool and a dedicated stress-test scene when the profiler window is capped (e.g. 300-frame limit) — Coroutine-driven chunked binary logs plus a custom loader let you inspect long-term behavior, and a controlled isolated load makes a system's scaling legible before it hits production. (Unity5Opt; Unity6Opt)
- Diagnose CPU-bound vs GPU-bound before optimizing rendering, and account for multithreaded rendering — with a graphics worker thread, freeing main-thread (AI/script) cycles won't help rendering; compare CPU "rendering" time vs GPU time to know whether you're draw-call-bound, vertex-bound, or fill-rate/bandwidth-bound. (Unity5Opt)
- Read instrumented values only after stopping the timer and emit one batched log at the end — mid-loop Debug.Log is prohibitively expensive in CPU and heap and pollutes the very data you collect; wrap repeatable timing in a disposable averaging timer, knowing averaging hides variance and first-invocation JIT cost. (Unity5Opt)

### Most Problems Are Problems of Scale
- Treat scale, not the single object, as the real enemy — a system runs fine in the small and collapses when instance count, light count, or draw count accumulates; design for the aggregate and put a hard cap on any per-object cost that multiplies. (Unity6Opt; SWEngGames)
- Question every algorithm's suitability for future data size, not just today's (10 vs 10,000 entries) and write efficient algorithms first — data growth outpaces CPU speed, no amount of assembly fixes an O(n²) approach, and a better algorithm beats hand-tuning regardless of language; pick the sort/structure that fits the input distribution. (PolishedGameDev; Tricks3D; GameAIPro2; ProgramArcade)
- Recognize all-pairs forces/collisions scale as N², and per-contributor-over-every-affected-entity processing is a multiplicative blowup — these need a hard cap or a smarter structure, not micro-tuning. (SWEngGames; Unity6Opt)
- Build scaffolding/mocks that generate large data sets to expose non-scalable code paths early — prototype the riskiest scale assumption first (1000 entities on screen, draw distance) so you fail fast where the choke point actually lives. (PolishedGameDev)
- Don't assume hardware growth solves scale — richer environments make individual checks (line-of-sight, perception, dynamic state-space analysis) more expensive faster than Moore's law (Halo 3 did fewer LoS checks than Halo 2). (GameAIPro2)
- Know when to stop optimizing — there is always a faster/cleaner version; declare "acceptable quality," weigh every change against workflow/maintainability/the risk of new bottlenecks (only algorithmic wins are free; every other optimization trades one resource for another), and re-profile after each fix to confirm it helped and didn't shift the bottleneck elsewhere. (Unity5Opt; PolishedGameDev)

### Data-Oriented & ECS Architecture
- Separate data from behavior — store state in data-only component structs (no methods), run logic in entity-agnostic systems that query by component signature; one shared system over N entities beats N independent update scripts for both performance and reuse, letting the same movement system process players and enemies alike. (ECSFundamentals; CertProgrammer)
- Treat entities as pure identifiers grouping components, never as logic holders — ask "what data does this entity need + which systems process it," which scales better than "what script does this object have." (ECSFundamentals)
- Store same-typed component data contiguously in memory chunks — cache-friendly contiguous iteration is dramatically faster than chasing scattered object references; pad/lay out structs to cache-line multiples and use interleaved vertex/data formats so smaller working sets fit in cache and increase throughput. (ECSFundamentals; Tricks3D; GameMath)
- Prefer std::vector / arrays / fixed structures over node-based set/map in hot paths and game-sized pointer collections — contiguous memory is cache-friendly and avoids per-node allocation; measure to find the n where a tree's O(log n) actually wins. (GPGems2; IntroGameDesign)
- Split heavy per-entity work into jobs distributed across cores instead of a serial main-thread loop — single-threaded iteration over thousands of objects is the bottleneck parallel jobs remove; schedule a job once and let the framework fan matching entities across worker threads, declaring the tightest access (read-only vs read-write vs by-value) so the scheduler runs more jobs in parallel with fewer conflicts. (ECSFundamentals)
- Favor value-type, allocation-free, reference-free code in hot systems and opt them into native compilation explicitly per unit — the compiler only optimizes a numeric, GC-free, reflection-free subset, so use the SIMD-friendly compiled-subset math library (not legacy engine math), prefer unmanaged struct systems by default, and stay inside the subset to unlock large speedups. (ECSFundamentals)
- Pass per-frame inputs (delta time, elapsed time, RNG seed) into jobs as data fields and use a deterministic, value-type, job-compatible RNG — jobs can't reach global/static APIs, so capture them in the system and hand them in. (ECSFundamentals)
- Budget per-entity work knowing the cost split — simple per-entity logic (movement) scales to tens of thousands cheaply, while expensive logic (AI, physics) and rendering raise the per-entity cost; expect a one-time first-run compile pause in editor that ahead-of-time builds remove. (ECSFundamentals)
- Build behavior by composition (delegate appearance/input/physics to pluggable parts), not a class per combination — composition is additive where inheritance is exponential (2×2×2 = 8 plug-ins vs 18 subclasses), and pointer-member delegates enable runtime behavior swaps. (SWEngGames; GameDevUnity; BulletHell; PatternsUnity6)
- Use the flyweight pattern for shared context-free entity data (media, FSM/script definitions) and keep only per-instance status (position, health, state) in the entity — the heavy shared data loads once; share one mesh/animation object across all instances of a type via a use count. (GPGems2; RPGDirectX)
- Reserve abstract-interface/virtual indirection for pluggable/replaceable modules (renderers, spatial DBs, AI behaviors); never put it on functions called in inner loops, and avoid virtual functions plus vtable pointers in small heavily-used objects — per-call indirection and instruction-cache misses aren't worth it in tight loops. (GPGems2)

### Object Pooling
- Pool any object that spawns and dies frequently (bullets, projectiles, particles, enemies, platforms) instead of Instantiate/Destroy — recycle via SetActive(false/true), shift allocation to load time, and eliminate the GC spikes, frame hitches, and memory churn that dozens/hundreds of spawns per second cause; pooling is effectively mandatory on mobile and dense scenes. (Unity5Opt; BulletHell; PatternsUnity6; CertProgrammer; Unity2DCookbook; Platformer2D; ProgramArcade; SWEngGames; IntroGameDesign)
- Understand the real cost being avoided: Instantiate clones the prefab + children, allocates, registers with physics/rendering/every tracking system, and runs Awake/OnEnable; Destroy reverses that plus GC — it is far more than memory. (BulletHell; PatternsUnity6)
- Prespawn the expected peak count of each prefab at scene init and right-size pools per prefab through testing — too few forces runtime allocation (defeating the system), too many wastes memory; instrument inactive-time to detect over-prespawning, or let the pool grow on demand so it stabilizes at real gameplay demand. (Unity5Opt; PatternsUnity6; BulletHell)
- Make pooling generic over a poolable contract (create / get-reactivate / release-deactivate / destroy-only-over-capacity) so any type fits one implementation — only the destroy callback calls Destroy (on Clear/Dispose or past max capacity); everywhere else, reuse. (Unity5Opt; BulletHell; PatternsUnity6)
- Re-initialize pooled objects on every Get, never assume a fresh Start, and reset ALL per-life state (velocity, hit-flags, timers) — pooled objects keep their last transform and stale state, and disabling a Rigidbody zeroes its velocity, so recycled instances spawn dead-on-arrival or misbehave unless explicitly re-applied; reset stateful poolable data during Despawn (spawn-time component order is undefined). (Unity5Opt; BulletHell; PatternsUnity6)
- Give each pooled instance a reference to its owning pool so it returns to the correct one, and have it release itself on every exit path (lifetime expiry AND impact) — required when multiple pools exist; guarantees no leaks, and enable collection-checks during development to catch double-release bugs. (BulletHell)
- Back the pool with fast keyed structures (Dictionary<prefab,pool> for spawn, Dictionary<gameObject,pool> for despawn) and precache each instance's poolable-component array at instantiation — so the system scales to thousands of prefabs without iterating pools or reacquiring components at runtime. (Unity5Opt)
- On despawn, SetActive(false) (one call disables collider/rigidbody/rendering/most subsystems) but explicitly Stop running Coroutines and deregister from custom systems (message bus, etc.) — they keep running otherwise; reset a scene-outliving static pool before loading a new scene, since Unity destroys pooled instances on scene change and leaves your dictionaries full of nulls. (Unity5Opt)
- Cap how many of a transient thing one source keeps active and give transients a fixed lifetime so they self-expire — shooting beyond the cap recycles the oldest bullet (never leaving the player defenseless), and bullets older than ~3s die even if they never hit, preventing unbounded growth and off-screen accumulation. (SWEngGames; BulletHell; Build3DUnity)
- Preallocate and cache frequently created/destroyed objects via a template cache / free list instead of constant new/delete, and override global new/delete to pool common small allocations — avoids heap fragmentation from many small short-lived objects; pass large allocations to a separate allocator. (GPGems2; PolishedGameDev)

### Memory & GC-Aware System Design
- Design for GC avoidance first, concealment second — mark-and-sweep cost scales with heap size and can freeze gameplay, so allocate little and control lifetimes tightly; prefer stack-allocated value types / structs for short-lived scope-local data, which deallocate for free and stay invisible to the GC. (Unity5Opt; IntroGameDesign)
- Lay data out to help the GC: separate large arrays of value types from reference types — one reference field inside a struct forces the GC to scan the whole array, while parallel primitive arrays let it skip them entirely; pass large structs by ref (with readonly fields) to avoid copying. (Unity5Opt)
- Treat strings as immutable reference types and avoid boxing — every concatenation allocates a new heap string (chained + built 9 strings / 524 bytes for one log line), so use StringBuilder / string.Format/Join, and never pass value types where System.Object is expected on a hot path. (Unity5Opt)
- Never read GameObject.tag or .name at runtime — these duplicate the string on the heap and attract the GC; use CompareTag (no allocation, errors on a bad/unregistered tag) in collision callbacks that fire every contact frame, and prefer component/type identity over string identity. (Unity5Opt; Platformer2D; Build3DUnity; CSharpForUnity)
- Avoid per-frame allocations on hot paths: no foreach over Mono generic collections or Transform children (allocates an enumerator — foreach over plain arrays is safe), no Closures/LINQ/Regex (heap captures, heavy overhead, LINQ breaks on AOT/iOS), and no Unity API calls returning arrays (GetComponents, Mesh.vertices, allCameras) — call once and cache, and reuse large temporary work buffers instead of reallocating. (Unity5Opt; IntroGameDesign)
- Understand the three memory domains (native C++ engine, managed Mono heap, external DLLs) and minimize native↔managed bridge crossings — every callback, null check, and string property carries hidden cost; optimizing managed memory indirectly trims native too, since their representations are linked. (Unity5Opt)
- Explicitly free unmanaged resources promptly (Dispose WWW, Resources.UnloadAsset, UnloadAudioData) — nulling references does not free native memory and freed memory returns asynchronously; conceal unavoidable GC by manually invoking GC.Collect() during loads/pauses/cutscenes, querying mono used/heap size to decide when. (Unity5Opt)
- Ship a drop-in debug memory manager (overload new/delete, log file+line) active only in debug builds — track leaks (entries at exit), bounds violations (sentinel padding), and actual-vs-allocated usage; every alloc needs a matching dealloc, which applies even in GC languages. (GPGems2; PolishedGameDev)
- Load an object's assets at game-load time (in its constructor, or have another object preload mid-game) — prevents memory fragmentation and mid-game allocation/GC stalls; load small frequently-used clips into memory and stream large ones from disk under memory pressure. (PolishedGameDev; Unity2DCookbook)
- Avoid Find()/SendMessage() for runtime inter-object wiring — Find scales O(n) with scene size and SendMessage is ~2000x slower than a direct call; cache component references once in Awake/Start instead of calling GetComponent per frame or per hit. (Unity5Opt; BulletHell; AdvancedCSharp; Build3DUnity; CertGameDev; Platformer2D; Unity2DCookbook)

### Batching & Draw Submission
- Minimize the number of discrete commands a system submits per frame — submission overhead (draw calls/batches) can saturate the CPU before the GPU is stressed; a runaway batch count is the clearest warning sign, and minimizing render-state changes (grouping by shared Material/Shader) keeps the parallel GPU from stalling. (Unity6Opt; Unity5Opt)
- Maximize state coherence and share assets/materials aggressively across similar entities — batching needs same material/shader state; proliferating unique material instances destroys it, and one incompatible shader variant fragments what should be a single batch. (Unity6Opt; Unity5Opt)
- Avoid reading renderer.material for per-instance effects — it clones a per-instance material, breaks SRP batching, and leaks memory; prefer the cheapest per-vertex path (SpriteRenderer.color, safe every frame on many sprites) or MaterialPropertyBlock for richer overrides. (BulletHell)
- Batch by shared state, not by combining payloads, when possible — caching per-instance properties so the system avoids re-uploading state every frame keeps individual commands cheap (the SRP-batcher pattern: same shader variant submits back-to-back even with differing material data). (Unity6Opt)
- Pre-combine static, non-moving geometry into consolidated batches (Static Batching) and atlas small textures sharing a shader — trades extra memory for far fewer per-frame commands; never include dynamic/moving entities (baked-in position data renders them wrong) and don't atlas animated Skinned Meshes (they always cost a draw call). (Unity6Opt; Unity5Opt; Unity2DCookbook)
- Require explicit author intent to flag entities static (the engine can't infer immutability) and never instantiate or move statically-batched meshes at runtime — Static Batching happens too early to intercept; author it in the scene and debug only at runtime. (Unity6Opt; Unity5Opt)
- Use Dynamic Batching for large groups of simple near-identical non-animated meshes sharing one Material, within its strict limits (≤900 vertex attributes, ≤300 meshes, no multi-pass shaders/real-time shadows) — it batches visible meshes at runtime. (Unity5Opt)
- Composite many per-tile/per-segment colliders into one outline (Composite Collider 2D) and prefer few long walls over many short ones — fewer collider shapes for the physics system to manage, fewer seams that snag fast bodies. (BulletHell; Platformer2D; SWEngGames)
- Let the engine batch and optimize heavy subsystems (draw-call batching, physics, collision, particles) and write your game on top — don't hand-roll what the engine already optimizes; batch small images into one atlas/spritesheet and reuse one shared material so multiple sprites render in a single draw call. (IntroGameDesign; Unity2DCookbook)

### Do-Less: Cull, Defer, Reject Early
- Not rendering/processing something is always the fastest way to draw it — skip work for entities the consumer (camera/player) can't perceive; stage the pipeline with cull/reject stages ordered cheapest-and-most-effective first (one bounding-sphere point test kills a whole mesh, then back-face removal ~50% of polys, then clipping). (Tricks3D; Unity6Opt)
- Layer cheap automatic culling (frustum, free and geometric) with expensive precomputed culling (occlusion/PVS) — per-frame occlusion testing is too costly, so bake a visibility set per space cell and look it up at runtime; match the strategy to scene shape (occlusion wins in dense/enclosed/corridor layouts, LOD wins in open scenes where the cost is distant visible geometry, not hidden geometry). (Unity6Opt; Tricks3D; Unity5Opt)
- Trade offline preprocessing + memory for runtime speed via spatial structures (BSP, octree, BVH, PVS, sectors) — visibility/partitioning don't scale in closed form, so precompute against static data; hierarchical bounding volumes let one root test reject an entire universe (10,000 sphere tests → a few dozen), and reuse the same structure for both rendering and collision (turning O(n²) = 100M tests into ~500K). (Tricks3D; GPGems2; RPGDirectX; GameMath)
- Disable non-visible system work, not just rendering — Frustum/Occlusion culling skip drawing, but AI/logic components must self-disable via OnBecameVisible/OnBecameInvisible or distance checks; gate distance-based activation with a low-frequency Coroutine and squared distance to avoid per-frame work and the costly sqrt. (Unity5Opt)
- Prune the pair/interaction set aggressively — maintain a list of only pairs that can meaningfully collide (not all N²), set fixed/immovable critters' flags so the collider ignores their pairs (100 power-pellets shouldn't generate pellet-pellet checks), disable collision-matrix layer pairs that never interact, and skip off-screen objects; use cheap broad tests (bounding spheres) before exact narrow tests. (SWEngGames; Unity5Opt; BulletHell)
- Destroy/cull off-screen or out-of-bounds dynamic entities that can't be regenerated cheaply — enemies that wander off-camera keep taking turns and slowing the sim; generate content in the direction of travel and destroy stale content behind to keep a bounded live object count for endless levels. (PCGUnity; Unity2DCookbook)
- Reduce overdraw to protect fill rate and avoid clearing the z-buffer every frame where you can — front-to-back traversal masks covered pixels, and 1/z-buffering with a per-frame additive bias skips a clear that can cost ~24% of a 60fps budget. (Tricks3D; Unity5Opt)
- Solve only the part of a problem you need now (lazy evaluation) and distribute long calculations across frames by saving/resuming state — hierarchical pathfinding computes room-to-room first and the micro-path per room as entered; spreading A* across frames lowers per-frame load for any algorithm of unspecified duration. (GPGems2)

### Level-of-Detail & Adaptive Fidelity
- Scale an entity's processing cost to its on-screen importance — render/simulate distant or small entities at reduced fidelity, full fidelity only up close, and include a fully-culled tier (the cheapest work is work skipped); spending equal cost on a horizon object wastes resources. (Unity6Opt; Tricks3D)
- Drive LOD swaps by apparent screen-space size, not raw distance, and expose a global bias multiplier over local thresholds — relevance to the final image should gate fidelity, and one quality knob shifts all transitions for different hardware tiers (verify on-device, where the bias may differ). (Unity6Opt; Unity5Opt)
- Apply LOD to AI and simulation, not just rendering — scale processing frequency by distance to camera/action, simplify or swap cheaper behaviors/animation drivers off-screen (full IK on-screen, dummy state tracking off), and represent many distant agents with one aggregate simulation; scale back if it shows. (GPGems2; GameAIPro2; Unity5Opt)
- Tune transition thresholds deliberately and smooth them (cross-fade) where silhouettes or reflective materials make pops obvious — provide a scrub/preview tool to find natural swap points; accept that LOD trades memory for compute since all variants stay resident for instant switching. (Unity6Opt; Unity5Opt)

### Run-Less-Often: Scheduling, Throttling & Staggering
- Run AI/perception/pathfinding less often than every frame and randomize each agent's callback window — creatures have reaction times anyway, throttling with interval timers is the primary lever for supporting many agents, and randomizing prevents synchronized processing peaks. (GPGems2; UnityAI; GameAIPro2; SWEngGames)
- Stagger periodic systems so timed events don't all fire on the same frame — randomize wait times, spread Coroutine starts across frames, or cap invocations-per-frame in a master scheduler; otherwise N objects sharing a frequency spike together. (Unity5Opt)
- Schedule rules/updates by a frequency timer (per-rule overridable, default once per game-day) rather than every frame, and make condition checks near-constant-time via a simplified condition language and an inexpensive-to-query world model — the production engine's CPU cost should be invisible in the profiler even on weak hardware. (GameAIPro2)
- Replace per-frame timer-gated Update logic with Coroutines or InvokeRepeating for delayed/periodic work, and prefer event-driven behavior over polling — calling an empty method plus a bool check every frame is pure waste, and agents that react to events instead of re-checking every frame cut processing dramatically (recompute derived/UI state only on the mutation that changes it, not in Update). (Unity5Opt; GPGems2; CSharpForUnity; AdvancedCSharp)
- Delete empty Update()/Start()/callback stubs — Unity hooks every declared callback and pays a native↔managed bridge cost per object per frame; thousands of empty Updates wreck the frame rate, and a single empty stub in a shared base class permeates every component (customize script templates to strip them). (Unity5Opt)
- Centralize updates: have one god-class Update() iterate registered IUpdateable objects calling OnUpdate(dt) — replaces N native-bridge callbacks with 1 callback + N managed virtual calls, keeping the hot path in managed code; register/deregister in Start()/OnDestroy() so init order is safe. (Unity5Opt; Tricks3D)
- Throttle queue processing (message bus, network callbacks) with a per-frame time budget — drain until a max-time threshold and defer the rest to next frame so a flood can't freeze the game; process a capped number of network messages per frame so the server never bogs down on bursts. (Unity5Opt; RPGDirectX)
- Partition dirty-on-change subsystems so a localized change triggers only a localized rebuild — splitting one large UI canvas into multiple isolates updates so a small change doesn't force the whole structure to rebuild, and disabling unused per-element capability (raycasting on non-interactive UI) removes avoidable per-element overhead at scale. (Unity6Opt)

### Precompute, Bake & Lookup Tables
- Shift expensive static computation out of the per-frame loop into a precomputed bake — lighting, visibility, navigation, terrain analysis, and similar data that never changes at runtime become a table lookup; do hard work offline (BSPs, trained nets, LOS tables, waypoint analysis) to cram thousands of hours of wisdom into kilobytes and trivial runtime cost. (Unity6Opt; GPGems2; Tricks3D; PolishedGameDev)
- Treat baking as a cost transfer, not a free win — it moves cost from frame time into bake time, disk space, and runtime memory; bake only when inputs are truly static, store the data with the scene, and offer a mixed mode (bake the static portion, keep a dynamic path for moving entities) to get most of the savings without losing dynamism. (Unity6Opt; CertGameDev; Unity5Opt; GameDevUnity)
- Use lookup tables aggressively for any function whose inputs fit in a few KB–MB, and cache redundantly-computed values lazily behind a sentinel — memory is cheap, so precompute instead of recompute; cascade tables logarithmically and scale inputs down to shrink huge tables, and never pay for a cached value a code path may skip. (Tricks3D; GameMath; GameAIPro2)
- Amortize expensive query costs by continuously updating a data structure as data changes rather than gathering it on demand — spreads cost over many frames so the query is cheap (influence maps, LOS lists, fog-of-war); batch and amortize big rebuilds (k-d trees, regions, queue sampling) in one pass, parallelizing across cores/frames. (GPGems2; GameAIPro2)
- Run a fast low-quality bake first to establish a baseline and validate the data layout a baker depends on (e.g. lightmap UVs) — early passes expose setup errors cheaply before long high-fidelity bakes; treat bake artifacts (blotches, leaks, pop-in) as tuning signals (raise sampling/resolution/padding) and provide a visualization overlay since designers can't tune what they can't see. (Unity6Opt)
- Precompute collision/derived data offline in the asset pipeline rather than in-engine, and separate the simulation representation from the render mesh — a simplified low-poly/sphere collider plus bit-packed masks prepared in the form the engine needs is low-memory and fast, and the benefit scales exponentially with object complexity. (PolishedGameDev; Unity5Opt; GameDevUnity)

### Physics System Cost Control
- Decouple physics from frame rate via a fixed timestep and only mutate Rigidbodies in FixedUpdate / physics callbacks — variable timesteps produce inconsistent collisions across machines/replays/multiplayer, and changes in Update or time-based Coroutines cause multiple unprocessed changes per step. (Unity5Opt; CertGameDev; CertProgrammer; Build3DUnity; Platformer2D; GameDevUnity; CSharpForUnity; Unity2DCookbook)
- Cap physics catch-up with a Maximum Allowed Timestep to prevent the "spiral of death," and budget physics work per step in best and worst case — each long update otherwise spawns another, and heavy FixedUpdate work steals from rendering and gameplay; clamp dt to a sane max (~0.1s) so entities don't teleport through walls. (Unity5Opt; SWEngGames)
- Prefer primitive colliders (Sphere < Capsule < Box, an order of magnitude cheaper than Mesh) and reserve Mesh Colliders for static geometry (convex only for moving bodies, ≤255 verts) — approximate complex shapes with a few child primitives, and decouple the collision shape from the render mesh since gameplay rarely needs exact accuracy. (Unity5Opt; CSharpForUnity; GameDevUnity; VRUnity; Build3DUnity)
- Optimize the collision matrix via layers — disable layer pairs that never need to collide so the engine skips those broadphase checks entirely; unchecked pairs are free performance, and engine-level layer filtering beats per-contact script conditionals. (Unity5Opt; BulletHell; Platformer2D; CertProgrammer)
- Distinguish Static Colliders (never move at runtime — moving one forces a costly full regeneration) from Kinematic Rigidbodies (script-movable, live in the moving-object structure) — and default to Discrete collision detection, reserving Continuous/ContinuousDynamic for rare fast small objects since each tier is ~an order of magnitude more expensive. (Unity5Opt; Build3DUnity; Platformer2D; BulletHell)
- Exploit the sleep system but guard against waking storms — sleeping objects cost almost nothing, but touching "islands" of sleepers wake in chain reactions causing CPU spikes; despawn/lock settled objects (especially ragdolls), and avoid per-frame forces or property changes that prevent sleep. (Unity5Opt)
- Ask whether physics is needed at all before using it, and tune FixedUpdate frequency early and rarely — replace simple cases with y-threshold checks or tweening, but replace heavy script scans with a single OverlapSphere where physics is cheaper; higher physics frequency catches fast collisions but costs CPU and couples to all FixedUpdate logic. (Unity5Opt)

### Spawning, Lifecycle & Deferred Mutation
- Defer all add/delete/spawn/replicate to a service-request queue drained once per cycle — adding to or removing from a collection you're iterating is unsafe and corrupts not-yet-updated interactions; never instantly destroy a damaged entity (play a death act first), and scrub dangling pointers when an entity dies. (SWEngGames; GPGems2)
- Disable a one-shot/spawn system at the very TOP of its update, before doing the work — disabling at the bottom lets it run one extra frame and double its effect (e.g. spawning twice the entities); order of self-disable vs side-effect is load-bearing. (ECSFundamentals)
- Drive spawning from data — a spawner component holds the prefab + count, a system reads it and instantiates from one template entity; authoring thousands of objects by hand is impractical, and one template plus a count scales arbitrarily, with a uniform spawn path keeping runtime creation manageable. (ECSFundamentals; CSharpForUnity; BulletHell)
- Inject runtime-only references (a pool created in Awake) into spawned objects via an Init method right after Instantiate — the editor can't assign a runtime object, so the spawner passes it post-spawn; guard a system so it only updates when relevant data exists (RequireForUpdate) to avoid wasted empty-work frames. (BulletHell; ECSFundamentals)
- Simulate in parallel: run ALL updates (look/decide) first, THEN all moves, keeping entities in one array (not one thread per object) — update-then-move per entity makes behavior depend on array order; conceptually freeze simulated time during update so every entity perceives the same world snapshot, giving deterministic reproducible ordering OS threads can't. (SWEngGames)

### Asset & Resource Systems
- Treat every asset optimization as an explicit tradeoff between metrics (size/memory/CPU/quality/workflow) — never apply a technique without understanding its cost, or you invite new bottlenecks; budget memory bandwidth per frame (bandwidth ÷ FPS), which limits texture swapping per frame, not total VRAM. (Unity5Opt)
- Keep textures square and power-of-2 (cap ~4096) — GPUs pad non-conforming textures and waste bandwidth pushing useless data; use Mip Maps in 3D (but disable for always-near UI/2D, where lower-res levels never render and cost ~33% extra), and choose per-device compression formats. (Unity5Opt; Unity2DCookbook; PolishedGameDev)
- Load every asset exactly once before the loop and reuse the handle — loading from disk per frame is needless and slow; defer audio/asset loading to natural stopping points or background loads rather than at first-play (which spikes CPU), and prefer LoadSceneAsync so loading spreads across frames instead of freezing the game. (ProgramArcade; Unity5Opt; Platformer2D; BulletHell)
- Use ScriptableObjects / shared assets for data that needn't be instantiated at runtime, loaded on demand — share by reference, not by copy, for fine-grained control over which data is in memory; tilemaps store tiles as lightweight ScriptableObjects in a sparse grid, so thousands of cells cost far less than individual GameObjects. (Unity5Opt; Platformer2D; GameDevUnity)
- Throttle active audio with a management/pooling system that caps simultaneous clips and reuses idle sources — each active source costs CPU; share clip references (multiple sources on one clip cost no extra memory) and mark sounds 2D (Spatial Blend 0) when the listener-source distance is fixed to skip 3D spatial calculations. (Unity5Opt; BulletHell; Unity2DCookbook; Platformer2D; PCGUnity)
- Choose audio Load Type per use (Decompress On Load default; Compressed In Memory to trade CPU for memory; Streaming for single-instance long clips) and encoding per purpose (PCM for short SFX, Compressed general, Tracker Modules for music) — never repeatedly decompress per frame, and pick the inaudible quality "sweet spot." (Unity5Opt; Unity2DCookbook)

### Frame-Rate Independence (Consistency Across Hardware)
- Multiply all per-frame motion/animation/physics by elapsed time (Time.deltaTime, telaps), never by a fixed per-frame constant — `pos += dt*vel` keeps apparent speed identical across slow and fast machines while `pos += vel` makes the game unplayable on a faster CPU; time all flip-book/lifetime logic off seconds, never cycle counts. (SWEngGames; Tricks3D; BulletHell; RPGDirectX; GameDevUnity; Build3DUnity; Platformer2D; ECSFundamentals; PolishedGameDev; Unity2DCookbook; VersionControl)
- Cap the frame rate (30 min, 60 ideal) with a clock tick or timing/wait, and keep per-frame work cheap — uncapped loops burn all CPU and are wasteful past the refresh rate, and too-frequent heavy redraws make the program sluggish; clamp dt to a min tied to the refresh rate so sub-refresh updates don't pile up. (Tricks3D; ProgramArcade; RPGDirectX; SWEngGames)
- Enforce the target frame rate continuously throughout production and fix any code/data that drops below it immediately — serious performance issues found in the last two months may be too structural to fix; treat performance as a continuous system constraint, not an end-of-project pass. (PolishedGameDev; QATesting)
- Use elapsed-time accumulators typed for long-session accuracy (double, not float) for timers, and centralize a reused per-frame magnitude in one cached value — float drifts over long play sessions, and a single source for a derived quantity keeps tuning consistent. (ECSFundamentals; VersionControl)

### Engineering Discipline & Payoff
- Game AI gets ~10% (rarely >20%) of the machine and must hit near-real-time — choose techniques whose time/memory you understand, since marginally inefficient code (cache misses, fragmentation) compounds into prohibitive cost; preallocate node memory with a dirty bit, avoid runtime allocation in search, and store operator sequences instead of full state copies. (GameAIPro2)
- Shrink memory before optimizing time — pick the smallest sufficient container, store information once and share by integer position, use a custom allocator; time complexity can't beat space complexity, so start with the memory footprint. (GameAIPro2)
- Saving system resources expands your possibility space — freed CPU/GPU/memory lets you build richer, more dynamic gameplay within the same hardware budget; real-world wins are layered, so combine multiple targeted fixes each addressing a distinct pipeline stage rather than hunting for one magic setting. (Unity5Opt; Unity6Opt)
- Treat every optimization as a trade and verify it against your target hardware budget — monitor the resource you're spending, not just the one you're saving (a "harmless" memory cost on desktop may bust a mobile budget); the ideal optimization is invisible to the player, so if output looks broadly the same after the change, the cost removed was genuinely unnecessary. (Unity6Opt)
- Identify the single highest-impact lever first and reserve expensive per-entity quality for entities that matter — in render systems shadows/lighting are often dominant, so the largest win comes from the most expensive feature, not many small ones; respect shared-budget pools (e.g. a shadow atlas) and compensate cheaply when you cut a feature (SSAO for removed shadows). (Unity6Opt)
- Build job systems, queues, schedulers, and crash-recovery on first-class command objects — a command packages computation that can be invoked later, on another thread, far from where it was created, and command store()/load() logging enables batch replay from a checkpoint cheaper than snapshotting large state every change. (HeadFirstPatterns)
- Crowdsource emergent-bug and scale-failure discovery from live players and reward reporting — players outnumber testers thousands-to-one and will find leaks you never checked, turning bug-finding into a system-hardening channel. (QATesting)
