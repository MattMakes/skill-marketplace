# System Architecture, Decoupling & Networking

## System Architecture & Decoupling

### Core Decoupling Principles
- Treat coupling as the primary scaling risk — minimize direct cross-script method calls and external variable reads/writes, because every direct connection makes the codebase more fragile as it grows. (PatternsUnity6; HeadFirstPatterns)
- Strive for loosely coupled designs between interacting objects — minimize interdependency so each side can change independently as long as the contract holds; this is what lets systems absorb change. (HeadFirstPatterns; PatternsUnity6; GDWorkshop; Tricks3D)
- Keep the number of classes any one class is coupled to small — many inter-class dependencies build a fragile, costly-to-maintain system that others struggle to understand. (HeadFirstPatterns)
- Apply the Principle of Least Knowledge ("talk only to immediate friends") — a method should only call methods on itself, its parameters, objects it creates, and its own components, to reduce cascading change through a web of coupled classes. (HeadFirstPatterns)
- Apply Separation of Concerns / Single Responsibility — give each script, system, or component one clear purpose and one reason to change; overlapping responsibilities (gameplay vs. animation vs. driver state machines) silently fuse into unmaintainable monoliths. (PatternsUnity6; HeadFirstPatterns; GameAIPro2; RPGDirectX; GDWorkshop; GameDevUnity; IntroGameDesign)
- Split a god-object manager into focused services (LevelLoader, ScoreManager, EnemySpawn) instead of one GameManager doing loading + score + spawning — separate concerns let you change one without disturbing the others. (PatternsUnity6; BulletHell)
- Apply "purity of purpose": every component has a single, clearly-defined mission, nothing fuzzy or redundant — then tweaking one element changes one aspect, making balancing methodical instead of guesswork. (GDWorkshop)
- Decompose the game into discrete, loosely-coupled subsystems (combat, magic, resource management) with defined inputs/outputs — modularity lets you predict the impact of any change. (GDWorkshop; Tricks3D; RPGDirectX)
- Design subsystem interfaces up front and keep cross-dependencies minimal — interrelationship sprawl is the single biggest mistake in engine architecture. (Tricks3D; RPGDirectX)
- Build each subsystem as a fully self-sustaining module (graphics-only, input-only, sound-only) with a uniform lifecycle (Init/Create, Shutdown/Free, per-frame Update/Render) — pick and combine pieces per project, with predictable composition and teardown. (RPGDirectX)
- Divide ownership so different contributors own different scripts/modules — clear module boundaries minimize overlapping edits and merge conflicts, the same decoupling that keeps systems maintainable. (VersionControl; ProgramArcade)
- Keep the update entry point focused on orchestration and isolate concrete logic in named methods (Update → Move) — separating dispatch from implementation improves readability and shrinks merge surface on hot paths. (VersionControl; IntroGameDesign)
- Aim for code clean enough to re-skin: truly data-driven levels, loosely-coupled scripts, no engine-side edge-case hacks — that is the real test of whether an engine is reusable/licensable. (PolishedGameDev)

### Components & Composition over Inheritance
- Favor composition over inheritance — "HAS-A is better than IS-A"; behavior assembled from parts can change at runtime and avoids the brittle class explosion of deep hierarchies. (HeadFirstPatterns; SWEngGames; Build3DUnity; IntroGameDesign; GameDevUnity; CertGameDev)
- Use composition to defeat combinatorial explosion — 2 sprites × 2 listeners × 2 forces is 8 plug-in parts, not 18 hand-coded subclasses; inheritance cost is exponential, composition is additive. (SWEngGames; HeadFirstPatterns)
- Identify what varies and separate it from what stays the same — encapsulate the changing parts (fly/quack, damage types, AI steering) so you alter or extend them without touching stable code. (HeadFirstPatterns)
- Build entities by attaching small, single-purpose components/scripts to a lightweight container, not by deep monolithic classes — a GameObject is a bag of components; put each distinct responsibility in its own component so they stay independently testable and reusable. (IntroGameDesign; GameDevUnity; Build3DUnity; CSharpForUnity; Platformer2D; BulletHell; PatternsUnity6; Unity2DCookbook; CertGameDev; GPGems2)
- Model your systems on the engine's component model: small focused components that don't know about each other (Rigidbody, MeshRenderer, AudioSource) — composability comes from each piece owning one concern. (PatternsUnity6; GameDevUnity; Unity2DCookbook)
- Delegate via pointer/reference members, not value members — pointer members enable polymorphic child plug-ins and runtime swapping; pass `this` (the owner) into the delegate so it can read and mutate owner state. (SWEngGames; HeadFirstPatterns)
- Compose behavior additively (Mesh Filter + Renderer + Collider + Rigidbody makes a physics prop) and swap or remove one component to change behavior — favor pluggable parts over monolithic classes. (GameDevUnity; SWEngGames)
- Separate the logic/physics root from the visual child (parent holds collider + Rigidbody + scripts, child holds the model) — lets you swap art, flip, or VFX the sprite and reuse the logic shell without disturbing physics. (Build3DUnity; CSharpForUnity; Platformer2D; GPGems2; RPGDirectX)
- Use prefabs / configurable templates so you author an entity once (data + components) and Instantiate many — centralizing definition makes balance edits propagate everywhere; build entity families as prefab variants off a shared base. (IntroGameDesign; Unity2DCookbook; Platformer2D; BulletHell; CertProgrammer)
- Use inheritance only where IS-A genuinely holds — derive a subtype from the more general/abstract type, subclass only to specialize, and never invert the hierarchy (a Dolphin must not parent Mammal). (ProgramArcade; IntroGameDesign)
- Keep transform/parent inheritance strictly one-directional (parent affects child, never the reverse) so hierarchies stay predictable — model "things that must stay together" as one-way downward grouping. (GameDevUnity)
- Reserve abstract-interface/virtual indirection for pluggable, replaceable modules (renderers, spatial DBs, AI behaviors, tool extensions); never put it on functions called in inner loops — and avoid virtual functions/inheritance entirely in small, heavily-used objects where the vtable pointer and indirection cost. **When it flips:** in inner loops needing type-based behavior, replace virtual + dynamic_cast with a single virtual behavior method or a swapped function pointer. (GPGems2; HeadFirstPatterns)

### Interfaces, Capabilities & Dependency Inversion
- Program to an interface (supertype), not an implementation — declare variables as abstract types so the concrete runtime object isn't locked into your code, letting you swap behaviors at runtime. (HeadFirstPatterns; SWEngGames; CertProgrammer; AdvancedCSharp; IntroGameDesign)
- Make high-level systems depend on abstractions (interfaces/events), not concrete low-level classes (Dependency Inversion) — both high- and low-level code depend on abstractions, keeping systems swappable, testable, and independently changeable. (PatternsUnity6; HeadFirstPatterns)
- Have systems depend on capabilities, not concrete classes — a damage system targets "anything implementing IDamageable" so the concrete type can change without forcing changes in callers. (PatternsUnity6; AdvancedCSharp; BulletHell; CertProgrammer; GPGems2)
- Ask "does this object support capability X?" (interface check) rather than "what class is this object?" — capability queries scale; type checks accumulate special cases and rot. (AdvancedCSharp; CertProgrammer)
- Avoid chains of type checks (`if it's a Ball... else if a Door...`) in dispatch code — they grow harder to maintain, extend, and keep correct as the roster grows. (AdvancedCSharp; GPGems2)
- Probe for a capability with `GetComponent<IInterface>()`/optional-component lookup and null-check before invoking — one controller drives any object that opts into the contract, and a hit on a non-participant is a safe no-op. (AdvancedCSharp; BulletHell; CSharpForUnity; GameDevUnity)
- Treat an interface as a promise of behavior (traits like IRenderable/ICollidable) and let entities advertise several — the loop iterates generic objects and invokes only the advertised trait, so new types drop in without editing the loop. (GPGems2; AdvancedCSharp)
- Use an interface instead of a forced inheritance hierarchy when classes share only a capability, not a gameplay purpose — express the shared ability without an artificial base class. (AdvancedCSharp; IntroGameDesign)
- Keep interfaces minimal and split fat interfaces into small capability interfaces (IGroundVehicle/IAirVehicle, not IVehicle.Drive+Fly) — classes shouldn't implement empty/placeholder methods they don't use. (AdvancedCSharp; PatternsUnity6)
- Design interface methods to return the outcome the caller needs (e.g. `Damage(int)` returns "is dead") — fold the post-condition the system must react to into the signature so callers don't re-query state. (CertProgrammer; SWEngGames)
- Protect each module's data (private/protected) and expose only public functions — outside code interacts through a known interface, never internal state. (RPGDirectX; SWEngGames; UnityAI)
- Keep fields private and expose intent through properties/getters/`[SerializeField]` — guard internal state so other code can't corrupt it, and never make a field public just to show it in the Inspector (that opens it to mutation and weakens boundaries). (UnityAI; AdvancedCSharp; BulletHell; Build3DUnity; CSharpForUnity; Platformer2D; GameDevUnity; SWEngGames; CertProgrammer)
- Use a QueryInterface-style runtime trait check or backward-compatible interface query (old interface can request a newer one) instead of RTTI/dynamic_cast — works with RTTI off, stays cheap, and lets newer components not break code written against older ones. (GPGems2; RPGDirectX)
- Pair each abstract interface with a factory that constructs the concrete type — callers include only the interface + factory headers, cutting recompiles and blocking illicit downcasts; always give an abstract interface a virtual destructor (empty body) so the concrete destructor runs. (GPGems2)

### SOLID & Open–Closed
- Design systems open for extension, closed for modification (OCP) — add new behavior (spells, enemies, items, interactables) by implementing the contract on a new piece, never by editing tested classes; repeatedly editing working code increases bug risk. (HeadFirstPatterns; PatternsUnity6; AdvancedCSharp)
- Apply Open–Closed only where change is actually likely, not everywhere — the abstraction has a cost; instantiating a stable class (e.g. a constant config) directly is fine. (HeadFirstPatterns)
- Define a base type with an abstract operation (e.g. `abstract Attack()`) and add new variants as subclasses — new enemy/weapon types ship without touching the base contract. (PatternsUnity6; IntroGameDesign)
- Put shared behavior (e.g. spike damage) on a common base type so the system interacts with the abstraction, not concrete Player/Enemy — emitters stay general and accept future subtypes automatically. (PatternsUnity6)
- Ensure any subclass works wherever its base type is expected (LSP) — if a subtype needs special-case exceptions, the inheritance is the wrong abstraction. (PatternsUnity6)
- Avoid the creation smells Dependency Inversion flags: no variable holding a concrete-class reference (use a factory), no class deriving from a concrete class (derive from an abstraction), no method overriding an already-implemented base method (that base wasn't a real abstraction). (HeadFirstPatterns)

### Events, Observers & Message Systems
- Build publish/subscribe with the Observer pattern: one Subject/observable holds state, many observers register/unregister to be notified automatically on change — the broadcaster needs no references to its listeners and scales as they come and go. (HeadFirstPatterns; PatternsUnity6; SWEngGames; CertProgrammer; EditorScripting; BulletHell; CSharpForUnity)
- Replace direct multi-target calls (a manager holding light1/light2/light3) with a single broadcast event — adding a fourth target then requires zero manager edits. (PatternsUnity6; HeadFirstPatterns)
- Separate "report that X happened" from "decide what X means" — e.g. Health raises an OnDeath event; player shows UI/animation, enemy self-destructs, audio/scoring react, all without touching Health. (BulletHell; HeadFirstPatterns)
- Keep observer notification the trigger that keeps UI/HUD, telemetry, achievements, and AI listeners in sync with model state — add a new listener with zero changes to the model. (HeadFirstPatterns; SWEngGames; CSharpForUnity)
- Mark delegates with the `event` keyword so outside code can only subscribe/unsubscribe (+=/-=), not invoke or reset them — enforces the correct observer access contract. (PatternsUnity6)
- Invoke events with the null-conditional `?.Invoke()` — a thread-safe single-step check that avoids NullReferenceException when no listeners are subscribed. (PatternsUnity6; BulletHell; EditorScripting)
- Subscribe in OnEnable/Awake and always unsubscribe in OnDisable/OnDestroy — tie subscription lifecycle to active state; dangling subscriptions later fire into disabled/destroyed targets and throw. (PatternsUnity6; BulletHell; EditorScripting; GameDevUnity)
- Prefer event-driven behavior over polling — agents that react to events instead of re-checking every frame cut processing dramatically; recompute derived UI/values on change, not in Update. (GPGems2; CSharpForUnity; CertGameDev; VRUnity)
- Decouple senders from listeners with a global message bus when many systems need the same signal — senders broadcast typed messages, listeners self-register and decide what they care about, so one message reaches 0..N listeners at equal cost. **When it flips:** for tiny setups, prefer Inspector-assigned or serialized references and graduate to a bus/events only as dependents multiply. (Unity5Opt; PatternsUnity6; CSharpForUnity)
- Generate logical events (logical sounds, contextual events) decoupled from real audio/physics, and interpret the same raw event differently by context before the behavior system selects a response — designers control what's sensed at what range without touching the underlying media. (GameAIPro2)
- Route raw input through a bridge/event layer (Player Input → Invoke Unity Events, or a controller buffer feeding listeners) so the controller never references key names and any entity can listen. (Build3DUnity; Platformer2D; SWEngGames; AdvancedCSharp; VRUnity)
- Bridge a signature mismatch between a zero-arg event and a parameterized method with a lambda adapter, computing values at fire time inside the lambda — and pass a method as a reference, not a call (`AddListener(Method)`, never `AddListener(Method())`). (AdvancedCSharp; CertProgrammer)

### State Pattern & State Machines
- Implement game flow, modes, units, and AI as explicit finite state machines (one active state, defined transitions and triggers) rather than tangled booleans/conditionals — states make flow legible, forbid illegal transitions, and cut bugs. (HeadFirstPatterns; Tricks3D; RPGDirectX; Unity2DCookbook; UnityAI; AoGD3; AoGD2; Build3DUnity; Platformer2D; PolishedGameDev; GPGems2; IntroGameDesign; GameAIPro2)
- Encapsulate each state as its own class implementing a common State interface; the Context delegates the current request to its current state object — behavior changes automatically as internal state changes, replacing giant switch blocks. (HeadFirstPatterns)
- Decide deliberately where transitions live: fixed transitions in the Context, dynamic/runtime-dependent transitions in the state classes — this also chooses which classes stay closed for modification as the system evolves. (HeadFirstPatterns)
- Minimize inter-state dependencies by routing transition decisions through Context getters rather than hard-coding the next concrete state class; clients should never change a Context's state directly — the Context owns its transitions. (HeadFirstPatterns)
- Decompose an FSM into States, Transitions, Rules (trigger conditions), and Events (what checks rules), and nest substate machines for complex states — separating these keeps the machine extensible without bloating the top-level graph. (UnityAI; AoGD3; GPGems2)
- Keep the data-feeding/sensing script ignorant of transition logic — the AI script writes `distanceFromPlayer`/`isPlayerVisible`; the state machine decides — to decouple sensing from deciding. (UnityAI)
- Drive screen/mode logic with a state stack (push/pop, process only the topmost state, a state pops itself when done) instead of one giant switch over CurrentState — adding an inventory/message state no longer bloats one render function. (RPGDirectX)
- Bridge gameplay and an animation state machine with parameters (bool/float/int/trigger): scripts set parameters, the controller decides transitions — keep the controller holding structure, not data, so it's reusable across objects via Animator Overrides. (Build3DUnity; BulletHell; Platformer2D; CertGameDev; Unity5Opt)
- Keep the state machine only as complex as gameplay requires — don't add states the behavior never needs (a slime is a single looping state). (Platformer2D; PolishedGameDev; GameAIPro2)
- Share stateless state objects as static singletons across many Context instances — works only if state objects hold no per-context data; otherwise pass the Context into each handler. (HeadFirstPatterns)
- Distinguish State from Strategy (same class diagram, different intent): State swaps behavior internally as the object's condition changes over time; Strategy is a client-chosen, usually fixed, alternative to subclassing. (HeadFirstPatterns; SWEngGames; IntroGameDesign)
- Separate always-run "processes" (input/network/sound polling) from mutually-exclusive "states" — run processes continuously via a process manager while modes swap above them. (RPGDirectX)

### Command Pattern (Input, Queues, Undo, Replay, Transactions)
- Encapsulate a request as a Command object binding a receiver to an action behind one Execute()/Undo() method — decouples the invoker (input handler, button, AI) from the object that performs the work, and lets the executor create commands rather than mutate game state directly. (HeadFirstPatterns; PatternsUnity6)
- Parameterize invokers with swappable commands (even at runtime) and keep all data a command needs (target + parameters) inside it — remap a control slot or AI action by handing it a different self-contained command. (HeadFirstPatterns; PatternsUnity6)
- Use Command for action queues, RTS unit orders, turn collection, replay recording, and multiplayer rewind/replay — any feature where operation order or history matters. (PatternsUnity6; HeadFirstPatterns; GPGems2; SWEngGames)
- Implement undo by giving each command an Undo() that applies the inverse (store the delta and negate it: Move(-movement)) and keep a history stack — symmetric inverse makes multi-step undo trivial and correct. (HeadFirstPatterns; PatternsUnity6)
- Back undo/redo with two LIFO stacks: on execute push to undoStack and clear redoStack; on undo pop→push→Undo; on redo pop→push→re-Execute; guard each pop with a count check — keeps the two stacks consistent and never pops empty history. (PatternsUnity6)
- Make new action types implement the shared command interface so they plug into existing execute/undo/redo with no infrastructure rewrite — extensibility is the payoff of treating actions as data. (PatternsUnity6; HeadFirstPatterns)
- Build queues, schedulers, thread pools, and deferred/structural changes on commands — wrap add/delete/spawn requests as service-request objects and drain the queue at a safe point so you never mutate a collection you're iterating. (HeadFirstPatterns; SWEngGames; GPGems2; RPGDirectX)
- Keep a command/task queue blind to who enqueues — player, scripted NPC, high-level AI, and network packets all push tasks identically, giving one flexible system; let each queued task draw its own queued-intent feedback for free. (GPGems2)
- Implement crash recovery/persistence by logging command store()/load() to disk and re-invoking Execute() in batch order from the last checkpoint, and apply logging transactionally so a set of operations all complete or none do. (HeadFirstPatterns)
- Use a NoCommand (null object) default and compose MacroCommands to avoid null checks and build combos from existing commands without new code. (HeadFirstPatterns)
- Schedule delayed one-shot work by separating "what to call" from "when" (a timed invoke carrying method + delay) — spawn timing becomes data, not control flow. (CertProgrammer)

### Services, Managers & Singletons (judiciously)
- Use a Singleton only when exactly one instance must exist with a global access point, and use it sparingly — many singletons signal a design problem. (HeadFirstPatterns; IntroGameDesign; PatternsUnity6; CertProgrammer; UnityAI; GameDevUnity)
- Scope singletons to genuinely-unique, cross-cutting services (game state, audio, save system, one world-representation manager) — they grant global read access without manual wiring but every `Manager.Instance` call is a direct dependency, so an API change can force edits across all consumers. (PatternsUnity6; Unity2DCookbook; UnityAI; CertProgrammer; HeadFirstPatterns)
- Implement the singleton with `public static Instance { get; private set; }` assigned in Awake, enforcing uniqueness (destroy a duplicate, or become the instance) — controlled global access that survives execution-order races; the Awake duplicate check is essential under DontDestroyOnLoad across scene reloads. (PatternsUnity6; Unity5Opt)
- Prefer a plain C# static class over a hand-rolled Singleton when you only need global access — same result with less ceremony; reach for a Singleton-as-Component only when the manager genuinely needs MonoBehaviour features (callbacks, coroutines, Inspector). (Unity5Opt; SWEngGames; PatternsUnity6)
- Guard singletons against recreation during application shutdown (track an `_alive`/IsAlive flag and check before cross-object calls in OnDestroy) — leftover instances corrupt scene files. (Unity5Opt)
- Extract singleton/manager boilerplate into a generic `Singleton<T>` base and centralize cross-cutting policy (DontDestroyOnLoad) there — one base-class edit updates every manager that inherits it. (PatternsUnity6)
- Use managers/coordinators as fictitious entities (no on-screen presence) to centralize cooperation among agents — a transient monster-group manager picks optimal targets so units don't all mob one enemy, simplifying multi-agent logic. (GPGems2; GameAIPro2)
- Centralize global input/hit-testing in one manager that raycasts and dispatches rather than letting every clickable object poll input — one detector scales to any number of targets and keeps entities ignorant of the cursor. (CSharpForUnity; GameDevUnity)
- Give the container (cBiota/cGame) the bulk responsibilities a single overloaded class shouldn't have (seeding, iteration, status, service-request queue) — keep each entity class light. (SWEngGames)
- Make objects own their own consequences and lifecycle (the balloon decrements its own counter and Destroys itself; entities handle their own off-screen recycling) rather than an external manager reaching in. (GameDevUnity; ProgramArcade)
- Centralize state in its owner and have others delegate into it (score lives in PlayerController, not the coin) — dependent subsystems (UI, audio) stay in sync from one place; rebuild derived views at the end of every mutating method so display can never drift from state. (Platformer2D; CSharpForUnity; AdvancedCSharp)

### MVC, Document/View & Data–Logic Separation
- Structure interactive systems (tools, editors, game UIs) as Model–View–Controller: Model owns state/logic, View presents it, Controller turns input into model operations — the dominant separation for editors and UIs. (HeadFirstPatterns)
- Keep the Model fully independent of Views/Controllers via Observer — attach different or multiple views to one model at once (debug view, HUD, minimap on one game state); the View delegates interface behavior to a swappable Controller (Strategy) and stays ignorant of how the model is changed. (HeadFirstPatterns; SWEngGames)
- Separate data (Document) from presentation (View): store game state in the doc, per-window state (zoom, viewpoint, wireframe) in the view, app-wide switches in the app — decide placement up front to prevent "where does this variable live" churn, and let one document drive many views (UpdateAllViews → OnDraw) so views never poll. (SWEngGames)
- Separate data from behavior in ECS — store state in data-only components, run logic in systems that query by component signature; entities are pure identifiers, so one system serves many entity kinds and both sides stay independently testable. (ECSFundamentals)
- Separate the "what" (data/config exposed in the Inspector) from the "how" (code), and move tunable parameters out of behavior classes into standalone data assets — designer-exposed fields let you tune without recompiling, and config becomes swappable and reusable. (IntroGameDesign; EditorScripting; PatternsUnity6; BulletHell; AdvancedCSharp; Build3DUnity; CSharpForUnity; Platformer2D; GameDevUnity)
- Separate the in-memory/true value from its displayed value (store 110 while animating the shown count, or store collision shape separate from render mesh) — never assume what you see is what the system tests against. (PolishedGameDev; GameDevUnity; Unity5Opt; SWEngGames)
- Keep tool/editor code in a separate assembly from game code so the runtime ships lean and tool bugs can't break the shipping build — and render a subsystem's own editor inside a host tool (compose authoring UIs like you compose components). (EditorScripting)
- Separate the data-authoring tool from the runtime system and externalize all game data (dialogue, stats, item/spell/character defs, layouts) — never hard-code game data in source, so changes don't force a recompile. (EditorScripting; RPGDirectX; SWEngGames; IntroGameDesign)

### Structural Patterns (Facade, Adapter, Decorator, Composite, Bridge, Proxy)
- Wrap a complex subsystem behind a Facade (a simplified higher-level interface) — gives clients an easy entry point, decouples them from internals, and lets the subsystem evolve; it is not a one-call wall, you can still reach the subsystem when needed. (HeadFirstPatterns; GPGems2)
- Use Adapter to make an incompatible interface fit what a client expects — wrap the adaptee via composition so the client codes to one stable target across many backends; prefer object adapters (composition) over class adapters (multiple inheritance). (HeadFirstPatterns; RPGDirectX)
- Distinguish Adapter (changes an interface), Decorator (adds responsibility, same interface), and Facade (simplifies an interface) by intent, not just structure. (HeadFirstPatterns)
- Use Decorator to attach responsibilities dynamically as a flexible alternative to subclassing — stack same-supertype wrappers (buffs, enchantments, damage multipliers) so a decorated object substitutes transparently, supporting open-ended effect stacking without a class explosion. (HeadFirstPatterns; GPGems2)
- Use Composite to compose objects into part-whole trees and let clients treat individual objects and groups uniformly (scene graphs, menu trees, squad-of-squads) — an operation on the root recurses through the whole tree. (HeadFirstPatterns; SWEngGames)
- Use Bridge when a whole family of methods has multiple implementations — abstract them into one interface class with implementation children (cGraphics → cGraphicsMFC/cGraphicsOpenGL) so you port to a new backend without forking the program or touching call sites. (SWEngGames; GPGems2)
- Use Proxy to put a substitutable surrogate in front of an object to control access (remote, virtual/lazy-load, protection, caching) — a virtual proxy defers creating heavy assets and stands in with a placeholder until ready, keeping the system responsive. (HeadFirstPatterns; GPGems2)
- Use Iterator to traverse a collection without exposing its internal representation, moving traversal responsibility off the aggregate — keeps the aggregate focused on managing its collection (Single Responsibility). (HeadFirstPatterns)
- Insert an actuation/abstraction layer between decision-making and a volatile subsystem (animation controller between AI and animgraph; transport messages converted to typed game messages) — sense/think/act layering lets you swap actuators or netcode without touching deciders. (GameAIPro2; RPGDirectX)
- Never let gameplay code reference animation control parameters or animgraph topology directly — that code/data dependency means every animgraph tweak breaks gameplay; push the coupling as far from gameplay as possible. (GameAIPro2)

### Factories, Strategy, Template Method & Data-Driven Construction
- Encapsulate object instantiation in factories so client code depends on abstractions, not concrete `new` calls — centralize the one place that knows which concrete type to build (a new enemy/item type touches one factory, not every call site). (HeadFirstPatterns; IntroGameDesign; GPGems2; SWEngGames)
- Pick the factory variant by what varies: Simple Factory pulls scattered `new` into one spot; Factory Method uses inheritance to vary one product; Abstract Factory uses composition to vary whole families of related objects (matched terrain/props/enemies for a theme). (HeadFirstPatterns)
- Use Strategy to encapsulate one swappable behavior (force, listener, firing/AI strategy) behind a delegate object — avoids subclass-per-variation and supports plug-in and runtime change. (SWEngGames; HeadFirstPatterns; IntroGameDesign; GPGems2)
- Swap an entity's strategy at runtime via a function pointer or by changing its composed behavior object — a single assignment changes behavior cleanly and can collapse a whole behavioral hierarchy. (GPGems2; SWEngGames; HeadFirstPatterns)
- Use Template Method to fix an algorithm's skeleton in a base (make it final/non-virtual) while deferring specific steps to subclass-implemented virtuals/hooks — preserves invariant ordering (boot/update/render, the delicate parallel-sim step order) while letting children customize steps. (HeadFirstPatterns; SWEngGames; GPGems2; PolishedGameDev)
- Template Method is the Hollywood Principle in action ("don't call us, we'll call you") — the base calls the subclass steps, the subclass never calls up, which prevents dependency rot in extensible pipelines. (HeadFirstPatterns)
- Build entities from a behavioral class hierarchy with an abstract base (Clone/UpdateSelf/HandleInteractions) plus a factory that loads each flyweight on first request and clones (Prototype) — adding a type needs only 2–3 overridden methods, and the factory needs zero knowledge of subclass internals. (GPGems2)
- Drive runtime variation through delegates/data (store "what happens when fired" as a delegate; pass leaf-node logic in via a delegate so one generic ActionNode reuses across behaviors) — behavior becomes swappable data, not branching code. (IntroGameDesign; UnityAI)
- Define each character/agent type by a set of skills, behaviors, and tuning data, never by concrete-type references in code — adding/removing a type means editing data, not hunting code branches; resist adding "just one" type-specific check, because it proliferates and erodes the data-driven design. (GameAIPro2; RPGDirectX; SWEngGames)
- Store behavior logic in ScriptableObject-style assets separate from scene instances, reaching runtime components through a passed-in owner reference — decouples logic from instances and enables reuse. (UnityAI; EditorScripting)
- Use a blackboard / shared singleton component as a communication channel between systems (input writes it, movement reads it) with global/group/local scopes — decouples producer and consumer without direct references while keeping logic coordinated. (GameAIPro2; ECSFundamentals)
- Provide a generic Property/PropertySet layer (name → member, hashed) so tools (editor, save, networking) operate on any object without per-game rewrites — derived types just register extra properties. (GPGems2)

### Object Pooling & Lifecycle Decoupling
- Pool objects instead of Instantiate/Destroy for anything spawned in bulk (bullets, enemies, particles) — repeated allocation/deallocation causes frame spikes and GC churn (worst on mobile/dense scenes); reuse via SetActive(false/true) and pre-spawn an inactive batch off the critical path. (PatternsUnity6; BulletHell; Unity5Opt; IntroGameDesign)
- Keep the pool responsible only for managing reusable instances; let the requesting script set position/rotation and re-initialize on every Get (pooled objects do not receive a fresh Start) — split per-launch setup into a dedicated method the caller invokes after Get. (PatternsUnity6; BulletHell)
- Reset all leftover/per-life state on reuse (zero Rigidbody velocity, hit-flags, timers) — recycled objects otherwise inherit the previous instance's motion/state and spawn dead-on-arrival; reset during Despawn rather than Spawn, since component spawn order is undefined. (BulletHell; Unity5Opt)
- Give each pooled instance a reference to the pool that created it so it can release itself on every exit path (expiry and impact), and enable collection-checks in development to catch double-release. (BulletHell)
- Keep poolable components self-contained and minimize components that reach across and mutate siblings — cross-component pooling logic is a top source of confusing bugs. (Unity5Opt)
- On death/disable, turn off the relevant components (collider, input) rather than destroying the object when other systems still hold references — disable interaction without invalidating those references. (BulletHell; CertGameDev)
- Defer all add/delete/spawn/replicate to a queue drained once per cycle and never instantly destroy a damaged entity (set a dying flag and play a death act first) — mutating a collection mid-iteration is unsafe and abrupt disappearance reads badly. (SWEngGames)
- Give transient entities a fixed lifetime so they self-expire and cap how many of a thing one shooter keeps active (recycle the oldest rather than block) — prevents unbounded growth without leaving the player defenseless. (SWEngGames; BulletHell; RPGDirectX)
- Maintain two-way references safely: when either side of an A↔B link can die independently, each destructor nulls/removes the other's pointer and a fixPointerRefs hook scrubs dangling target pointers — and null its Next before deleting a list node so the recursive destructor doesn't free the rest. (SWEngGames; RPGDirectX)
- Inject runtime-only references (a pool created in Awake) into spawned objects via an Init method called right after Instantiate — the editor can't assign a runtime object, so the spawner passes it post-spawn. (BulletHell)

### Initialization Order & Lifecycle Robustness
- Use engine lifecycle hooks deterministically (Awake for self-contained setup, Start for cross-object references, Update for per-frame, OnDestroy for cleanup/unsubscribe) and never call them yourself — cache component references once in Awake instead of GetComponent per frame/hit. (GameDevUnity; Build3DUnity; Platformer2D; Unity5Opt; BulletHell; AdvancedCSharp; CSharpForUnity; Unity2DCookbook)
- Control initialization order explicitly when a subscriber's OnEnable depends on a manager's Awake-set singleton (`[DefaultExecutionOrder]`, lower runs earlier) — Unity gives no default ordering, so Instance may be null when observers subscribe. **When it flips:** needing Script Execution Order to fix plain logic usually signals fragile tight coupling, so reserve it for genuinely time-sensitive systems (e.g. audio). (PatternsUnity6; Unity5Opt; IntroGameDesign)
- Wrap the engine lifecycle in a uniform set of entry points across all objects (constructor, startGame, startLevel, draw, postDraw, update) with consistent signatures — a common vernacular guarantees complete coverage and predictable composition/teardown. (PolishedGameDev; RPGDirectX)
- Make every system function return a success/failure code, check it at each init step, abort and release on first failure, and pair every acquisition with a guaranteed release — a half-initialized system is a crash waiting to happen and leaks accumulate into instability. (RPGDirectX; AdvancedCSharp)
- Use early-return guard clauses for invalid input and guard any operation that throws on empty/invalid state (check Count/ContainsKey before Dequeue/Add) — convert recoverable edge cases into handled, observable feedback rather than crashes. (AdvancedCSharp; PatternsUnity6; UnityAI)
- Use `nameof(Method)` instead of string literals for scheduled calls and match animator/parameter names exactly between code and controller — string keys are silent contracts; a misspelling never fires and renames silently break. (PatternsUnity6; BulletHell)
- Make singleton/world-resource access fail loud (throw on zero or more than one instance) and lazily create it on first run if absent — a hard error surfaces accidental duplicates instead of silently picking the wrong one. (ECSFundamentals)

### Applying & Removing Patterns (KISS / YAGNI / Anti-Patterns)
- Keep It Simple — solve in the simplest way that works; simplicity, not pattern-count, is the goal, and a pattern that isn't needed only adds complexity. (HeadFirstPatterns; IntroGameDesign)
- Treat design principles as guidelines you violate knowingly, not absolute rules — reserve the heavy machinery for the parts that actually change; instantiating a stable class directly is fine. (HeadFirstPatterns)
- Introduce a pattern only when it addresses a real, present problem or a change that is genuinely likely — add flexibility for change that will actually happen, not speculative generality you may never use. (HeadFirstPatterns)
- Let patterns emerge from design principles and the simplest working code, applying one (often adapted, rarely canonical) when a need naturally arises — match a candidate by intent and applicability, and verify you can live with its consequences before committing. (HeadFirstPatterns)
- Treat refactoring time as pattern time — dense conditionals hint at State, tangled concrete dependencies hint at Factory; restructure toward the pattern when the need emerges. (HeadFirstPatterns; SWEngGames)
- Don't be afraid to remove a pattern — when planned flexibility went unused and the system got complex, a simpler solution without it is the right move; be willing to cut a flaky feature rather than ship it (avoid gold-plating and feature creep). (HeadFirstPatterns; SWEngGames)
- Document recurring bad-but-tempting solutions as named anti-patterns (e.g. "Golden Hammer": forcing one familiar tech onto every problem) — say why they look attractive, why they hurt, and which good pattern replaces them. (HeadFirstPatterns)
- Use a production system / heavy AI machinery only when the problem genuinely demands it (many non-quantifiable factors, fast reaction, expert knowledge resisting a clean algorithm) — otherwise simpler FSMs and plain rules suffice; complexity should come from composition, not exotic mechanics. **When it flips:** smarter is not always better — predictable, rule-based automata let players plan, so use simple AI unless fiction-driven interaction dominates. (GameAIPro2; DesigningGames)
- Never store the same fact in two places ("no forgery") and don't write the same code twice — derive values instead of caching duplicates that desync, and factor any 3–4 line repeat into a method before two copies drift apart. (SWEngGames)
- Use the shared pattern vocabulary (and the taxonomy: Creational/Behavioral/Structural, Class vs Object) to communicate designs at the design level — naming intent ("this is a State machine here") aligns the team faster. (HeadFirstPatterns)
- Treat recurring economic/system structures as named design patterns with a fixed template, and compose/nest them to build complex systems from understood parts — a shared vocabulary makes deep structures comparable and reusable rather than reinvented. (GameMechanics; HeadFirstPatterns)

### Dependency Mapping & Build Order
- Map dependencies (a relationship where changing one element forces changes in another) and build a dependency stack — graph the strongest dependencies, ignore the weakest, so you avoid building on shifting foundations. (DesigningGames; GPGems2)
- Build bottom-up: solidify and playtest core/foundation elements first (raising their certainty), then stack dependent elements on proven ground — uncertainty multiplies through dependencies, so upper-stack elements built on shaky foundations get destroyed when the foundation shifts. (DesigningGames)
- Sequence work by dependency to minimize rework (lock movement mechanics in graybox before animating; lock a tool's identity-defining properties before tuning) — finished work on a foundational element is destroyed when that foundation moves. (DesigningGames)
- Model tech/build trees and an entity's economy as explicit dependency graphs per actor — a single basis for building toward goals and for inference (seeing a Pikeman implies a Barracks). (GPGems2)

## Networking & Multiplayer Systems

### Topology & Network Architecture
- Treat "online/multiplayer" as a baseline requirement once the genre expects it, and bake the transport model (LAN-only vs. internet-native) into the design from the start — systems that bolt networking on late fight their own architecture and fail to scale to dispersed play (post-Doom LAN vs. Quake-built-for-internet). (GDEssentials)
- Make server-authoritative, many-client topology the default for shared persistent worlds — centralize world state on a server so all clients stay consistent at scale; it is the MMO's defining system. (GDEssentials)
- For massive/persistent worlds, plan a multi-server / lobby / connection-server topology rather than one host — scale a single logical world across many machines instead of betting on one. (RPGDirectX; GDEssentials)
- Choose the system topology that matches your workload, not the most powerful architecture — a heavier networking stack's baseline overhead loses to a lighter one when the workload doesn't need its capacity. (Unity6Opt)
- Choose the timing model deliberately — real-time (synchronous or asynchronous) vs. turn-based; turn-based "show up when you can" play scales best for asynchronous/social audiences and lets players come and go freely. (Challenges)
- Budget concurrency limits explicitly — the simultaneous-player count is a hard system constraint that shapes data layout, update cadence, and netcode; set min/max player limits per match. (GDEssentials; Challenges)
- Ship moddable/forkable, openly-documented systems to seed an ecosystem — freely-available codebases (Essex MUD spreading across ARPAnet) and open cloneable architectures multiply content and adoption through the community. (GDEssentials)

### Replication & State Sync
- Separate transport messages from game messages — convert raw network create/destroy/receive callbacks into a typed, sized game-message format the application understands, so netcode is decoupled from game logic. (RPGDirectX)
- Wrap every game message with a header (type, size, sender ID) plus a fixed data buffer, then cast to specific message structs — one container carries all message kinds and the type field drives interpretation. (RPGDirectX)
- Send state-change messages (state, position, direction, speed, latency) and only update a player's animation when it differs from the last known one — minimize redundant work and traffic. (RPGDirectX)
- Choose delivery semantics per message — guaranteed+sequenced for critical events, unreliable for frequent updates — and mark priority so a throttler can drop low-priority data; pay the reliability cost only where it matters. (RPGDirectX)
- Store a per-player context pointer with the connection so network events map straight to the player's data instead of scanning by ID — fast association of network events to game entities. (RPGDirectX)
- Bridge networking and application through a derived class overriding callbacks plus a global app pointer, and keep the application matched on a shared GUID — mismatched server/client GUIDs are the top reason peers fail to connect, and the indirection keeps neither component dependent on the other's internals. (RPGDirectX)
- Treat control/network latency as a system constraint, not an afterthought — pipelines impose a 3–4 frame minimum; pick frame rate by need (60 fps for high-skill rapid-input shooters/racers/fighters, 30 fps for art/narrative/turn-based) and defend it against per-frame-budget pressure. (DesigningGames; VRUnity)

### Authority, Determinism & Lockstep
- Route ALL input (keyboard, mouse, joystick, network, time) through one input system that records every frame — this single record enables bug repro, replays, and lockstep multiplayer where you transmit input, not state. (GPGems2)
- Make the simulation fully deterministic for lockstep and replay — never change game state in rendering functions, avoid uninitialized data, and approximate async events; any unpredictable input breaks determinism and desyncs peers. (GPGems2; GameMechanics)
- Give the update loop and the render loop separate RNGs and keep RNG call counts identical between runs — a shared generator with a variable render-per-update ratio makes state indeterminate and breaks replay/multiplayer; gate randomness behind a fixed time-step accumulator. (GPGems2; PolishedGameDev)
- Use deterministic, controllable PRNGs you can seed and restart — never `rand()` (non-portable, single-stream, unseedable to a saved state); deterministic seeds also power attract demos, instructional replays, and regression tests. (GPGems2; PolishedGameDev; GameMath)
- Advance the whole engine in lockstep off one explicit elapsed-time clock passed into Update/Render — one clock drives spells, characters, and animations together so the simulation stays consistent. (RPGDirectX)
- Keep simulation objects in one controlled array with deterministic ordering, not one-thread-per-object — OS threads aren't truly parallel and schedule erratically, destroying reproducible ordering. (SWEngGames)
- Record some game state (entity health/positions) alongside input and diff on playback — automatically catches race conditions and floating-point/optimizer divergence (the classic lockstep desync) before it becomes visible. (GPGems2)

### Scalability of Spawns & Economy
- Support dynamic scalability when player count is variable — scale spawned creatures, items, and gold to the number of players present so a zone stays competitive, never trivial or a slaughter. (Challenges)
- Decide drop-out / join-in handling up front — AI takeover, seamless continuation, ruined match, or wait-for-next-match — rather than discovering it live. (Challenges)
- Defer all add/delete/spawn/replicate to a queue drained once per cycle — mutating a collection you're iterating is unsafe, and a single drain point gives the server a controlled, reproducible spawn cadence. (SWEngGames)
- Cap network and spawn work per frame — funnel incoming callbacks into a ring-buffer message queue and process only a capped number per frame so the server never bogs down on bursts; never process network data inline. (RPGDirectX)
- Cap or floor prices via a system agent (Catan-style bank, MMO shopkeepers that always buy) — base prices keep low-level "employment" steady and prevent runaway market values at scale. (GDWorkshop)
- Manage persistent / meta economies as first-class design — players will create secondary markets (MMO real-money trades, card markets) you don't control, so use rarity as your main lever and watch for collusion and holes in trade-enabled worlds. (GDWorkshop; AoGD3)

### Anti-Grief & Containment
- Assume bad actors and build containment into the system, not after the fact — PvP servers, report/record, and per-player block/contact controls; avoid exploitable systems (unrestricted PvP, stealing/looting, kill-stealing where only the final-blow dealer gets XP, misrepresentable trades) and confine PvP to special areas rather than policing afterward. (Challenges; AoGD3)
- Solve only the most severe griefing strategies (high griefer-fun × high victim-harm) by making them impossible — pass-through doors, safe zones — ignore low-severity ones, and add policing (votes/mods) only as a last resort. (DesigningGames)
- Treat divergent player goals as system threats in multiplayer — one player's invented goal breaks everyone's finely balanced experience; align goals first, then add buffers. (DesigningGames)
- Use large player counts as a buffer against quitters, griefers, and divergent goals — one bad actor matters far less in 12 than in 2. (DesigningGames)
- Give competitive games surrender mechanics and reduce enforced interdependency (optional short alliances, shared victory without shared failure) — ending a hopeless game beats forcing a foregone loss, and low interdependency keeps one player from dragging the team down. (DesigningGames)
- Reduce skill-differential damage with matchmaking and structural separation (solo before group, single before multiplayer) plus adaptive in-match training — negative-feedback-balance teams by equalizing skill ratings before a match, since players enjoy uncertain outcomes against similar-skill opponents. (DesigningGames; GameAIPro2; UnityAI)
- Design assuming clients can be read and overwritten — external tools (Game Genie-style memory patching) will alter values, so validate and protect the state that must stay authoritative. (GDEssentials)

### Viral & Network-Effect Loops
- Engineer virality as a system — propagation mechanics (invite rewards, newsfeed testimonials, milestone broadcasts) should grow the player base from play itself; in networked games this is designed, not hoped for. (Challenges)
- Reward both inviting and accepting invites with tangible in-game benefits — propagation that grants resources outcompetes solo-player apps. (Challenges)
- Use friend-affecting mechanics (help or harm friends, alter their score) — acting on real social contacts is more satisfying and more viral than acting on strangers. (Challenges)
- Target the propagation message at the recipient's self-interest, not the sender's — "which X are you?" spreads; "view my room / join my court" doesn't. (Challenges)
- Exploit the positive feedback where faster propagation feeds still-faster propagation (more friends shown → more installs) — design for that compounding network-effect loop. **When it flips:** over-propagation turns from fun into spam → build throttles and respect etiquette or the loop self-destructs at critical-mass backlash. (Challenges)
- Engineer required-return mechanics (timed ticketing, maxed-earning cash-ins, changing constraints) — integrating time into mechanics pulls players back; timeless mechanics don't. (Challenges)

### Persistence & Identity
- Persist player identity, not just a number — recording initials made a score belong to someone; attaching achievement to an identity is what turns a transient session into a social/competitive ladder that drives replay. (GDEssentials)
- Design persistent-world state as a first-class system for online play — persistence, identity, and grouping (characters, guilds) are the load-bearing systems of MMOs, not genre skin. (GDEssentials)
- Let players author and persist their own content inside the world — player-authored, persisted state (MUD-style environments) extends the possibility space far beyond shipped content. (GDEssentials)
- Maintain world consistency across episodic/persistent content — one out-of-character or contradictory episode retroactively spoils the whole persistent world and kills player projection. (AoGD3; AoGD2)
- Build community-support systems (guilds/clans, friend lists, leader recognition) as part of the system — in multiplayer the community is internal to the design, not external; support the immediate game, the session, and the long-term meta. (Challenges; AoGD3)
- Manage persistent high-score / leaderboard systems against demoralizing leaders — use rolling-window scores, periodic resets, or player-triggered end conditions to keep new players competitive. (Challenges)

### Concurrency & Network Testing
- Guard shared queue/player memory with tiny, fast critical sections when a background network thread and the main loop both touch it — concurrent producer/consumer access corrupts data without locking, but holding a lock too long can hang the system. (RPGDirectX)
- Wrap all network/file/API code in a virtual-network module the test suite controls — enables reliably reproducing broken-network conditions (lost connection, corrupt packets, slow downloads, missing files). (PolishedGameDev)
- Heavily document networking failure modes (dropped connection, unaccepted invite, lag, invisible player, scoring error) by frequency, timing, and conditions — lag and invisible players are symptoms of deeper issues (dropped packets, excessive bandwidth) and are hard to reproduce. (QATesting)
- Test online games online with strangers, not friends in a room, and partition large persistent worlds into zones with a tester (and networking strike team) per system — match test conditions to shipping conditions or the protocol hides the very flaws you are hunting. (DesigningGames; QATesting)
